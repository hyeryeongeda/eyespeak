# EYESPEAK 아이트래킹 개발 — 일의 순서

> 기획의도(루게릭 환자 시선 기반 의사소통)에 가장 적합한 모델·파이프라인을 만들기 위한 단계별 작업 순서.

---

## 전제 정리

- **목표**: 실사용 환경(침대/휠체어, 일반 또는 적외선 웹캠)에서 **시선으로 UI 선택**이 안정적으로 동작.
- **한계 인식**: 데이터셋(전용 카메라·고정 거리)과 실제 환경 차이, RGB 한계, 연산·지연 이슈.
- **전문가 요약**: **데이터가 가장 중요** / 가능하면 **적외선 카메라**(노트북 직결 선호) / **UI 버튼 크기로 오차 흡수** / **OpenCV 전처리 활용**.

---

## 1단계: 하드웨어·환경 결정 (우선 수행)

**목적**: “어떤 카메라로, 어떤 환경을 타깃으로 할지”를 먼저 정해서 이후 데이터·모델 전략이 흔들리지 않게 함.

| 순서 | 작업 | 산출물 | 비고 |
|------|------|--------|------|
| 1-1 | **적외선 vs 일반 웹캠** 결정 | 1페이지 결정서 | 전문가: 조명·반사 이슈에 IR이 유리. 예산·구입 가능성(노트북 연동 IR 웹캠) 검토. |
| 1-2 | **타깃 거리·각도 범위** 정의 | 숫자로 된 스펙 (예: 40~60cm, ±30° 등) | “침대에 누운 상태 / 휠체어” 등 실제 사용 시나리오 1~2개로 범위 고정. |
| 1-3 | (IR 선택 시) **테스트용 IR 웹캠** 선정·구입 | 제품명, 드라이버/API 확인 | 노트북 USB 직결 가능 제품 우선. |

**다음 단계로 가기 전 체크**: “일반 웹캠만 쓸지, IR을 쓸지”와 “얼마나 가까이/얼마나 기울어져도 쓸지”가 문서로 정리되어 있는지.

---

## 2단계: 데이터 전략 수립

**목적**: 학습/검증 데이터가 “실제 사용 환경”을 반영하도록 해서, 이전에 겪었던 **데이터-환경 괴리**를 줄임.

| 순서 | 작업 | 산출물 | 비고 |
|------|------|--------|------|
| 2-1 | **AI Hub(안구 움직임) 데이터 포맷** 확인 | 폴더 구조, 메타데이터, 레이블 유무 문서 | 레이블 있음 → 파인튜닝/학습용. 없음 → 추론·준지도용. 500GB 전부 말고 **샘플(소량)** 먼저. |
| 2-2 | **도메인 갭 정리** | 갭 목록 (예: 거리/각도/해상도/조명) | “AI Hub는 고정 거리 → 우리는 40~60cm 변동” 등. 이 갭을 줄이기 위한 수단(전처리·재수집·합성) 식별. |
| 2-3 | **최소 데이터 규모** 설정 | 클래스별 장수, 총 이미지 수 | 전문가: 클래스당 최소 100, 이상적 1000. 16방향이면 1,600장 이상. “9그리드면 9×100” 등으로 목표치 수치화. |
| 2-4 | **직접 수집 vs 기존만 활용** 결정 | 데이터 계획 1페이지 | 직접 수집 시: IR/일반 웹캠 중 무엇으로, 누가(환자 유사 포즈), 몇 장/몇 방향으로 찍을지. 품 대비 효과 보고 결정. |

**다음 단계로 가기 전 체크**: “어떤 데이터로, 어떤 레이블(방향/그리드)로 학습·검증할지”가 한 문장으로 설명 가능한지.

---

## 3단계: 파이프라인 고정 (모델 + 전처리)

**목적**: “얼굴/눈 검출 → 시선 추정 → 그리드(0~8)”까지 한 번에 돌아가는 경로를 하나 정하고, 지연·정확도를 같이 본다.

| 순서 | 작업 | 산출물 | 비고 |
|------|------|--------|------|
| 3-1 | **전처리 공통화** | OpenCV 기반 전처리 스크립트/함수 | 밝기·대비·노이즈·얼굴/눈 크롭 등. 전문가 권장 OpenCV 활용. 학습/추론 동일 적용. |
| 3-2 | **베이스 모델 선택** | 1개 모델로 고정 (예: L2CS-Net 또는 ETH-XGaze) | “얼굴+눈” 입력 모델이 도메인 갭 보정에 유리. 이전에 L2CS-Net 경험 있으니 연동·재현부터. |
| 3-3 | **입출력 규격 통일** | 입력 해상도, 출력 형식(yaw/pitch 또는 그리드 인덱스) 정의 | gaze_server와 9그리드 UI가 기대하는 형식과 맞출 것. |
| 3-4 | **오프라인 정확도 측정** | 스크립트 + 결과 수치(각도 오차, 그리드 정확도) | AI Hub 또는 자체 검증셋으로. “모델만 놓고 보면 얼마나 나오는지” 기록. |
| 3-5 | **실시간 지연 측정** | FPS, end-to-end 지연(캡처→그리드 반영) | 전문가: 실시간 지연은 어느 정도 있을 수 있음. 수치로 파악 후, UI·기능 기획(예: LLM 대기 시간)에 반영. |

**다음 단계로 가기 전 체크**: 동일 전처리·동일 모델로 “오프라인 수치”와 “실시간 지연”이 문서/숫자로 남아 있는지.

---

## 4단계: UI·오차 흡수 설계

**목적**: “모델이 완벽하지 않아도” 사용 가능하도록, **UI와 오차 범위를 맞춤** (전문가 제안 반영).

| 순서 | 작업 | 산출물 | 비고 |
|------|------|--------|------|
| 4-1 | **현재 오차 범위 정리** | 그리드당 오차(각도 또는 픽셀), 잘못 선택되는 패턴 | 3단계 측정 결과를 “어느 방향에서 어디로 틀리는지”까지 정리. |
| 4-2 | **버튼/그리드 크기·간격 재설계** | UI 스펙 (버튼 최소 크기, 그리드 간격) | 오차 범위 안에서도 선택이 겹치지 않도록 **버튼을 키우고**, 필요 시 그리드 수 조정(예: 9→6). |
| 4-3 | **캘리브레이션·감도**와 연동 | 캘리브레이션 절차, 감도 파라미터 | 사용자별 보정으로 오차 일부 상쇄. 감도는 “반응 속도 vs 떨림” 트레이드오프 명시. |
| 4-4 | (선택) **확정 방식** 도입 | “N초 응시 시 선택” 등 규칙 | 잘못 선택 감소. SOS는 “즉시” vs 일반 선택은 “짧은 유지” 등 기능별로 다르게 설계 가능. |

**다음 단계로 가기 전 체크**: “오차가 이 정도일 때, 이 UI 스펙이면 사용 가능한지”가 팀/테스터와 합의되었는지.

---

## 5단계: 통합·환자 시나리오 테스트

**목적**: 실제 사용에 가까운 시나리오에서 “의사소통 기능”이 통째로 동작하는지 검증.

| 순서 | 작업 | 산출물 | 비고 |
|------|------|--------|------|
| 5-1 | **gaze_server + 선택한 모델** 연동 | 단일 서버에서 “캠 → 그리드”까지 동작 | 기존 9그리드 HTML과 호환 유지. |
| 5-2 | **MVP 기능별 시나리오** 작성 | SOS / 필수 의사소통 / 자유 의사소통 등 시나리오 1~2줄씩 | “침대에 누운 상태에서 SOS 버튼 응시 → 알람” 등. |
| 5-3 | **통합 테스트** (자기 자신 또는 동의한 테스터) | 체크리스트, 버그/불편 목록 | 거리·각도·조명을 1단계에서 정한 범위로. “선택이 안 됨/잘못 선택됨” 구체적으로 기록. |
| 5-4 | **반복** | 3→4→5 수정 후 재테스트 | 오차가 크면 3(전처리·모델·데이터), UX 불만이면 4(버튼·캘리브레이션)부터 다시. |

**다음 단계로 가기 전 체크**: “SOS + 필수 의사소통”이 정해진 환경(일반/IR, 거리)에서 **재현 가능한 수준**으로 동작하는지.

---

## 6단계: 지속 개선 (데이터·모델)

**목적**: 실제 환경 데이터가 조금이라도 쌓이면, 그걸로 **도메인 맞춤** 개선.

| 순서 | 작업 | 산출물 | 비고 |
|------|------|--------|------|
| 6-1 | **실사용 로그/수집** 설계 | 익명화된 시선·선택 로그 또는 이미지 수집 방식 | 환자 동의 하에. 프라이버시·윤리 준수. |
| 6-2 | **소량이라도 “실환경” 데이터** 확보 | 검증셋 또는 파인튜닝용 소규모 데이터 | 2단계 최소 규모에 맞춰 클래스당 100장 등. |
| 6-3 | **파인튜닝 또는 재학습** | 파인튜닝 스크립트, 새 체크포인트 | L2CS-Net 등 선택 모델을 실환경 데이터로 파인튜닝. |
| 6-4 | **재측정·재테스트** | 3단계·4단계·5단계 지표 다시 수집 | 개선 여부를 숫자와 체감으로 확인. |

---

## 요약: 한 번에 보는 순서

```
1. 하드웨어·환경 결정 (IR vs 일반, 거리·각도)
      ↓
2. 데이터 전략 (AI Hub 포맷 확인, 갭 분석, 최소 규모·수집 여부)
      ↓
3. 파이프라인 고정 (전처리 + 모델 1개 + 오프라인/실시간 측정)
      ↓
4. UI·오차 흡수 (버튼 크기, 캘리브레이션, 확정 방식)
      ↓
5. 통합·시나리오 테스트 (gaze_server 연동, MVP 시나리오, 반복)
      ↓
6. 지속 개선 (실환경 데이터 수집, 파인튜닝, 재측정)
```

---

## 이 프로젝트(EYESPEAK)에 가장 맞게 하려면

- **정확도만 보지 말고**, “환자가 **의도를 전달할 수 있는지**”를 1차 지표로 두는 것이 좋음.  
  → 그래서 **4단계(UI·오차 흡수)**를 빼먹지 않고, 버튼 크기·캘리브레이션을 반드시 포함.
- **데이터**는 “실제 사용 환경에 가까운 것”이 있어야 이전 한계(데이터셋-웹캠 갭)를 줄일 수 있음.  
  → 2단계에서 “직접 수집 vs 기존만”을 명확히 하고, 가능하면 소량이라도 **실환경(또는 유사 환경)** 데이터 확보.
- **지연**은 완전 제거보다 “기획과 조합”(예: SOS는 즉시, 문장 선택은 1~2초 유지)으로 설계.  
  → 3단계에서 지연을 측정한 뒤, 4·5단계에서 “확정 시간” 등으로 흡수.

이 순서대로 진행하면, “기획의도에 가장 적합한 아이트래킹”을 단계적으로 만들어 나갈 수 있습니다.
