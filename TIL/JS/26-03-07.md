## 1. 2단계 추천 아키텍처 (Candidate Generation + Re-ranking)

### 두괄식 결론

1. **1단계** — 정답 후보 생성
2. **2단계** — 리랭킹으로 최종 후보 순위 선정

위의 로직이 '추천'에 매우 효과적이다.

---

### 1.1 개념

추천 시스템에서 **2단계 아키텍처**란, 추천 과정을 두 개의 독립된 단계로 분리하는 설계 패턴이다.

**Stage 1 — Candidate Generation (후보 생성)**

- 전체 아이템 풀에서 **빠르게** 유력한 후보를 추려내는 단계
- **속도**가 핵심이다. 정밀도는 다소 희생할 수 있다

**Stage 2 — Re-ranking (리랭킹)**

- Stage 1이 추려낸 후보를 **정밀하게** 재정렬하는 단계
- 후보 수가 적으므로, 더 풍부한 컨텍스트와 복잡한 모델을 사용할 수 있다

**왜 분리하는가?**

| 접근                                      | 속도     | 정확도   | 문제               |
| ----------------------------------------- | -------- | -------- | ------------------ |
| 전체 아이템에 정밀 모델 적용              | 느림     | 높음     | 실시간 서비스 불가 |
| 전체 아이템에 빠른 모델만 적용            | 빠름     | 낮음     | 추천 품질 부족     |
| **빠른 모델로 축소 → 정밀 모델로 재정렬** | **빠름** | **높음** | **두 마리 토끼**   |

이 원리는 YouTube 추천 논문(Covington et al., 2016)에서도 **"classic two-stage information retrieval dichotomy"** 라고 표현한 바 있다.

---

### 1.2 근거 논문 ① — 리랭킹 단계의 필요성 실증

> **논문**: Neural Re-ranking in Multi-stage Recommender Systems: A Review
> **게재**: IJCAI 2022 Survey Track

IJCAI 서베이 논문에서 다양한 리랭킹 알고리즘(MiDNN, GSF, DLCM, SetRank, PRM 등)을 초기 랭킹 모델(LambdaMART)과 직접 비교 실험한 결과:

| 데이터셋            | Init (리랭킹 없음) | PRM (최고 리랭킹) | 개선폭   |
| ------------------- | ------------------ | ----------------- | -------- |
| Ad (MAP@10)         | 0.6075             | 0.6178            | +1.7%    |
| PRM Public (MAP@10) | 0.1842             | 0.3096            | **+68%** |

*MAP@10(Mean Average Precision at 10): 상위 10개 추천의 평균 정밀도. 정답을 얼마나 상위에, 얼마나 정확하게 배치했는지를 종합적으로 측정하는 지표.*

**6개 리랭킹 모델 전부가 Init를 상회**했으며, 논문은 다음과 같이 결론짓는다:

> _"The results of all the re-ranking algorithms are appealing and outperform the initial ranker by a large margin."_
> _"This confirms the necessity of the re-ranking stage in MRS by integrating the listwise context."_

---

### 1.3 근거 논문 ② — LLM 리랭킹의 효과 실증

> **논문**: LLM-enhanced Reranking in Recommender Systems (2024, arXiv: 2406.12433)

GMF로 사용자당 20개 후보를 생성(Stage 1)한 뒤, 다양한 리랭킹 모델로 재정렬(Stage 2)하는 실험 결과:

**GMF(리랭킹 없음) 대비 LLM4Rerank-A Hit Ratio 개선폭:**

| 데이터셋     | GMF (리랭킹 없음) | LLM4Rerank-A | 개선폭   |
| ------------ | ----------------- | ------------ | -------- |
| ML-1M        | 0.4156            | 0.7031       | **+69%** |

리랭킹을 추가한 **모든 모델(DLCM, PRM, RankGPT, LLM4Rerank)이 일관되게 초기 랭킹을 상회**했다.

## 2. Stage 1 추천 모델 프로토타입 평가

위의 이론적 기반을 바탕으로 우리 프로젝트에 맞게 이를 적용, 테스트 코드를 작성하고 평가해보았다. 다만, 아직 GMS key를 받지 못해 Stage 1만 진행하고, 추후에 Stage 2까지 완료하려 한다.

### 2.1 5-Signal Weighted Scoring 설계

ALS 환자가 다음에 선택할 표현을 예측하기 위해 5가지 시그널을 조합한다.

| 시그널 | 이름   | 설명                       | 예시                         |
| ------ | ------ | -------------------------- | ---------------------------- |
| **T**  | 시간대 | 이 시간대에 자주 쓰는 표현 | 아침 7시 → "세수하고 싶어요" |
| **F**  | 빈도   | 전체적으로 자주 쓰는 표현  | "물 주세요"가 가장 많음      |
| **R**  | 최근성 | 최근에 쓴 표현 (지수 감쇠) | 5분 전에 "아파요" 선택       |
| **S**  | 전이   | 이전 표현 다음에 오는 패턴 | "배고파요" → "죽 주세요"     |
| **P**  | 선호도 | 보호자 설문 기반 초기 선호 | "환자가 죽을 주로 먹습니다"  |

**점수 계산**: `Score(표현, 시점) = α·T + β·F + γ·R + δ·S + ε·P`

150개 모든 표현에 대해 점수를 계산하고, 상위 3개를 화면에 표시한다.

**각 시그널의 원점수 계산 방식 (프로토타입 코드 기준):**

| 시그널 | 계산 방식                                                                                                                      | 비고                                       |
| ------ | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------ |
| **T**  | `0.7 × (해당 시간대 이 표현 빈도 / 시간대 내 최고 빈도) + 0.3 × (해당 시간대 이 카테고리 빈도 / 시간대 내 최고 카테고리 빈도)` | 카테고리 레벨 스무딩으로 희소 데이터 보완  |
| **F**  | `log(1 + 이 표현의 전체 빈도) / log(1 + 전체 최고 빈도)`                                                                       | 로그 스케일링으로 극단적 빈도 격차 완화    |
| **R**  | `e^(-0.3 × 경과시간(h))`                                                                                                       | 지수 감쇠. 단, 가중치 0이므로 실사용 안 함 |
| **S**  | `직전 표현 → 이 표현 전이 횟수 / 직전 표현의 전체 전이 횟수`                                                                   | 조건부 확률                                |
| **P**  | `보호자 설문 가중치 / 최대 가중치` (0~1 정규화)                                                                                | 사용 로그와 무관한 고정 값                 |

**핵심 설계 — 상황별 가중치 전환:**

가중치 세트는 단순히 2개가 아니라, 데이터 축적량에 따라 세션 시작 가중치가 3단계로 분기하여 **총 4개**가 존재한다.

| 상황                            | T    | F    | R    | S    | P    |
| ------------------------------- | ---- | ---- | ---- | ---- | ---- |
| **세션 시작 + 로그 50건 미만**  | 0.40 | 0.05 | 0.00 | 0.00 | 0.55 |
| **세션 시작 + 로그 50~199건**   | 0.35 | 0.10 | 0.00 | 0.00 | 0.55 |
| **세션 시작 + 로그 200건 이상** | 0.30 | 0.15 | 0.00 | 0.05 | 0.50 |
| **세션 중간**                   | 0.05 | 0.00 | 0.00 | 0.80 | 0.15 |

데이터가 적을수록 P(선호도)와 T(시간대) 비중이 더 높고, S(전이)는 완전히 꺼진다. 데이터가 충분히 쌓이면 S에도 약간의 가중치(0.05)를 부여하기 시작한다.

**가중치 전환 조건:**

세션 중간 가중치로 전환되려면 두 조건이 모두 충족되어야 한다:

1. 직전 표현이 존재 (세션 첫 표현이 아님)
2. 그 직전 표현에 대한 **전이 데이터가 실제로 축적**되어 있음

즉, 세션 중간이라도 직전 표현의 전이 데이터가 한 번도 쌓이지 않았으면 세션 시작 가중치를 사용한다. 단순히 "이전 표현 유무"가 아니라 **"이전 표현의 전이 통계 유무"** 까지 확인하는 구조다.

### 2.2 평가 결과

시뮬레이션 환자 페르소나(70세 남성 ALS 환자)로 30일간 1,018건의 사용 로그를 생성하여 평가했다.

**평가 지표:**

| 지표 | 의미 | 우리 서비스에서의 해석 |
| --- | --- | --- |
| **Hit@K** | 추천 K개 안에 정답이 포함된 비율 | Hit@3 = 첫 화면에서 원하는 표현을 찾는 확률 |
| **Hit@1** | 1순위 추천이 정답인 비율 | 첫 번째 추천이 바로 정답인 확률 |
| **MRR** | 정답의 평균 순위 역수 (Mean Reciprocal Rank) | 정답이 평균적으로 몇 번째에 위치하는지. 1에 가까울수록 상위에 위치 |

**비교 대상 (베이스라인):**

| 방식                   | 설명                                                    |
| ---------------------- | ------------------------------------------------------- |
| **Random**             | 150개 중 무작위 3개 추천. 최악의 기준선                 |
| **Popular**            | 전체에서 가장 많이 사용된 상위 3개를 항상 동일하게 추천 |
| **Time-only**          | 현재 시간대에서 가장 많이 사용된 3개 추천               |
| **Stage 1 (5-signal)** | 우리 모델. 5가지 시그널을 종합하여 추천                 |

**메인 비교 결과:**

| 방식                   | Hit@1    | Hit@3     | Hit@6     | Hit@9     | MRR       |
| ---------------------- | -------- | --------- | --------- | --------- | --------- |
| Random                 | 0.0%     | 0.3%      | 3.1%      | 4.6%      | 0.012     |
| Popular                | 4.9%     | 10.0%     | 15.7%     | 22.3%     | 0.094     |
| Time-only              | 4.6%     | 12.3%     | 20.6%     | 25.1%     | 0.106     |
| **Stage 1 (5-signal)** | **8.3%** | **15.4%** | **24.0%** | **30.0%** | **0.143** |

- Random 대비 약 **50배 개선** (Hit@3: 0.3% → 15.4%)

**세션 컨텍스트별 성능:**

| 상황      | Hit@3 | 설명           |
| --------- | ----- | -------------- |
| 세션 시작 | 9.6%      | T+P만으로 예측          |
| 세션 중간 | **19.6%** | S(전이) 활용 → 2배 성능 |

### 2.3 Ablation Study (시그널 기여도)

Ablation Study란 모델의 각 구성 요소를 하나씩 제거하면서 성능 변화를 측정하여, 어떤 요소가 얼마나 기여하는지 확인하는 실험 방법이다. 여기서는 5개 시그널을 하나씩 빼면서 Hit@3 변화를 측정했다.

| 구성               | Hit@3 | 변화       | 해석                |
| ------------------ | ----- | ---------- | ------------------- |
| Full (T+F+R+S+P)   | 11.7% | (기준)     |                     |
| **-T** (시간 제거) | 9.1%  | **-2.6%p** | T는 가장 큰 기여    |
| -F (빈도 제거)     | 11.7% | ±0.0%p     | F는 T+P에 이미 포함 |
| **-R** (최근 제거) | 12.9% | **+1.1%p** | R은 오히려 해로움   |
| -S (전이 제거)     | 10.9% | -0.9%p     | S는 유효            |
| -P (선호 제거)     | 10.6% | -1.1%p     | P는 유효            |

**핵심 발견**: R(최근성)은 이 도메인에서 해롭다. 환자는 같은 말을 반복하지 않고 다음 단계의 말을 하기 때문이다.

---

### 2.4 Cold Start 분석

- **초기 10건만으로도 16% Hit@3** 가능 → P(보호자 설문)가 초기를 지탱
- 데이터 100건(약 3일) 이후 안정적으로 높은 성능 도달

### 2.5 P(보호자 설문) 시그널에 대한 고찰

평가 결과를 돌아보면, 세션 시작 시 가중치의 55%를 P가 차지하고 있고, Cold Start에서 첫날부터 16% Hit@3을 달성할 수 있었던 것도 P 덕분이었다. 이를 통해 **첫 질문의 적중률을 높이기 위해서는 보호자 설문을 어떻게 받느냐가 핵심 포인트 중 하나**가 아닐까 생각하게 되었다.

**프로토타입에서의 P 구현 방식:**

현재 프로토타입에서는 보호자 설문이 실제 설문 형태가 아니라, 페르소나 설정에 맞춰 **150개 표현 각각에 개발자가 직접 가중치를 하드코딩**한 형태이다 (예: "죽 주세요"=10.0, "밥 주세요"=3.0). 가중치가 지정되지 않은 표현은 기본값 0.5로 처리된다.

**왜 하드코딩일 수밖에 없었는가:**

P는 T, F, S와 성격이 다르다고 느꼈다. T, F, S는 사용 로그가 쌓이면 자동으로 통계가 만들어지지만, P는 "이 환자는 죽을 주로 먹는다"같은 **실제 보호자의 외부 입력**이 있어야 한다. 개발 중에는 실제 보호자가 없으므로, 페르소나 설정에 맞춰 개발자가 직접 지정하는 것 외에는 방법이 없다고 판단했다.

**주의할 점 — 프로토타입의 P 성능은 실제 서비스의 상한선일 수 있다:**

여기서 한 가지 유의해야 할 부분이 있다고 생각한다. 현재 하드코딩은 "개발자가 정답을 알고 있는 상태에서 최적의 가중치를 넣은 것"이다. 실제 서비스에서는 보호자가 설문에서 얼마나 정확한 정보를 주느냐에 따라 P 성능이 달라질 것이므로, 프로토타입의 P 시그널 성능은 실제보다 높을 가능성이 있다. 따라서 **보호자 설문을 얼마나 정교하게 설계하느냐**가 실제 서비스에서의 Cold Start 성능을 좌우하지 않을까 생각한다. 이 부분은 반드시 보완이 필요한 영역이라고 본다.

## 3. 우리 프로젝트에의 적용

| 논문 속 구조                              | 우리 프로젝트                                   |
| ----------------------------------------- | ----------------------------------------------- |
| Stage 1: GMF로 20개 후보 생성             | Stage 1: 가중 스코어링 모델로 10~15개 후보 생성 |
| Stage 2: LLM4Rerank(Llama-2-13B)로 리랭킹 | Stage 2: LLM API로 맥락 기반 리랭킹             |
| 폴백 없음                                 | LLM 장애 시 Stage 1 결과로 자동 전환            |

### 검증된 것

1. **5-Signal 모델은 유효하다** — Random 대비 50배, Popular 대비 1.5배 개선
2. **전이(S) 시그널이 가장 강력하다** — 세션 중간 Hit@3 = 19.6%
3. **보호자 설문(P)이 Cold Start를 해결한다** — 첫날부터 16% Hit@3
4. **동적 가중치 전환이 효과적** — 단일 가중치(11.7%) → 동적 전환(15.4%)
5. **R(최근성)은 이 도메인에서 해롭다** — 제거 시 성능 상승

### 미검증 (다음 단계)

1. **Stage 2 (LLM 리랭킹)**: API 속도 제한으로 미완
2. **실제 환자 데이터**: 시뮬레이션과 실제 환자의 행동 차이 검증 필요
3. **통증 모드**: 긴급 상황에서의 별도 추천 로직

## 4. RAG 도입 검토

### 4.1 핵심 개념

**RAG(Retrieval-Augmented Generation)** 란, LLM이 응답을 생성할 때 외부 지식 저장소에서 관련 정보를 **검색(Retrieval)** 하여 프롬프트에 함께 넣어주는 기법이다.

LLM은 학습 시점까지의 지식만 갖고 있으므로, 학습되지 않은 정보(사내 문서, 최신 데이터, 도메인 특화 지식 등)에 대해서는 **환각(Hallucination)** 을 일으키거나 "모른다"고 답한다. RAG는 이 한계를 외부 지식 주입으로 보완한다.

### 4.2 작동 과정

```
사용자 질문
    │
    ▼
┌───────────────────────────┐
│  1. 임베딩 (Embedding)     │
│  질문을 벡터로 변환         │
└─────────────┬─────────────┘
              │
              ▼
┌───────────────────────────┐
│  2. 검색 (Retrieval)       │
│  벡터 DB에서 유사한 문서를  │
│  Top-K개 검색              │
└─────────────┬─────────────┘
              │ 관련 문서 K개
              ▼
┌───────────────────────────┐
│  3. 증강 (Augmentation)    │
│  검색된 문서를 프롬프트에   │
│  컨텍스트로 삽입            │
└─────────────┬─────────────┘
              │
              ▼
┌───────────────────────────┐
│  4. 생성 (Generation)      │
│  LLM이 컨텍스트를 참고하여  │
│  답변을 생성                │
└───────────────────────────┘
```

핵심은 **"LLM이 모르는 정보를 검색해서 넣어주면, LLM이 그 정보를 기반으로 더 정확한 답을 생성한다"** 는 것이다.

### 4.3 RAG가 잘 맞는 문제

| 특성                     | 설명                                                        | 예시                                  |
| ------------------------ | ----------------------------------------------------------- | ------------------------------------- |
| **대규모 비정형 지식**   | 수천~수만 건의 문서에서 관련 정보를 찾아야 함               | 사내 위키, 법률 문서, 의료 가이드라인 |
| **지식이 수시로 갱신됨** | LLM을 재학습시키기엔 비용이 크고, 지식이 자주 바뀜          | 최신 뉴스 기반 Q&A, 제품 매뉴얼       |
| **자연어 생성이 필요**   | 단순 검색이 아니라, 검색 결과를 종합하여 문장으로 답해야 함 | 고객 상담 챗봇, 리서치 어시스턴트     |
| **정답이 열린 형태**     | 선택지가 고정되어 있지 않고, 맥락에 따라 답이 달라짐        | "이 계약서의 리스크는?"               |

### 4.4 우리 프로젝트와의 대조

RAG의 작동 과정을 공부하면서, 우리 프로젝트에 적합한지 생각해보았다. 내가 주목한 부분은 **"텍스트 유사도" vs "상황 유사도"** 의 차이다.

RAG의 검색(Retrieval)은 본질적으로 **텍스트 유사도**를 찾는 기술이라고 이해했다. 사용자의 질문과 의미적으로 가까운 텍스트 조각을 벡터 공간에서 검색하는 것이다. 즉, **"이 질문과 비슷한 말이 어디에 적혀 있는가?"** 를 푸는 것이라고 볼 수 있다.

반면, 우리 프로젝트가 풀어야 하는 문제는 **상황 유사도**에 더 가깝다고 생각한다. **"지금 이 환자의 상황과 비슷한 과거 상황에서, 환자가 어떤 표현을 선택했는가?"** 를 예측해야 하기 때문이다. 여기서 '상황'이란 시간대, 직전에 한 말, 환자의 컨디션, 일과 루틴 등 **비텍스트적 맥락 신호의 조합**을 의미한다.

| 비교 항목       | RAG                                       | 우리 프로젝트                                       |
| --------------- | ----------------------------------------- | --------------------------------------------------- |
| **찾는 유사도** | 텍스트 유사도 (질문 ↔ 문서의 의미적 거리) | **상황 유사도** (현재 맥락 ↔ 과거 맥락의 패턴 일치) |
| **입력**        | 사용자의 자연어 질문                      | 환자의 현재 상황 (시간, 직전 표현, 루틴 등)         |
| **검색 기준**   | "이 질문과 의미가 비슷한 텍스트는?"       | "이 상황과 비슷한 과거에 환자가 선택한 표현은?"     |
| **유사도 계산** | 텍스트 임베딩 간 코사인 유사도            | 시간대·전이 패턴·선호도 등 복합 신호의 가중 합산    |
| **LLM의 역할**  | 검색된 텍스트를 종합하여 답변을 **생성**  | 후보 표현들의 순서를 맥락에 맞게 **재정렬**         |

이 차이가 왜 중요하다고 느꼈냐면, 예를 들어 RAG의 벡터 검색은 "물 주세요"와 "음료 부탁합니다"가 의미적으로 가깝다는 것은 찾을 수 있다. 하지만 우리가 알아야 하는 것은 "아침 7시에 기상 직후, 직전에 '세수하고 싶어요'를 선택한 환자가 다음에 '물 주세요'를 선택할 확률이 높다"는 **상황적 패턴**이다. 이건 텍스트 간 의미 거리가 아니라, **행동 데이터의 통계적 패턴**에서 나오는 정보이기 때문에, RAG의 검색 메커니즘으로는 포착하기 어렵지 않을까 하는 것이 내 생각이다.

### 4.5 그렇다면 임베딩 벡터에 맥락 유사도를 저장하면 되지 않을까?

여기서 의문이 들었다. RAG가 텍스트 유사도를 기반으로 검색한다면, **임베딩 자체를 맥락 유사도로 저장하면 되지 않을까?** 즉, 텍스트가 아니라 환자의 상황 패턴을 벡터로 만들어서 검색하면 RAG를 활용할 수 있지 않을까 하는 생각이었다.

조사해본 결과, 기술적으로 불가능한 것은 아니지만 실질적으로 의미가 없다는 결론을 얻었다.

**텍스트 임베딩이 바로 작동하는 이유:**
텍스트 임베딩 모델(예: sentence-transformers)은 인터넷의 수십억 개 문장으로 이미 사전 학습되어 있다. "물 주세요"와 "음료 부탁합니다"가 가깝다는 것은 **범용 지식**으로 바로 알 수 있다. 별도 데이터 수집 없이, 텍스트를 넣기만 하면 유사도가 나온다.

**맥락 임베딩이 바로 작동할 수 없는 이유:**
"아침 7시 + 기상 직후 + 직전에 '세수하고 싶어요' 선택"이라는 상황을 벡터로 만든다고 치자. 이 벡터가 "물 주세요"와 가깝다는 걸 모델이 어떻게 알 수 있을까? 범용 모델은 이걸 알 수 없다. 이건 **이 환자 개인의 행동 패턴**이지, 언어의 보편적 의미 관계가 아니기 때문이다. 이 관계를 알려면 해당 환자의 사용 로그 데이터가 충분히 쌓여야 하고, 그 데이터로 패턴을 학습시켜야 한다.

|                   | 텍스트 임베딩             | 맥락 임베딩             |
| ----------------- | ------------------------- | ----------------------- |
| **사전 학습**     | 범용 모델이 이미 존재     | 환자별로 직접 학습 필요 |
| **필요 데이터**   | 없음 (텍스트만 넣으면 됨) | 해당 환자의 사용 로그   |
| **유사도의 근거** | 언어의 보편적 의미 관계   | 개인의 행동 패턴        |
| **만들면 결국**   | RAG의 검색 단계           | 추천 모델 그 자체       |

결국, 맥락 임베딩을 만들겠다고 하면 **환자별 데이터를 모아서 모델을 직접 학습시키는 과정**이 반드시 필요한데, 그게 바로 추천 모델이 하는 일과 같다고 볼 수 있다. RAG의 장점인 "사전 학습된 범용 모델을 그대로 활용"하는 이점을 잃게 되고, 어차피 추천 모델을 만드는 것과 동일한 작업을 하게 되는 셈이라고 이해했다.

### 4.6 정리

위의 검토를 종합해보면, RAG는 **"LLM이 모르는 대규모 텍스트 지식을 검색하여 자연어 답변을 생성"** 하는 문제에 최적화된 기법이라고 생각한다. 우리 프로젝트는 텍스트 지식의 검색보다는 **환자의 상황적 맥락에서 행동 패턴을 예측하는 것**이 핵심이기 때문에, RAG의 강점이 잘 발휘되기 어려운 구조라고 판단했다.

따라서 현재 검토 중인 **2단계 아키텍처(스코어링 → LLM 리랭킹)** 가 우리 문제 구조에 더 적합하지 않을까 생각한다. Stage 2에서 LLM을 활용하되, LLM의 역할은 "지식 검색 + 생성"이 아니라 **"후보 간 맥락적 재정렬"** 에 한정하는 방식이다. 이는 RAG와는 근본적으로 다른 LLM 활용 방식이라고 볼 수 있다.
