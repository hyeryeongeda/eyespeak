### Problem — 문제가 된 것

- **하나를 파고들면 완벽하게 풀 때까지 놓지 못하는 경향.** 나를 포함해 팀원 여럿이 이런 성향이 있는데, 개발자라는 직업에서 가장 중요한 소양 중 하나가 마감 기간을 지키는 것이다. 완벽하게 파고드는 것이 나쁜 건 아니지만, 그로 인해 데드라인을 놓치면 전체 일정이 밀린다. 항상 업무에는 마감기한을 정해두고, 그 안에서 최선을 다하는 방식으로 진행해야 한다는 것을 다시 한번 느꼈다.
- **추천 로직을 고민하다가 UI/UX 영역까지 깊이 들어간 것.** 우리 프로젝트가 루게릭 환자분들을 위한 프로젝트이다 보니, 일반 유저에 비해 UI/UX가 제한되는 부분이 있다. 이 상황에서 추천 로직을 고민하다 보니, 자연스럽게 "이 데이터를 화면에서 어떻게 보여줘야 하지?"라는 UI/UX 고민까지 깊게 해버린 것 같다. 물론 백엔드에서도 이런 부분을 고려하면 좋지만, 이로 인해 마감 기한이 미뤄지고, 프론트엔드 팀원들의 역할을 침범한 건 아닌가 반성하게 되었다.

## 금일 학습한 것

### 1. 설계 프로세스 순서 — 기능 명세서를 건너뛰면 안 되는 이유

보호자 모드/환자 모드의 기능 명세서를 작성하기에 앞서, 설계 문서를 어떤 순서로 작성해야 하는지부터 고민이 생겼다. 처음에 내가 생각한 선택지는 세 가지였다.

```
A: 요구사항 명세서 → ERD → API 명세서
B: 요구사항 명세서 → 기능 명세서 → ERD → API 명세서
C: 요구사항 명세서 → 명사/동사 추출 → ERD → 기능 명세서 → API 명세서
```

A안이 가장 빠르고 간결해 보였는데, 실제로 검토해보니 문제가 있었다. 예를 들어 요구사항에 "사용자가 상품을 주문할 수 있다"라고만 적혀있다면, 이것만 보고 ERD를 그릴 때 다음과 같은 질문에 답할 수 없었다.

```
- 주문 취소는 가능한가? 부분 취소는?
- 장바구니가 필요한가?
- 쿠폰 적용이 있는가?
```

이런 질문들이 해결되지 않은 상태에서 ERD를 그리면, 나중에 "아, 이 기능도 필요했구나"라는 순간이 오고, ERD 수정 → API 수정 → 연쇄 재작업이 발생한다는 것을 이해했다.

C안도 검토해봤는데, 명사/동사 추출로 ERD를 먼저 그린 뒤에 기능 명세서를 쓰는 방식은 순서가 뒤바뀌어 있다는 것을 깨달았다. ERD는 "어떤 데이터를 저장해야 하는가"인데, 이걸 알려면 "어떤 기능이 있는가"가 먼저 확정되어야 한다.

결국 B안이 맞다는 결론을 내렸다.

```
요구사항 명세서 → 기능 명세서 → ERD → API 명세서
```

기능 명세서가 ERD와 API 사이의 다리 역할을 한다는 것을 배웠다. 요구사항은 "무엇을 할 수 있는가"를 정의하고, 기능 명세서는 "어떻게 동작하는가"를 구체화한다. 이 구체화가 끝나야 ERD에서 테이블을 빠짐없이 도출할 수 있고, API에서 요청/응답 필드를 정확히 설계할 수 있다.

실제로 보호자 모드 기능 명세서를 하나씩 작성해보니, 요구사항 단계에서는 보이지 않았던 세부 결정사항들(활동 태그 구성, 입력 방식, 데이터 필드 등)이 대량으로 나왔다. 이걸 기능 명세서에서 확정하지 않고 ERD로 넘어갔다면, 상당한 재작업이 불가피했을 것이라고 느꼈다.

### 2. 복합 PK vs 대리키 — 실무에서는 대리키가 기본값인 이유

ERD를 공부하면서 중간 테이블(연결 테이블)의 PK 전략을 고민하게 되었다. 복합 PK(두 FK의 조합)와 대리키(auto increment id) 중 어떤 것을 써야 하는지가 처음에는 명확하지 않았다.

복합 PK가 간결해 보여서 처음에는 이쪽이 나을 것 같았지만, 실제로 테이블이 확장되는 상황을 시뮬레이션해보니 문제가 드러났다.

```
예: 수강(학생ID + 과목ID) 테이블에 과제 테이블이 연결되면
→ 과제 테이블의 FK도 학생ID + 과목ID (복합 FK)
→ 과제에 첨부파일 테이블이 연결되면 또 전파
→ 테이블이 늘어날수록 복합 FK가 계속 퍼져나감
```

대리키를 쓰면 FK는 항상 id 하나로 끝나므로, JOIN 쿼리도 단순해지고, REST API 설계에서도 `/enrollments/42`처럼 자연스러운 경로가 가능했다. JPA/ORM에서도 복합키는 별도 클래스와 equals/hashCode 구현이 필요한 반면, 대리키는 `@Id @GeneratedValue` 한 줄이면 충분하다는 것을 알게 되었다.

설계 초기에는 "이 중간 테이블을 나중에 참조할 일이 있을까?"를 예측하기 어렵고, 요구사항이 추가되면서 참조가 생기기 마련이라는 점에서, 처음부터 대리키로 설계하는 것이 안전하다고 판단했다. 복합 PK에서 대리키로의 마이그레이션은 FK가 걸린 모든 테이블을 수정해야 하므로 비용이 크기 때문이다.

### 3. 자유 입력 vs 선택형 설계 — 유저 자율 input의 리스크

보호자 모드의 환자 루틴 관리 기능을 설계할 때, 각 시간대 슬롯에 활동 태그(선택형) 외에 메모(자유 입력)를 추가할지 고민했다. 보호자가 "오전에 재활치료사 방문"처럼 자유롭게 적으면 더 풍부한 정보가 될 것 같았다.

하지만 이 루틴 데이터는 환자 표현 추천 로직의 input으로 사용될 예정이었다. 여기서 문제가 생겼다.

```
선택형 input:
  [경관식/수분섭취] [체위변경] → 바로 추천 로직에 매핑 가능

자유 입력 input:
  "오전에 재활치료사 방문" → 어떤 카테고리? 파싱 필요
  "물리치료 선생님 오심" → 같은 의미인데 다른 표현. 또 파싱 필요
```

자유 입력을 추천 로직에 연결하려면 매번 텍스트를 파싱하여 카테고리를 판별해야 하는데, 이 과정에서 부정확한 결과가 나올 수 있고, LLM을 항상 경유시켜야 하는 비용도 발생한다. 무엇보다, 잘못 파싱되면 환자에게 엉뚱한 표현이 추천될 수 있다는 점이 가장 큰 리스크였다.

결국 메모 필드를 제거하고, 활동 태그 선택만으로 구성하기로 결정했다. 유저에게 자유도를 주는 것이 항상 좋은 설계가 아니라는 것을 배웠다. 특히 그 input이 시스템의 다른 로직에 연결될 때는, **input을 고정시켜서 예측 가능한 데이터를 확보하는 것이 더 안전하고 정확한 설계**라는 것을 느꼈다.

이 관점은 루틴 관리뿐 아니라, 자주 쓰는 표현 관리에서도 동일하게 적용되었다. 보호자가 직접 표현을 타이핑하는 대신, 프로그램이 제시하는 목록에서 선택하도록 한 것도 같은 이유였다.

### 4. 웹 푸시(Web Push) 기술 — 알림 시스템의 구조 이해

보호자 모드의 호출 수신(GUARDIAN_005)과 SOS 알람 수신(GUARDIAN_006) 기능을 설계하면서, 웹 푸시 기술을 처음 공부하게 되었다. 처음에는 "서버에서 브라우저로 알림을 보내는 것"이라는 정도만 알고 있었는데, 실제 구조를 파악해보니 4가지 등장인물이 관여한다는 것을 알게 되었다.

```
우리 서버 → 푸시 서비스(구글 FCM 등) → 보호자 브라우저 → Service Worker
```

우리 서버가 보호자 브라우저에 직접 연결하는 것이 아니라, 푸시 서비스라는 중간 서버를 거쳐서 전달되는 구조였다. 택배에 비유하면 우리 서버가 보내는 사람, 푸시 서비스가 택배 회사, 브라우저가 받는 집, Service Worker가 택배를 기다리는 사람이라고 이해했다.

공부하면서 가장 헷갈렸던 부분은 **키와 구독 정보가 섞여서 이해된 것**이었다. 정리해보니 세 가지를 명확히 구분해야 했다.

| 구분 | 개수 | 저장 위치 | 역할 |
|------|------|----------|------|
| 서버 인증용 키 | 서비스에 1개 | 서버 환경변수 | "이 알림은 우리 서버가 보낸 것" 증명 |
| 메시지 보호용 키 | 보호자마다 1개 | DB (구독 정보에 포함) | 중간 전달자(푸시 서비스)가 내용을 못 보게 보호 |
| 구독 정보 (주소) | 보호자마다 1개 | DB | "이 브라우저로 보내줘" 배송 주소 |

서버 인증용 키는 우리 서비스 전체에서 딱 1개이고 .env나 application.yml에 고정값으로 저장하는 반면, 구독 정보(주소)와 메시지 보호용 키는 보호자가 알림을 허용할 때마다 생성되어 DB에 저장된다는 차이를 이해하는 데 시간이 걸렸다.

일반 호출과 SOS 호출의 구분도 고민했는데, 서버 인증용 키를 따로 만들 필요 없이 메시지의 type 필드 값만 다르게 보내고, 프론트엔드의 Service Worker가 type을 보고 알림 소리와 화면 표시를 다르게 처리하면 된다는 것을 알게 되었다. 참고로 type이라는 필드명은 관례일 뿐 강제가 아니어서, 팀에서 합의한 이름이면 무엇이든 상관없다고 한다.

### 5. application.yml — Spring Boot의 설정 파일

프론트엔드에서 .env 파일에 환경변수를 저장하듯, Spring Boot에서는 application.yml이 그 역할을 한다는 것을 처음 배웠다.

```
프론트: .env → KEY=VALUE 형식
백엔드: application.yml → key: value 형식 (들여쓰기로 계층 표현)
```

둘 다 "코드 밖에 설정값을 적어두고, 코드에서 꺼내 쓰는 파일"이라는 점에서 목적은 동일하다. 차이점은 프론트의 .env는 빌드 시 코드에 포함되어 브라우저에서 볼 수 있지만, 백엔드의 application.yml은 서버 내부에서만 접근 가능하다는 것이다. 그래서 비밀키 같은 민감 정보는 반드시 백엔드에만 두어야 한다.

민감 정보의 깃 관리도 배웠다. application.yml 자체를 .gitignore하는 방법과, 일반 설정은 올리고 민감 정보만 application-secret.yml로 분리하여 .gitignore하는 방법이 있다. Spring Boot는 .env처럼 파일명이 고정이 아니라, `application-{이름}.yml` 형식으로 자유롭게 분리할 수 있고, `profiles.include`로 어떤 파일을 함께 읽을지 지정하는 구조라는 것도 알게 되었다.

### 6. 설정 변경의 반영 시점 — 즉시 반영의 위험성

보호자 모드의 입력 잠금 시간 설정(GUARDIAN_007) 기능을 설계하면서, "변경 즉시 환자 모드에 반영"이라고 적었다가 문제를 발견했다.

```
상황: 환자가 시선으로 선택지를 읽고 있는 중에
     보호자가 입력 잠금 시간을 1.0초 → 0초로 변경

→ 갑자기 잠금이 풀리면서 의도치 않은 선택 발생
→ SOS가 잘못 눌릴 수도 있음
```

이 문제는 입력 잠금 시간만이 아니라, 보호자가 수정 가능한 대부분의 설정에 해당했다. 즐겨찾기 표현이 즉시 바뀌면 선택하려던 표현이 사라질 수 있고, 여가 콘텐츠 목록이 즉시 바뀌면 보고 있던 목록이 바뀔 수 있었다.

해결 방법으로 세 가지를 검토했다.

| 방식 | 설명 |
|------|------|
| 즉시 반영 | 가장 위험. 사용 중 오작동 가능 |
| 다음 화면 전환 시 반영 | 현재 화면은 안전하지만 구현이 약간 복잡 |
| 환자 모드 재시작 시 반영 | 가장 안전하고 구현도 가장 단순 |

결국 환자 모드 재시작 시 반영하는 방식을 선택했다. 시작할 때 설정을 한 번 불러오면 끝이므로 구현이 단순하고, 사용 중 변경으로 인한 문제가 원천 차단된다. 보호자가 설정을 바꾸는 시점은 대부분 환자 옆에 있을 때이므로, "설정 바꿨으니 다시 시작할게"라고 안내하면 충분하다고 판단했다.

또한 이 로직은 보호자 모드가 아니라 환자 모드에서 다루는 것이 맞다는 것도 정리했다. 보호자 모드는 설정값을 DB에 저장할 뿐이고, "언제 반영할 것인가"는 환자 모드가 DB에서 값을 읽어오는 시점의 문제이기 때문이다.
