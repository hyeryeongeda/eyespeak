### 1. AI 비전 모델 학습 파이프라인과 핵심 개념 (YOLO 모델 등)

**1) 데이터와 하이퍼파라미터의 이해**

- **데이터 분류 및 편향 유의**: 순수 이미지 데이터인 '원천 데이터'와 라벨링된 정답 파일(XML, TXT 등)인 '라벨링 데이터'의 역할을 명확히 구분했다. 모델 모델의 지식을 쌓는데 쓰이는 `Train`(12,000장 등)과 학습이 옳은 방향으로 가고 있는지 검증하는 `Validation`(전체의 10~20%) 데이터로 엄격히 나누어 진행해야 한다. 이때, 데이터를 단순히 앞에서부터 자르는 것이 아니라 **랜덤 셔플(Random Shuffle)**을 통해 피험자나 환경 편향(Bias) 현상을 철저히 방지하는 것이 매우 중요하다.
- **학습 하이퍼파라미터 (Hyperparameters)**:
  - `에포크(Epoch)`: 전체 학습 데이터를 처음부터 끝까지 다 도는 횟수.
  - `배치 사이즈(Batch Size)`: 모델이 한 번에 GPU를 통해 연산하는 묶음 단위이다. 병목을 막고 병렬 처리를 극대화하기 위해 VRAM 한계치가 허락하는 선까지 최대한 높이는 것이 좋다.
  - `이터레이션(Iteration)`: 설정한 배치 사이즈로 데이터를 나누었을 때, 1개의 에포크를 채우기 위한 1회 연산의 반복 횟수이다.
  - `조기 종료(Early Stopping/Patience)`: 모델 훈련 시 특정 기준(예: 10 에포크) 동안 Validation 기반 평가 점수의 향상이 없을 때, 무의미한 암기식 훈련(과대적합)을 막기 위해 스스로 학습을 멈추도록 강제하는 트리거 필수 수단이다.

**2) 시스템 및 전체 학습 생명주기 (Data Preprocessing -> Train -> Evaluate)**

- **독립된 환경 관리 필수**: 프로젝트 간 충돌 방지를 위해 Conda와 같은 가상환경을 사용하여 각기 다른 파이썬/PyTorch 의존성 트리를 독립적으로 가져가야 한다. 또한 코드를 실행하는 커널(프로세스) 메모리인 VRAM(GPU)의 한계를 고려해 Out of Memory(OOM)가 나지 않도록 데이터 압축과 관리가 이루어져야 한다.
- **학습 A to Z 프로세스**:
  - **전처리(Preprocessing)**: 기존 연구 목적의 XML 좌표를 YOLO 연산에 적합한 좌표 형태(`txt`)로 변환한다. 1024px과 같이 고해상도인 원본을 모델 입력 사이즈 크기인 640px 대역으로 축소(Resize)하며, 21만 장 전체가 아닌 **데이터 다이어트**를 거쳐 효율이 높은 핵심 샘플만 집중 추출해 학습 수렴 시간을 효과적으로 단축한다.
  - **설정 및 전략**: 성능과 속도 요건 사이의 타협(Trade-off) 전략으로, 요구 사항에 맞춰 아키텍처(YOLO Nano의 빠른 수렴성 vs Medium의 견고한 정확도)를 전략적으로 선택한다.
  - **훈련 및 검증 (Train & Inference)**: 실시간 모니터링 툴(MLflow 등)로 Loss 곡선(오차 감소)과 mAP율(정확도 상승 곡선)을 모니터링해야 한다. 훈련이 성공적으로 종료되면, 수치상 최적의 성과를 달성한 가중치 포인트인 `best.pt`를 파일화하여 최종 모델로 추출해낸다.

### 2. 데이터베이스 심화: 조인부터 무결성과 트랜잭션, 최적화까지

**1) 테이블 분리와 고도화된 조합 패턴 (JOIN 및 서브쿼리, UNION)**

- **내부/외부 조인(JOIN)**: 정규화의 산물로 나뉘어진 `users`, `orders`, `products` 테이블들을 실무 목적에 맞춰 의미 있게 이어붙이는 핵심 기술. 양쪽에 키가 있는 교집합만을 구하는 `INNER JOIN`부터, "한 번도 주문한 적 없는 유령 상품" 등을 도출하기 위해 기준 테이블 데이터를 우선 보존하고 없는 값은 `NULL` 처리하는 `LEFT OUTER JOIN`의 사용이 실무 쿼리의 근간이다. 부모-자식 계층이 있는 테이블(사원과 매니저 관계 등) 조회 시 적용하는 셀프 조인(Self Join) 기법도 학습했다.
- **UNION vs UNION ALL**: 수평 확장이 조인이라면 검색 결과를 수직으로 계속 이어붙이는 기술은 UNION이다. `UNION`은 중복 처리 로직으로 백그라운드에서 전체 정렬 절차를 강제하므로 성능 측면에서 매우 느려진다. 따라서 압도적인 퍼포먼스를 위해서는 웬만한 경우라면 중첩을 허용하는 `UNION ALL`을 우선 고려하는 것이 실무 1원칙이다.
- **서브쿼리 유의사항**: 쿼리 안에 쿼리를 넣는 스칼라 값, 다중 컬럼 서브쿼리 등 논리 구조를 캡슐화시킬 수 있지만, 반복 실행에 의한 성능 오버헤드가 단점이다. `IN`, `EXISTS` 등의 올바른 활용 시점을 정리했다.

**2) 데이터의 동적 분류 및 재사용성 (CASE와 VIEW)**

- **CASE 구문**: 프로그래밍의 IF-THEN-ELSE 처럼 쿼리 단에서 데이터를 가공 처리하고 판단하여 분기하는 기능이다. 특히 실무에서는 `SUM()`, `COUNT()` 같은 집계 함수 내부에 CASE문을 삽입하는 '조건부 집계 기술'을 통하여 엑셀과 같은 복잡한 카테고리별/상태별 피벗 리포트 테이블을 쿼리 단 한 번의 실행으로 만들어내는 효율성을 발휘한다.
- **뷰(VIEW)**: 복잡하게 얽힌 JOIN과 서브쿼리를 하나의 단일 포맷으로 네이밍해 캡슐화시키는 가상의 테이블. 디스크에 본 데이터를 중복 저장하지 않고 내부 셀렉트 로직만을 보유한 채로 호출 때마다 수행(최신 데이터 유지율 100%)된다. 비전문 직군 사용자에게 필요한 요약 뷰만 노출시켜 민감 데이터를 가리는 보안성과 쿼리 재사용성을 극대화한다. 삽입/갱신 제약이 많으므로 기본적으로 읽기 전용으로 대우한다.

**3) 데이터 탐색 최적화의 꽃: 인덱스 (INDEX) 원리와 함정**

- **B-Tree의 O(log n) 위력**: 전체 데이터를 비효율적으로 뒤지는 풀 스캔(Full Table Scan) 체제를 방지하기 위해 생성하는 책갈피(색인). 이진 탐색 기법을 이용해 데이터가 1억 건이 넘어가더라도 20~30회의 이내의 탐색 횟수로 점프가 가능한 것이 인덱스가 빠른 이유이다.
- **옵티마이저와 EXPLAIN**: 쿼리 앞에 `EXPLAIN`문을 붙여 실행 계획을 검토. `type: ALL`(풀스캔 위험), `ref/range`(인덱스 사용 중), `Extra: Using filesort`(비효율적 추가 정렬 발생 중) 등을 통해 현재 내 쿼리가 인덱스를 올바르게 타는지 진단할 수 있다.
- **복합 인덱스 디자인 (3대 원칙)**: 여러 종류의 컬럼을 엮어 다중 인덱스를 구축할 경우 기억해야 할 3원칙이 있다. 1) 반드시 정의된 좌측 접두어 순서대로(예: 카테고리 먼저, 그다음 가격) 조건을 물고 갈 것. 2) WHERE 구문 내에서 부등성 등 범위 조회 구문(`<, >`)이 걸린 필드 뒤로 배치된 필드는 인덱스 스캔을 무용지물화시키므로 범위 비교 구문은 항상 끝으로 배치할 것. 3) 정렬 속도 개선의 수혜를 보려면 ORDER BY 정렬 구문 역시 인덱스 순서와 동일하게 세팅할 것.
- 원본 테이블 조회 없이 즉각 결과를 리턴하는 궁극기인 **커버링 인덱스(Covering Index)**의 활용 전략 팁을 배웠다. 카디널리티(고유값 식별력)가 너무 낮은 데이터에 거는 것은 피해야 하며, 인덱스가 많을수록 업데이트(수정/삭제) 로직이 무거워지므로 남용을 금한다.

**4) 무결성과 안정성의 방어 체계 (분산 처리 제약조건과 트랜잭션)**

- **무결성 제약 (Constraints)**: DB는 데이터를 지키는 견고한 최후의 보루다. 필수 요건인 `NOT NULL`, 회원 아이디 중복을 차단하는 `UNIQUE`, 부모-자식 간(회원-주문) 유령 테이블을 미연에 방어해 참조 무결성을 강제하는 `FOREIGN KEY`, 내부 비즈니스 룰 방어 역할인 `CHECK` 제약선율 등이 있다.
- **트랜잭션(Transaction)과 ACID 원칙**: 쇼핑몰 결제 완료 시 출금 조치와 재고 차감이 같이 성공하거나 같이 실패 원복되어야 하듯("All or Nothing"), 트랜잭션은 분리할 수 없는 작업 묶음 구역이다. `START TRANSACTION`으로 개방하고 확정 시 `COMMIT`, 실패/예외 발생 시 원복을 위한 `ROLLBACK` 절차로 시스템 장애를 방어한다.
  - 원자성(Atomicity), 일관성(Consistency), 격리성(Isolation), 지속성(Durability)이라는 필수 4가지 속성을(ACID) 모두 보증해야 한다. 트랜잭션 단위 간 데이터 간섭 현상인 Dirty Read/Phantom Read 방지와 자원 점유 병목성 완화 사이의 트레이드오프를 맞추기 위해, InnoDB 엔진 내에선 `REPEATABLE READ` 격리 레벨을 표준으로 삼고 있다.

**5) 실무에서 자제 권장하는 DB 내장 기술: 스토어드 프로시저/트리거**

- 저장 프로시저(비즈니스 복합 로직을 SQL로 뭉쳐놓은 함수 블럭)와 특정 삭제/업데이트 발생 시점 전후로 자동 발동되는 트리거 함수는 과거부터 전통적으로 많이 쓰였으나 오늘날의 마이크로 아키텍처 환경에서는 철저히 배제하는 추세이다.
- 유지보수의 파편화(에러가 자바 코드 탓인지, DB 탓인지 디버깅의 어려움 증가) 문제와 분산, 확장이 힘든 DB 서버에 고용량 부하를 몰리게 한다는 설계상 큰 오점, 그리고 제조사별 서로 다른 SQL 스크립트 방식이 불러일으키는 벤더 종속(Vendor Lock-in) 문제 때문이다. 모던 웹 백엔드 설계 철학에서는 DB 기능을 오로지 강력한 저장, 복구, 조회(옵티마이저 등), 트랜잭션 정합성 수호 등 본연의 역할에 국한시키고 복잡한 비즈니스 로직은 애플리케이션 프레임워크 층에 전담시키는 것이 정석적인 역할 분리임을 다시금 깨달았다.
