## 1. 자바 예외 계층 구조

### 개념
자바에서 예외는 단순한 오류 메시지가 아니라 **객체(Object)** 로 취급되며, 상속 관계를 가진다.

| 클래스 | 설명 |
|---|---|
| `Throwable` | 모든 예외와 오류의 최상위 부모 |
| `Error` | 복구 불가능한 시스템 예외 (예: 메모리 부족 `OutOfMemoryError`). 직접 잡으려 해서는 안 됨 |
| `Exception` (체크 예외) | 애플리케이션 로직에서 사용하는 최상위 예외. 컴파일러가 체크하며, 반드시 `catch`로 잡거나 `throws`로 던져야 함 |
| `RuntimeException` (언체크/런타임 예외) | 컴파일러가 체크하지 않는 예외. 명시적 선언 없이도 자동으로 전파됨 |

### 🏗️ 비유
> **"병원 응급 분류"** — `Error`는 심폐소생술로도 살릴 수 없는 상태(시스템 종료), `Exception`은 반드시 담당의(개발자)가 처리 방법을 명시해야 하는 환자, `RuntimeException`은 자동으로 다음 의사에게 이송되는 환자.

## 2. 예외 처리의 기본 규칙: 잡거나 던지거나

### 개념
예외가 발생하면 반드시 두 가지 중 하나를 선택해야 한다. 아무 처리도 하지 않고 `main()` 밖으로 나가면 프로그램이 종료된다.

| 방식 | 키워드 | 설명 |
|---|---|---|
| 예외 처리 | `try-catch` | 발생한 예외를 직접 잡아 정상 흐름으로 복구 |
| 예외 던짐 | `throws` | 자신이 처리할 수 없는 예외를 호출한 곳으로 미룸 |

### 핵심 원리: 예외와 다형성
예외도 객체이므로 **다형성**이 적용된다. 부모 타입 예외를 `catch`하면 그 하위 자식 예외들도 함께 처리할 수 있다.

```java
// Exception을 잡으면 그 하위의 모든 예외도 처리됨
try {
    // ... 예외 발생 가능 코드
} catch (Exception e) {
    System.out.println("예외 처리: " + e.getMessage());
}
```

## 3. 예외 처리 방식의 진화

### 1단계: 반환 값(오류 코드) 방식 — 한계

초기에는 `"success"`, `"error1"` 같은 문자열/숫자를 반환해 에러를 확인했다.

**문제점:**
- 비즈니스 로직과 에러 처리 코드가 **뒤섞여** 가독성이 최악
- 외부 자원(네트워크 연결 등) 해제를 **잊기 쉬움**

### 2단계: `try-catch-finally` 도입

정상 로직은 `try`에, 예외 로직은 `catch`에 분리하여 코드 가독성을 확보하였다.

```java
String conn = connect(); // 네트워크 연결
try {
    // 정상 비즈니스 로직
    send(conn, "data");
} catch (Exception e) {
    // 예외 처리 로직
    System.out.println("예외 처리: " + e.getMessage());
} finally {
    // 예외 여부와 무관하게 항상 실행 → 리소스 해제에 사용
    disconnect(conn);
}
```

> **`finally` 블록**: 예외 발생 여부와 상관없이 **무조건 실행**된다. 네트워크 연결 해제처럼 반드시 수행해야 하는 마무리 작업에 사용한다.

### 3단계: `Try-with-resources` (Java 7 이상)

`finally`에서 리소스를 직접 닫는 번거로움을 해결하기 위해 도입되었다.

- `AutoCloseable` 인터페이스를 구현한 리소스를 `try()` 괄호 안에 선언하면, 블록이 끝날 때 **자동으로 `close()`** 가 호출된다.

```java
// NetworkClient가 AutoCloseable을 구현한 경우
try (NetworkClient client = new NetworkClient("https://example.com")) {
    client.connect();
    client.send("data");
    // 블록을 벗어나는 순간 client.close()가 자동 호출됨
} catch (Exception e) {
    System.out.println("예외 처리: " + e.getMessage());
}
```

## 4. 실무에서의 예외 처리 전략

### 체크 예외 → 런타임 예외(언체크) 선호로의 전환

| 구분 | 설명 |
|---|---|
| **체크 예외의 부담** | 시스템이 복잡해질수록 처리할 수 없는 예외가 너무 많아짐. 모든 예외를 `throws`에 명시하는 '예외 처리 지옥' 발생 |
| **런타임 예외 선호** | Spring, JPA 등 현대적 라이브러리는 대부분 런타임 예외 사용. 필요한 것만 잡고 나머지는 알아서 전파됨 |

### 🌱 실제 Spring에서의 활용

- **공통 예외 처리기(Exception Handler)**: 서비스 계층에서 해결 불가능한 시스템 에러(네트워크 불능 등)는 억지로 잡으려 하지 않고, 상단의 공통 예외 처리기에서 한꺼번에 처리한다.
  - 사용자에게는 "문제가 발생했습니다" 메시지 노출
  - 개발자에게는 상세 로그를 기록

```java
// Spring의 공통 예외 처리기 예시
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(Exception.class)
    public ResponseEntity<String> handleException(Exception e) {
        log.error("시스템 예외 발생", e); // 개발자용 로그
        return ResponseEntity.status(500).body("문제가 발생했습니다."); // 사용자용 메시지
    }
}
```
