### 1. AI 서버의 DB 직접 접근 차단 — Single Writer Principle을 근거로 팀원 설득

---

AI 서버(채팅 추천) 담당 팀원에게서 연락이 왔다. AI 서버가 우리 DB에 직접 접근하게 해달라는 요청이었다. 근거는 "오버헤드를 줄이기 위해"라는 것이었고, 이해는 갔지만 보안적으로 불안하다고 느꼈다.

그런데 "불안하다"는 느낌만으로 반대하기는 어려웠다. 팀원도 오버헤드 감소라는 근거를 가지고 제안한 것이니, 나도 뭔가 근거를 찾아봐야 했다. 그래서 두 가지를 조사했다.

첫째, 내부 REST API의 레이턴시. 우리 프로젝트는 BE와 AI 서버가 같은 Docker Compose로 띄워지기 때문에, 동일한 물리 서버 위의 컨테이너끼리 통신하는 구조다. 마이크로서비스 레이턴시 벤치마크 자료들을 찾아보니, 이런 환경에서 REST API 1회 호출은 약 1~3ms, GET + POST 2회를 해도 약 6ms 이하다. AI 추론 자체가 200~2,000ms인 상황에서 6ms는 전체 응답 시간의 0.3~3%에 불과하다. "오버헤드"라고 부르기 어려운 수준이라고 판단했다.

둘째, Single Writer Principle. "특정 데이터의 쓰기 책임은 단일 서비스에 할당해야 한다"는 마이크로서비스 설계 원칙이다. usage_log 같은 테이블에 BE와 AI 서버 둘 다 쓰면, 스키마 변경 시 양쪽 코드를 동시에 수정해야 하고, 장애 추적 시 "이 row는 누가 썼지?"부터 확인해야 한다. Microsoft Azure Architecture Center에서도 "두 서비스가 같은 데이터 저장소를 공유하면 안 된다"고 명시하고 있었다.

결국 팀원에게 "AI 추론이 500ms 걸리는데, 내부 API 6ms를 아끼려고 usage_log 쓰기 주체를 둘로 나누면, 나중에 정합성 맞추는 데 드는 비용이 더 크다"는 논리로 설득했고, REST API 경유 방향으로 합의됐다.

"위험해 보인다"는 느낌에서 출발했지만, 그걸 레이턴시 수치와 설계 원칙으로 뒷받침할 수 있었기 때문에 팀원을 설득할 수 있었다고 생각한다. 느낌만 있었으면 "그냥 불안한데..." 수준에서 끝났을 것 같다.

### 2. 팀원 계획서 검토 — API 4개를 3개로 줄인 판단

---

팀원이 마이그레이션 계획서를 보내왔다. AI 서버의 DB 직접 접근을 제거하기 위해 BE가 만들어야 할 API 4개가 정리되어 있었다. 계획서의 테이블 매핑이나 응답 구조는 정확했지만, 구조적으로 문제가 있는 부분을 발견했다.

4번째 API인 `GET /api/v1/ai/hints/{matchingId}`가 문제였다. 현재 `RecommendationController.getCategories()`는 BE → AI → DB → AI → BE 순서로 hint 데이터를 가져온다. 마이그레이션 후 계획대로 하면 BE → AI → BE → DB → BE → AI → BE가 되어 순환 호출이 발생한다.

AI 서버 코드를 직접 열어봤다. `/recommend/hints` 엔드포인트(913~1000줄)의 로직은 daily_mood 조회, routine JOIN, usage_log GROUP BY COUNT, usage_log ORDER BY DESC — 전부 순수 SQL 조회와 Map 변환이었다. AI/ML 로직이 0%였다.

그래서 이 API를 삭제하고, BE가 `getCategories()` 안에서 직접 DB 조회하도록 변경하는 방향을 제안했다. AI 서버의 `/recommend/hints` 엔드포인트도 삭제 대상으로 잡았다. 결과적으로 BE가 만들 API는 4개에서 3개로 줄었고, 순환 호출 문제도 해결됐다.

계획서만 보면 문제가 없어 보였는데, 기존 코드의 호출 방향까지 따져보니까 순환 호출이 보였다. 계획서의 숫자와 구조가 맞는지만 볼 게 아니라, 데이터가 실제로 어떻게 흐르는지를 같이 봤어야 했다. 안 봤으면 그대로 넘어갈 뻔했다.

### 3. 데이터 정합성 vs FE 변경 최소화 — 키보드 입력 처리 방식 결정

---

마이그레이션 과정에서 가장 골치 아팠던 부분은 키보드 자유입력 처리였다. 기존에는 환자가 키보드로 "배고파"를 입력하면 `POST /usage-logs {content: "배고파"}`로 usage_log에만 저장하고, 채팅은 `contentType=TEXT`로 보냈다. 하지만 팀 합의에 따라 키보드 입력도 expressions 테이블에 들어가야 했다.

처음에는 BE에서 해결하려 했다. ChatService 안에서 `contentType=TEXT`가 들어오면 내부적으로 Expression을 생성하고, Message에 연결하고, contentType을 EXPRESSION으로 바꿔서 저장하는 방식이었다. FE 변경이 전혀 필요 없어 보여서 매력적이었다.

하지만 곰곰이 따져보니 문제가 있었다. FE는 TEXT로 보냈는데 DB에 EXPRESSION으로 저장되면, WebSocket 응답에도 `contentType=EXPRESSION`이 내려간다. FE가 TEXT와 EXPRESSION을 다르게 렌더링할 경우 UI가 깨질 수 있다. 그리고 "FE가 보낸 것과 DB에 저장된 것이 다르다"는 것 자체가 데이터 정합성 문제라고 봤다.

결국 FE에 수정을 요청하는 방향을 택했다. 키보드 입력 시 `POST /recommendations/record {text}` → expressionId 받음 → `contentType=EXPRESSION, expressionId=N`으로 채팅 전송. FE 입장에서는 저장 API 호출 대상과 contentType 두 가지만 바꾸면 된다.

당장은 BE에서 내부 처리하는 게 편하지만, FE가 TEXT로 보냈는데 DB에 EXPRESSION으로 저장되면 나중에 분명 버그가 생길 것 같았다. 지금 편한 것보다 나중에 안 깨지는 쪽을 택했다.

### 4. AI 서버 코드 수정 최소화를 위한 API 설계 — user-context API 존치 판단

---

3번의 연장선에서, 또 하나의 설계 결정이 있었다. `GET /ai/user-context/{matchingId}` API가 정말 필요한가? BE가 AI 서버를 호출할 때 request body에 user context 데이터를 같이 넣어주면, AI 서버가 다시 BE를 호출할 필요가 없지 않은가?

이 방식이 아키텍처적으로는 더 깔끔하다. "호출자가 데이터를 제공한다"는 원칙에 맞고, AI → BE 역방향 호출이 사라진다. 하지만 현실적인 문제가 있었다. AI 서버의 `_load_user_data_from_db()` 함수가 추천 로직 곳곳에서 호출되고 있었다. body에 데이터를 넣는 방식으로 바꾸려면 AI 서버의 모든 엔드포인트가 request 구조를 변경해야 한다.

반면 API를 유지하면, AI 서버는 `pymysql` 호출 한 줄을 `requests.get()` 한 줄로 바꾸면 끝이다. 내부 구조는 그대로 유지된다.

구조적으로 가장 깔끔한 방법은 알고 있었지만, 그렇게 하면 팀원의 AI 서버 코드를 전부 뜯어고쳐야 했다. pymysql 한 줄을 requests.get 한 줄로 바꾸는 것과, 모든 엔드포인트의 request 구조를 바꾸는 것은 작업량 차이가 크다. 일정을 생각하면 이쪽이 현실적이라고 봤다.
