### 1. 에러코드 설계 — 포괄적 에러코드 vs 구체적 에러코드

---

채팅 메시지 전송 검증 로직을 만들면서, 에러코드를 어떤 단위로 나눌지 고민했다. 처음 AI가 제안한 구조에서는 `CHAT_SEND_FAILED` 하나로 모든 전송 실패를 묶었다. 내용이 비어있든, 메시지 타입이 잘못됐든, 문구 ID가 빠졌든 전부 같은 코드였다.

그대로 쓰기엔 아쉬웠다. 이전 프로젝트에서 프론트엔드를 담당했을 때, 포괄적인 에러코드를 받으면 클라이언트 쪽에서 할 수 있는 게 거의 없었던 기억이 있다. `CHAT_SEND_FAILED` 하나만 오면 사용자에게 "메시지 전송에 실패했습니다" 이상의 안내를 줄 수가 없고, 디버깅할 때도 결국 서버 로그를 열어봐야 원인을 파악할 수 있다. 에러코드를 줄이는 것이 백엔드 입장에서는 간결해 보이지만, 그 비용이 프론트의 에러 핸들링 복잡도로 전가되는 구조라고 판단했다.

그래서 5개로 분리하는 방향을 선택했다. `CHAT_INVALID_CONTENT_TYPE`(잘못된 메시지 타입), `CHAT_TEXT_EMPTY`(텍스트 비어있음), `CHAT_PHRASE_ID_REQUIRED`(문구 ID 누락), `CHAT_EXPRESSION_ID_REQUIRED`(표현 ID 누락), `CHAT_MATCHING_MISMATCH`(본인 매칭 아닌 채팅 접근). 처음에 접근 권한 에러를 `ACCESS_DENIED`라는 범용 코드로 잡았다가, 이것도 `CHAT_MATCHING_MISMATCH`로 변경했다. 같은 맥락인데, "접근 거부"라는 범용적 표현보다 "매칭 불일치"라는 구체적 원인이 프론트에서 더 활용하기 좋은 정보라고 봤기 때문이다.

돌아보면 이 판단은 어제 TIL에 쓴 Swagger 도입과 같은 뿌리에서 나온 것 같다. 프론트 경험이 백엔드 설계 판단에 영향을 준 셈이다. API 명세 자동화도, 에러코드 세분화도, 결국 "프론트에서 받았을 때 바로 쓸 수 있는가"라는 같은 기준에서 결정한 부분이 있다. 에러코드는 팀 전체의 에러 핸들링 품질에 직결되는 영역이라, 백엔드 쪽의 간결함보다는 팀 전체의 개발 효율을 우선하는 것이 더 합리적이라고 생각했다.

### 2. FCM 전송 실패 시 예외를 전파하지 않는 설계

---

채팅 메시지를 보낼 때, 상대방이 오프라인이면 FCM 푸시 알림을 보내는 구조로 만들었다. 여기서 고민이 생겼다. FCM 전송이 실패하면 예외를 던져야 하는가?

처음에는 실패하면 예외를 던지는 게 자연스럽다고 생각했다. 그런데 전체 흐름을 따져보니 생각이 달라졌다. 메시지 전송 로직은 DB 저장 → WebSocket 전달 또는 FCM 전달 순서로 진행된다. 만약 FCM 단계에서 예외를 던지면 트랜잭션이 롤백되면서, 이미 DB에 저장된 메시지까지 함께 사라지게 된다. 알림 전송이 실패했을 뿐인데 메시지 자체가 유실되는 셈이라, 사용자 입장에서는 보낸 메시지가 어디로 갔는지 알 수 없는 상황이 된다.

그래서 `FcmService.sendPush()` 메서드에서 `FirebaseMessagingException`을 catch하되 다시 던지지 않는 설계를 택했다. FCM 토큰이 없거나 Firebase가 초기화되지 않은 경우에도 `log.warn`만 남기고 `return`한다. 메시지는 DB에 보존되고, 상대방이 다음에 앱을 열면 채팅 목록에서 확인할 수 있다.

```java
try {
    String messageId = FirebaseMessaging.getInstance().send(message);
    log.info("FCM 전송 성공: messageId={}, type={}", messageId, data.get("type"));
} catch (FirebaseMessagingException e) {
    log.error("FCM 전송 실패: token={}, type={}, error={}",
            fcmToken, data.get("type"), e.getMessage());
}
```

물론 한계도 있다. 상대방이 오프라인인데 FCM까지 실패하면 알림이 아예 가지 않게 된다. 현재로서는 앱 재진입 시 미읽은 메시지를 조회하는 것으로 보완하고 있지만, 재전송 큐나 폴링 같은 장치는 고도화 과제로 남아있다. 다만 모든 실패 케이스를 한 번에 해결하려고 하기보다, 지금 단계에서 가장 중요한 것(메시지 보존)을 먼저 확보하는 편이 현실적이라고 판단했다.

### 3. 방어적 코딩의 기준 — "발생 안 하는 상황"에도 로그를 남겨야 하는가

---

WebSocket 이벤트 리스너를 구현하면서, `event.getUser()`가 null인 경우를 처리할지 고민했다. 인증 인터셉터에서 이미 Principal을 설정하기 때문에, 정상 흐름이라면 null이 올 수 없다. 마찬가지로 채팅 서비스에서 보호자가 환자에게 메시지를 보내는데 환자가 오프라인인 상황도, 앱 구조상 환자는 항상 WebSocket에 연결되어 있으므로 이론적으로 발생하지 않는다.

선택지는 세 가지였다. 첫째, 조용히 무시하기. null 체크 없이 진행하면 코드가 깔끔하지만, 만약 발생하면 NPE가 터지고 원인 파악이 어렵다. 둘째, 예외 던지기. 확실하게 막을 수 있지만, 실제로 발생하지 않는 상황에 예외를 던지면 정상 흐름이 불필요하게 중단될 수 있다. 셋째, 경고 로그만 남기기. 정상 흐름은 깨지지 않으면서, 혹시 발생하면 원인을 추적할 수 있다.

경고 로그를 선택했다. WebSocket 이벤트 리스너에서는 Principal이 null이면 `log.warn`을 남기고 `return`하는 식으로 구현했다.

```java
StompPrincipal principal = (StompPrincipal) event.getUser();
if (principal == null) {
    log.warn("WebSocket 연결 이벤트에 Principal이 없습니다. 인증 인터셉터를 확인하세요.");
    return;
}
```

채팅 서비스에서도 환자가 오프라인인 "있을 수 없는" 상황에 `log.warn`을 남겼다.

```java
} else {
    log.warn("환자가 오프라인입니다. recipientUserId={}, matchingId={}",
            recipientUserId, matching.getId());
}
```

이번 경험을 통해 나름의 기준을 정리해봤다. "발생하면 안 되지만, 발생하더라도 정상 흐름을 깨뜨릴 이유가 없는 경우"에는 경고 로그를 남기는 것이 적절하다고 본다. 코드 한 줄 추가하는 비용에 비해, 나중에 디버깅할 때 절약할 수 있는 시간이 크기 때문이다. 특히 WebSocket처럼 비동기적으로 이벤트가 발생하는 환경에서는, "이론적으로 불가능한" 상황이 동기 코드보다 실제로 발생할 가능성이 높다고 느꼈다. 방어적 코딩에서 중요한 것은 "지금 발생하느냐"보다 "발생했을 때 추적할 수 있느냐"가 아닐까 싶다.

### 4. 채팅과 호출의 전송 경로를 다르게 설계한 이유

---

채팅과 호출(일반 호출/SOS)은 둘 다 "상대방에게 무언가를 보내는" 기능이지만, 전송 경로를 완전히 다르게 가져갔다. 처음에는 둘 다 WebSocket STOMP로 통일하는 게 깔끔하지 않을까 싶었는데, 사용 맥락을 따져보니 같은 경로를 쓸 수 없는 이유가 보였다.

채팅은 사용자가 채팅 화면에 들어와 있는 상태에서 발생한다. 이미 WebSocket 연결이 맺어진 상황이므로, STOMP 메시지로 보내는 것이 자연스럽다. 그런데 호출은 다르다. 환자가 메인 화면에서 SOS 버튼을 누르는 상황처럼, 채팅 화면 밖에서도 호출이 가능해야 한다. 이 경우 WebSocket 연결이 반드시 열려 있다고 보장할 수 없기 때문에, 호출은 REST API(`POST /api/calls`)로 설계하는 것이 더 안정적이라고 판단했다. WebSocket에 의존하면 연결 상태에 따라 호출 자체가 실패할 수 있고, 그건 긴급 호출 기능에서는 허용하기 어려운 리스크라고 봤다.

전달 방식도 의도적으로 다르게 가져갔다. 채팅에서는 상대방이 온라인이면 WebSocket으로, 오프라인이면 FCM으로 보내는 택1 구조를 썼다. 반면 호출에서는 FCM을 항상 보내면서, 보호자가 온라인이면 WebSocket도 추가로 보내는 이중 전송 구조로 만들었다. 이렇게 나눈 이유는 두 채널의 역할이 근본적으로 다르기 때문이다. FCM은 Google 서버를 경유하기 때문에 수백ms에서 수초까지 지연이 생길 수 있지만, 디바이스 레벨의 알림(소리, 진동)을 발생시킬 수 있다. WebSocket은 서버-클라이언트 직통이라 거의 즉시 도달하지만, 앱 UI 갱신에만 쓸 수 있다. 채팅은 이미 화면을 보고 있는 상황이니 둘 중 하나면 충분하지만, 호출은 긴급성이 높은 기능이라 "즉시 화면 갱신(WebSocket) + 확실한 디바이스 알림(FCM)"을 모두 확보해야 한다고 판단했다.

결과적으로 채팅과 호출이 같은 인프라(WebSocket, FCM)를 쓰면서도 전송 정책은 정반대로 갈라지게 됐다. 기능의 성격이 다르면 같은 기술을 쓰더라도 조합 방식이 달라져야 한다는 걸 체감한 부분이다. "기술이 같으니 경로도 같아야 한다"는 생각이 오히려 설계를 제약할 수 있다는 점을 배운 것 같다.
