### 1. STOMP Principal 세션 전파 실패 — 1차 수정 실패 후 Spring 소스코드까지 추적한 과정

---

WebSocket 채팅 기능을 로컬에서 테스트하는데, 클라이언트가 메시지를 보내면 아무 응답도 돌아오지 않았다. 메시지가 그냥 사라졌다. 응답도 안 오고, 에러 응답도 안 왔다. 그런데 WebSocket 연결(CONNECT) 자체는 성공한 상태였다.

#### 1.1 원인 추적

메시지 흐름을 처음부터 따라가봤다.

```
클라이언트 SEND /app/chat
  → StompChannelInterceptor.preSend()  ← 여기서 JWT 검증 + "이 사용자가 누구인지(Principal)" 세팅
  → ChatController.sendMessage()       ← 여기서 Principal을 꺼내서 사용
  → ChatService.sendMessage()          ← 여기서 DB 저장 + 응답 발송
```

ChatController에서 Principal을 꺼내는데, 이 값이 null이면 NPE가 터진다. 서버 로그를 보니 실제로 NPE가 발생하고 있었다. 그러면 Interceptor에서 Principal을 세팅하는 부분이 제대로 동작하지 않는 것이다.

Interceptor 코드를 보니 이렇게 되어 있었다:

```java
StompHeaderAccessor accessor = StompHeaderAccessor.wrap(message);
if (StompCommand.CONNECT == accessor.getCommand()) {
    accessor.setUser(new StompPrincipal(userId, role));  // accessor에 사용자 정보 세팅
}
return message;  // 원본 메시지를 그대로 리턴
```

여기서 핵심은 `wrap(message)`의 동작 방식이다. 이 메서드는 원본 메시지의 헤더를 직접 수정할 수 있게 해주는 게 아니라, 헤더의 **복사본**을 가진 새로운 accessor를 만든다. 그러니까 `accessor.setUser()`는 복사본에만 사용자 정보를 세팅한 것이고, `return message`는 사용자 정보가 없는 원본을 돌려주고 있었다.

#### 1.2 1차 수정 — 그리고 재발

원인을 찾았으니 수정은 간단하다고 생각했다. 복사본에 사용자 정보를 세팅했으면, 그 복사본의 헤더로 새 메시지를 만들어서 리턴하면 된다.

```java
accessor.setUser(new StompPrincipal(userId, role));
return MessageBuilder.createMessage(message.getPayload(), accessor.getMessageHeaders());
```

CONNECT가 성공하고, 로그에도 `userId=2, role=GUARDIAN`이 찍혔다. 해결됐다고 생각했다. 그런데 이후 SEND 메시지에서 또 Principal이 null이었다. CONNECT 시점에는 사용자 정보가 붙었는데, 같은 세션의 다음 메시지에는 전파가 안 되고 있었다.

이게 이해가 안 됐다. 연결할 때 사용자 정보를 붙여서 리턴했으면, Spring이 그걸 세션에 저장하고 이후 메시지에도 넣어줘야 하는 거 아닌가?

#### 1.3 Spring 소스코드 추적 — 근본 원인 발견

뭔가 더 깊은 곳에서 놓치고 있는 게 있다는 느낌이 들어서, Spring이 CONNECT 메시지를 어떻게 처리하는지 소스코드를 직접 열어봤다.

Spring은 CONNECT를 처리할 때, 메시지에 붙어있는 **원본 accessor**를 꺼내서 거기에 콜백을 등록한다. 이 콜백의 역할은, 누군가 `setUser()`를 호출하면 세션 관리자에게 "이 유저가 연결됐다"고 알려주는 것이다.

이걸 보는 순간 이해가 됐다. 내가 `wrap()`으로 만든 건 복사본이니까, 이 콜백이 복사본에는 없다. 복사본에서 `setUser()`를 호출해봤자 세션 관리자에게는 아무 신호도 가지 않는다. 그러니까 1차 수정에서 `MessageBuilder`로 새 메시지를 만들어 리턴했을 때, CONNECT 자체는 성공한 것처럼 보였지만 세션에는 사용자 정보가 저장되지 않았던 것이다.

#### 1.4 최종 수정

복사본을 만들지 말고, 원본 accessor를 직접 수정해야 한다. `getAccessor()`는 `wrap()`과 달리 메시지에 이미 붙어있는 원본을 그대로 꺼내준다.

```java
StompHeaderAccessor accessor = MessageHeaderAccessor.getAccessor(message, StompHeaderAccessor.class);
accessor.setUser(new StompPrincipal(userId, role));  // 원본을 직접 수정 → 콜백이 작동 → 세션에 저장됨
return message;
```

이후 CONNECT → SEND → 응답 수신까지 정상 동작을 확인했다.

#### 1.5 연쇄 장애 구조

이 과정에서 하나 더 깨달은 게 있다. Principal이 null이면 단순히 "인증 실패"로 끝나는 게 아니라, 시스템 전체가 무응답 상태에 빠진다.

```
Principal null
  → WebSocketEventListener: 사용자 정보가 없으니 세션 등록 실패 → 모든 유저가 오프라인으로 판정
  → ChatController: Principal을 꺼내려다 NPE
  → StompExceptionHandler: NPE를 잡긴 하지만, "누구에게 에러를 보내야 하는지" 모르니까 에러 응답도 전송 불가
  → 클라이언트: 아무 응답도 없음 — 메시지가 사라진 것처럼 보임
```

에러를 처리하는 ExceptionHandler조차 "이 에러를 누구에게 보내야 하는지" Principal에 의존하고 있어서, Principal이 없으면 에러를 잡아도 전달할 방법이 없었다. 하나의 실패 지점이 시스템 전체를 무응답으로 만드는 구조였다. 이 경험이 바로 아래 2번 항목에서 장애 전파를 더 민감하게 보게 된 계기가 됐다.

### 2. 코드리뷰에서 API 책임 분리 판단 — 편의를 위해 합치자는 구조에 분리 유지를 선택한 것

---

팀원의 MR을 리뷰하는데, `ChatService.sendMessage()` 안에서 메시지 전송뿐만 아니라 로그 기록과 AI 분류까지 한꺼번에 처리하는 구조로 되어 있었다. 팀원의 의도는 이해가 됐다. 클라이언트가 메시지를 보낸 뒤 별도로 로그 API를 호출하지 않아도 되니까, 호출 횟수가 줄어든다는 장점이 있었다.

그런데 기존에 이미 로그 기록 API가 분리되어 있었다.

| API | 책임 |
|---|---|
| `POST /usage-logs` | PHRASE 사용 로그 |
| `POST /recommendations/record` | Expression/키보드 입력 로그 |

여기서 `sendMessage()` 안에 로그 기록을 넣으면 두 가지 문제가 생긴다.

첫째, **이중 기록**이다. 기존 로그 API가 살아있는 상태에서 sendMessage도 로그를 쓰면, 클라이언트가 기존 API도 호출하는 경우 같은 로그가 두 번 쌓인다. 이걸 방지하려면 기존 로그 API를 삭제해야 하는데, 그러면 로그 API를 쓰고 있는 다른 곳까지 전부 바꿔야 한다. 변경 범위가 sendMessage 하나에서 시작해서 프로젝트 전체로 번진다.

둘째, **장애 전파**다. 1번에서 경험한 것처럼 하나의 실패가 연쇄적으로 시스템 전체를 멈출 수 있다. sendMessage가 전송 + 로그 + AI 분류를 전부 담당하면, AI 분류 서버가 응답을 안 줄 때 메시지 전송 자체가 실패한다. 채팅이라는 핵심 기능이 부가 기능(로그/분류) 때문에 깨지는 구조가 되는 셈이다.

결국 "API 호출 횟수를 줄이는 편의"보다 "기존 API와의 충돌 방지 + 장애 격리"가 더 중요하다고 판단해서, 로그 기록은 기존 분리 구조를 유지하는 방향으로 리뷰 의견을 남겼다.

### 3. 코드리뷰에서 데이터 흐름 역추적 — String 파라미터의 출처를 추적해 분류 버그를 발견한 것

---

2번에서 sendMessage()의 책임 범위를 따지면서, 내부 데이터 흐름도 같이 따져봤다. 그 과정에서 메시지 내용(content)을 꺼낸 뒤 그 값을 Expression 기록 서비스에 그대로 넘기는 부분이 눈에 걸렸다.

```
resolveContent(request) → content(String) → recordExpression(matchingId, content)
```

언뜻 보면 문제가 없어 보이지만, `resolveContent()`를 열어보면 contentType에 따라 **완전히 다른 출처**의 content를 반환한다:
- TEXT → 사용자가 키보드로 직접 입력한 텍스트
- PHRASE → 미리 등록된 문구 목록에서 가져온 문구
- EXPRESSION → AI가 분류한 표현 목록에서 가져온 표현

문제는 다음 단계인 `recordExpression()`이다. 이 메서드는 받은 content를 Expression 테이블에서 찾는다. EXPRESSION에서 온 content라면 당연히 찾을 수 있다. 하지만 PHRASE에서 온 content가 들어오면? Expression 테이블에 없으니 "처음 보는 표현"으로 판단하고, AI 분류를 돌려서, PHRASE 문구를 Expression으로 잘못 저장하게 된다.

이 버그가 보인 이유는, `recordExpression()` 메서드만 봐서는 문제를 알 수 없었기 때문이다. 메서드 시그니처는 `recordExpression(Long matchingId, String content)`인데, 이 String이 PHRASE에서 온 건지 EXPRESSION에서 온 건지 타입만 봐서는 구분이 안 된다. `resolveContent()`까지 거슬러 올라가서 "이 content가 실제로 어디서 만들어지는 건지" 따져봐야 비로소 문제가 보였다. 파라미터가 String이나 Long처럼 범용적인 타입일수록, 메서드 단위가 아니라 호출 체인 단위로 읽어야 한다는 걸 느꼈다.
