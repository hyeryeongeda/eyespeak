### 1. ERD 설계의 출발점 — 테이블이 아니라 관계에서 시작해야 한다

ERD를 처음 접하면서 가장 먼저 부딪힌 문제는 "어디서부터 시작해야 하는가"였다. 기능 명세서를 보면서 테이블부터 뽑아내려고 했는데, 생각보다 쉽지 않았다. 테이블 하나를 만들 때마다 "이 데이터는 누구의 것인가", "다른 테이블과 어떻게 연결되는가"라는 질문이 꼬리에 꼬리를 물었기 때문이다.

이 고민 끝에 깨달은 것은, 테이블을 먼저 나열하는 것이 아니라 **엔티티 간의 관계를 먼저 정의해야 한다**는 것이었다. 우리 프로젝트에서는 환자와 보호자가 1:1로 매칭되는 관계가 핵심이다. 이 관계를 Matching이라는 독립 테이블로 승격시킨 것이 설계의 출발점이 되었다.

처음에는 "환자와 보호자가 1:1이면, Patient 테이블에 guardian_id를 FK로 넣으면 되는 거 아닌가?"라고 생각했다. 그런데 이렇게 하면 문제가 생겼다. 즐겨찾기, 루틴, 메시지 등 환자-보호자 쌍에 속하는 모든 데이터가 특정 테이블에 접근하려면, 매번 Patient에서 Guardian으로 JOIN해서 상대방 정보를 가져와야 했다. 관계 자체가 테이블 안에 숨어 있으니, 모든 쿼리가 불필요하게 복잡해지는 것이었다.

Matching 테이블을 만들고 나니, 모든 공유 데이터가 `matching_id` 하나만 참조하면 되는 구조가 되었다.

```sql
-- matching_id 하나로 해당 쌍의 모든 데이터에 접근 가능
SELECT * FROM favorite_phrase WHERE matching_id = 7;
SELECT * FROM message WHERE matching_id = 7;
SELECT * FROM routine_slot_tag WHERE matching_id = 7;
```

Patient나 Guardian을 거치지 않고, matching_id만 알면 해당 쌍의 모든 데이터에 바로 접근할 수 있었다. "관계가 속성을 가질 때, 그 관계를 테이블로 승격시킨다"는 원칙을 이 과정에서 체감하게 되었다. 그리고 결과적으로, 17개 테이블 전부가 이 matching_id를 중심으로 연결되는 구조가 되었다. 하나의 설계 결정이 전체 구조를 관통한다는 것이 이렇게 강력한 것인지 처음 느꼈다.

### 2. 단일 책임 원칙이 테이블 설계에도 적용된다 — User와 Patient/Guardian을 분리한 이유

1번에서 관계 중심으로 설계를 시작하면서, 자연스럽게 "하나의 테이블이 하나의 역할만 해야 한다"는 원칙과 마주하게 되었다. 처음에는 User 테이블 하나에 로그인 정보, 환자 정보, 보호자 정보를 전부 넣으면 간단하지 않겠냐고 생각했다. 컬럼 몇 개 더 추가하면 되는 거 아닌가.

그런데 실제로 그려보니, 이 접근에는 구조적인 문제가 있었다. 환자의 경우 birth_year, gender, fcm_token 같은 정보가 필요하고, 보호자의 경우 fcm_token만 필요하다. 하나의 테이블에 전부 넣으면, 보호자 행에서 birth_year와 gender가 항상 NULL이 된다. 테이블에 "이 행이 환자인지 보호자인지"에 따라 어떤 컬럼은 쓰이고 어떤 컬럼은 쓰이지 않는 구조가 되는 것이다.

더 큰 문제는 우리 프로젝트의 온보딩 플로우에서 드러났다. 보호자가 먼저 가입하고 초기 설문을 통해 환자 정보를 등록하는데, 이 시점에서 환자는 아직 회원가입을 하지 않은 상태다. 즉, Patient 행은 존재하지만 user_id가 NULL인 상태가 발생한다. 만약 User 테이블 하나에 전부 넣었다면, "로그인 정보가 없는 User 행"이라는 모순이 생겼을 것이다.

```
[User]     → 인증/로그인 담당 (login_id, password, role)
[Patient]  → 환자 프로필 담당 (user_id=NULL 가능, name, birth_year, gender)
[Guardian] → 보호자 프로필 담당 (user_id NOT NULL)
```

이렇게 분리하니, User는 인증만, Patient/Guardian은 각자의 프로필만 책임지게 되었다. 객체지향에서 말하는 단일 책임 원칙(SRP)이 DB 설계에도 그대로 적용된다는 것을 이 과정에서 알게 되었다. 코드에서 클래스를 분리하는 이유와, 테이블을 분리하는 이유가 본질적으로 같다는 것이 인상적이었다.

### 3. 시드 데이터와 사용자 데이터는 섞이면 안 된다 — 루틴 테이블이 1개에서 3개가 된 이유

2번에서 테이블의 역할을 분리하는 원칙을 이해한 뒤, 이 원칙이 가장 극적으로 적용된 사례가 루틴 테이블이었다. 처음에 루틴은 하나의 테이블로 설계했었다.

```sql
-- 초기 설계 (잘못된 것)
Routine: id, matching_id, time_slot, activity, repeat_days, ...
```

그런데 우리 프로젝트의 루틴은 자유 입력이 아니었다. 시간대 7개(새벽, 이른 아침, 아침, ..., 저녁, 밤)와 활동 태그 11개(기상, 식사, 산책, ...)가 **고정**되어 있고, 보호자는 이 조합 중에서 선택만 하는 구조였다. 즉, 시간대와 활동 태그는 시스템이 미리 정해놓은 **시드 데이터**이고, 사용자의 선택은 이 시드 데이터 간의 **조합**이다.

이 둘을 하나의 테이블에 넣으면 무슨 일이 생기는가? 시드 데이터가 사용자 데이터와 섞이면서, 시드 데이터를 수정해야 할 때 모든 사용자 행에 영향이 간다. 시간대 이름을 "새벽"에서 "심야"로 바꾸고 싶으면, VARCHAR로 저장된 모든 행을 UPDATE 해야 하는 것이다. 데이터 정합성을 보장하기 어려워진다.

결론적으로 3개의 테이블로 분리했다.

```
TimeSlot    (시드, 7행 고정)   — id, name, start_time, end_time
ActivityTag (시드, 11행 고정)  — id, name, order_index
RoutineSlotTag (사용자 선택)  — matching_id, time_slot_id, activity_tag_id
```

TimeSlot과 ActivityTag는 시스템이 미리 넣어두는 시드 데이터이고, RoutineSlotTag는 사용자의 선택을 기록하는 테이블이다. "시드 데이터와 사용자 데이터를 분리해야 한다"는 원칙을 적용하다 보니 자연스럽게 이 구조가 나왔다. "서로 다른 성격의 데이터는 서로 다른 테이블에 살아야 한다"는 2번의 원칙이 여기서도 그대로 적용될 수 있을 것 같다.

### 4. Self-referencing으로 트리 구조 표현하기 — 하나의 테이블로 무한한 깊이를 담는 법

3번에서 시드 데이터의 구조를 고민하다 보니, 환자가 사용하는 표현 카테고리도 시드 데이터의 일종이라는 것을 알게 되었다. "몸"과 "마음" 아래에 하위 카테고리가 있고, 그 아래에 구체적인 표현이 있는 트리 구조인데, 이것을 테이블로 어떻게 표현할 것인가가 문제였다.

처음에 떠올린 방법은 depth별로 테이블을 나누는 것이었다. MainCategory, SubCategory, DetailCategory처럼. 그런데 이렇게 하면 깊이가 바뀔 때마다 테이블을 추가해야 하고, 쿼리도 depth별로 다르게 써야 한다. 유연하지 않다.

결론은 **self-referencing**, 즉 자기 자신을 참조하는 FK를 쓰는 것이었다.

```sql
Category: id, parent_id(FK → Category.id), name, depth, order_index
-- parent_id가 NULL이면 최상위 (몸, 마음)
-- parent_id가 있으면 해당 카테고리의 하위
```

하나의 테이블로 무한한 깊이의 계층 구조를 표현할 수 있었다. parent_id가 NULL이면 루트, 값이 있으면 해당 ID의 자식이 된다. 파일 시스템의 디렉토리 구조와 동일한 원리라는 설명을 듣고 바로 이해가 되었다. 디렉토리 안에 디렉토리가 있고, 그 안에 또 디렉토리가 있는 것처럼, Category 안에 Category가 있고, 그 안에 또 Category가 있는 것이다.

여기서 depth 컬럼이 흥미로웠다. parent_id를 재귀적으로 타고 올라가면 계산할 수 있는 값이니, 처음에는 "이것도 의도적 비정규화인가?"라고 생각했다. 그런데 곰곰이 따져보니 성격이 달랐다. Category는 시드 데이터다. 시스템 초기화 시 한 번 넣고 거의 변하지 않는다. depth는 카테고리를 트리에 배치할 때 "이 카테고리는 몇 번째 깊이에 있다"라고 정의하는 구조적 속성이지, 다른 컬럼에서 매번 계산해야 하는 파생값과는 다르다. 시드 데이터를 넣는 시점에 이미 알고 있는 값을 명시적으로 기록하는 것에 가깝다.

그런데 여기서 한 가지 더 의문이 들었다. 구조적 속성이라는 건 알겠는데, 현재 기능에서 depth를 실제로 쓰기는 하는가? 환자의 표현 선택 화면에서 쓰이는 쿼리는 `WHERE parent_id = ?`이지, `WHERE depth = ?`가 아니다. 지금으로서는 depth를 조회할 일이 없다.

그런데 우리 프로젝트의 본질을 다시 생각해보았다. 사용자가 루게릭 환자다. 시선추적으로 화면을 조작하는데, depth가 깊어질수록 환자가 눈을 움직여야 하는 횟수가 늘어난다. 안구 피로도는 이 프로젝트에서 단순한 편의성 문제가 아니라 핵심 UX 제약조건이다. 지금 당장 depth를 쿼리하는 기능은 없더라도, 카테고리 구조가 환자의 안구 피로에 어떤 영향을 주는지 분석할 시점이 올 가능성이 높다. 게다가 시드 데이터 테이블에 INT 컬럼 하나를 추가하는 비용은 사실상 0이다.

"지금 쓰이는가"만으로 판단하면 depth는 빠져야 한다. 하지만 "프로젝트의 핵심 관심사와 관련이 있는가"와 "저장 비용이 얼마인가"까지 함께 따지면, 남겨두는 것이 합리적이라는 결론을 내렸다.

### 5. 의도적 비정규화와 오버엔지니어링의 경계 — 넣을 것과 뺄 것을 구분하는 기준

4번에서 depth가 비정규화인지 아닌지를 따져본 것처럼, 설계 과정에서는 "이 컬럼이 정말 필요한가", "이 테이블이 정말 필요한가"를 판단해야 하는 순간이 여러 번 있었다. 그 중에서 "정규화를 깨는 것이 오히려 맞는 경우"와 "불필요한 것을 추가하는 오버엔지니어링"을 생각해볼 수 있는 두 가지 케이스가 있었다.

#### 5.1 의도적 비정규화 — UsageLog.time_slot_id

UsageLog 테이블에 time_slot_id 컬럼을 넣은 것이 대표적인 의도적 비정규화였다. 이 값은 used_at(사용 시각)에서 계산할 수 있다. "새벽 6시에 사용했으면 time_slot_id = 1"처럼 시간대를 판별할 수 있으니, 정규화 원칙대로라면 저장할 필요가 없는 파생 데이터다.

그런데 추천 시스템의 핵심 쿼리가 "이 시간대에 이 환자가 가장 많이 사용한 표현"이었다. 이 쿼리를 매번 실행할 때마다 used_at을 time_slot 범위와 비교 연산하는 것보다, time_slot_id를 미리 저장해두고 인덱스 검색을 하는 것이 성능상 유리하다고 생각했다.

```sql
-- 비정규화 덕분에 인덱스로 바로 검색 가능
SELECT phrase_id, COUNT(*) as cnt
FROM usage_log
WHERE matching_id = 7 AND time_slot_id = 3
GROUP BY phrase_id
ORDER BY cnt DESC;
```

#### 5.2 오버엔지니어링 제거 — Notification 테이블

반대 방향의 결정도 있었다. 처음에는 알림 이력을 저장하는 Notification 테이블을 설계에 포함시켰다. 알림이 발생할 때마다 행을 쌓고, 읽음 처리를 하고, 목록을 보여주는 구조였다.

그런데 하나씩 따져보니, 이 테이블이 담당해야 할 역할이 이미 다른 곳에 있었다.

```
- 호출/SOS 이력    → Call 테이블에 이미 기록됨
- 채팅 알림        → WebSocket/FCM으로 실시간 전달, DB 저장 불필요 (fire-and-forget)
- 메시지 읽음 상태 → Message.is_read가 이미 있음
```

Notification 테이블이 할 일이 없었다. 존재 이유가 "알림이니까 테이블이 있어야 하지 않을까"라는 막연한 느낌뿐이었다. "있으면 좋을 것 같은" 테이블을 만드는 것이 오버엔지니어링이라는 것을 이 사례에서 배웠다.

이 두 경험을 통해, 설계에서 무언가를 추가하거나 제거할 때의 판단 기준이 조금 더 명확해진 것 같다. 기본은 "이것이 실제 쿼리나 기능에서 쓰이는가"를 물어보는 것이다. 쓰이면 넣고, 쓰이지 않으면 빼는 것이다. 다만 4번의 depth처럼, 프로젝트의 핵심 관심사와 직결되면서 저장 비용이 거의 없는 경우는 예외적으로 남겨둘 수 있다는 것도 함께 배웠다. 단순하지만, 이걸 직접 경험해보지 않았으면 쉽게 체화되지 않았을 것 같다.

### 6. ERD는 코드를 짜기 전에 하는 "사고의 설계"다 — 오늘 하루를 관통하는 깨달음

여기까지 오고 보니, 오늘 하루 동안 배운 것이 단순히 "ERD 작성법"이 아니었다는 것을 느꼈다. SRP, 정규화, 비정규화, self-referencing, 시드 데이터 분리 — 이것들은 결국 **"데이터가 어떤 구조로 살아야 하는가"**에 대한 사고 과정이었다.

코드를 짜기 시작하면, 테이블 구조를 바꾸는 것은 코드를 바꾸는 것보다 훨씬 비용이 크다. migration을 돌려야 하고, 기존 데이터를 변환해야 하고, 관련된 모든 쿼리를 수정해야 한다. 그래서 ERD 설계는 코드를 짜기 전에 가능한 한 많은 문제를 사고 실험으로 해결하는 과정이라는 것을 알게 되었다. 머릿속에서 시뮬레이션을 돌리고, 빈틈을 찾고, 구조를 다듬는 것. 이것이 설계라는 행위의 본질이 아닌가 싶었다.

그리고 이것을 KPT 회고와 연결해서 생각해보면, 오늘의 ERD 설계가 바로 "실질적인 결과물"이 아닌가 싶었다. 지난번에는 추천 로직에 빠져서 ERD를 미뤘고, 이번 주말에는 컨디션 관리 실패로 진도가 느려졌다. 하지만 결국 17개 테이블 설계를 마무리하고, 왜 이렇게 설계해야 하는지를 이해하는 과정을 거쳤다. 열심히 하는 것에 도취되지 않고, 실질적인 결과물을 낸다는 것이 이런 것이라고 생각한다.

다만, 솔직하게 말하면 아직 부족한 부분이 많다. 인덱스 전략의 세부 사항, 실제 쿼리 최적화, 테이블 간의 cascade 삭제 정책 같은 것들은 아직 깊이 있게 다루지 못했다. 설계가 끝이 아니라 시작이라는 것을, 구현 단계에서 체감하게 될 것 같다. 꾸준히, 하나씩 해 나가야 한다.
