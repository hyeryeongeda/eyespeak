### 1. Docker 컨테이너의 OS 구조 — 커널 공유와 유저 영역 격리의 의미

---

프로젝트 인프라를 이해하려고 Docker 내부 구조를 파고들었다. "컨테이너 하나당 OS 하나인가?"라는 질문에서 시작했는데, 답은 "아니다"였다.

OS 메모리는 **커널 영역**(하드웨어 제어, 프로세스/메모리 관리)과 **유저 영역**(애플리케이션, 라이브러리, 파일시스템)으로 나뉜다. VM은 이 둘을 통째로 복제해서 완전히 독립된 OS를 만든다. 반면 Docker는 **호스트의 커널을 공유하고, 유저 영역만 격리**한다. 그래서 Dockerfile에서 `FROM ubuntu:22.04`라고 쓰는 건 Linux 커널을 설치하는 게 아니라 파일시스템과 라이브러리만 가져오는 것이다. AWS Ubuntu 서버 위에 컨테이너를 10개 띄워도 커널은 1개만 돌아간다.

여기서 흥미로웠던 건 Windows/Mac에서의 Docker 동작이다. Docker는 Linux 커널 기반이기 때문에, Windows/Mac에서는 Docker Desktop이 내부에 **경량 Linux VM을 하나 띄우고**, 그 위에서 컨테이너를 실행한다. 결국 어디서 돌리든 Docker 컨테이너는 Linux 커널 위에서 돌아가는 셈이다. Linux 서버에서는 네이티브로 커널을 공유하고, Windows/Mac에서는 VM이 그 커널을 제공하는 것이다.

이 구조를 알고 나니 Docker의 핵심이 뭔지 정리가 됐다. **유저 영역을 격리하는 것**이 Docker의 본질이고, 그래서 격리된 컨테이너끼리 통신하려면 docker-compose에서 **network 설정**으로 연결해야 하고, 연결되더라도 접근 인증을 위해 **.env 파일**에 비밀번호나 키를 넣어야 한다. 격리 → 연결 → 인증이라는 흐름이 자연스럽게 이해됐다.

### 2. 파일 수정 시 재빌드가 필요한 조건 — 메모리 캐싱과 자동 갱신 메커니즘

---

AWS dev 서버에 아이트래킹용 HTML/JS 파일을 드래그 앤 드롭으로 올렸는데, "이거 도커 재빌드 해야 하나?"라는 의문이 생겼다. 결론부터 말하면, 파일이 **도커 안에 있느냐 밖에 있느냐**가 기준이다.

도커 컨테이너 안에 있는 파일은 이미지 빌드 시점에 복사된 상태로 실행되기 때문에 재빌드가 필요하다. 호스트에 직접 놓인 파일은 바로 반영된다. 이때 "정적 파일이냐 동적 파일이냐"는 기준이 아니다. Spring Boot의 `.java` 파일이든 HTML 파일이든, 도커 이미지 안에 포함되어 있으면 재빌드가 필요하고, 호스트에 놓여 있으면 바로 반영된다.

더 파고들어보니, 호스트 파일이라도 **프로세스가 파일을 메모리에 캐싱하고 있고, 자동으로 캐시를 갱신하는 메커니즘이 없으면** 프로세스 재시작이 필요하다는 걸 알게 됐다. 구체적으로:

- **컴파일 언어(Java/Spring Boot)**: 소스가 JAR로 컴파일되어 실행되므로, 원본 `.java`를 수정해도 의미가 없다. 재빌드 필수.
- **인터프리터 언어(Python Flask)**: 모듈을 import 시점에 메모리에 캐싱한다. 프로세스가 살아있으면 변경을 감지하지 못하므로 재시작이 필요하다. 다만 재컴파일은 불필요하다.
- **웹서버 설정(Nginx)**: `nginx.conf`를 시작 시 메모리에 로드하고 이후 디스크를 참조하지 않는다. `nginx -s reload`가 필요하다.
- **정적 파일 서빙(Nginx의 HTML/JS/CSS)**: 요청마다 디스크에서 읽어서 응답한다. 캐싱 자체를 안 하므로 즉시 반영된다.

반대로, 캐시 갱신 메커니즘이 있는 경우는 재시작 없이도 반영된다. Spring Boot DevTools는 파일 변경을 감지해서 자동 재시작하고, React의 HMR은 코드 변경을 브라우저에 즉시 반영한다. 이런 도구들이 "개발 편의 도구"로만 보였는데, 사실 **캐시 갱신 문제를 해결하기 위한 도구**였다는 게 새로운 시각이었다.

### 3. JPA 영속성 컨텍스트 — EyeSpeak 코드에서 발견한 것

---

`PatientService.updatePatientInfo()`를 다시 보다가 질문이 생겼다. `patient.updateInfo(name, birthYear, gender)`는 그냥 자바 setter인데, `save()`를 호출하지 않는데도 DB가 업데이트된다. 왜?

답은 **영속성 컨텍스트(Persistence Context)**의 변경 감지(Dirty Checking) 메커니즘이었다.

#### 영속성 컨텍스트의 구조

영속성 컨텍스트는 엔티티를 DB에 보내기 전에 관리하는 중간 저장소다. 내부에 세 가지가 있다:

- **1차 캐시**: `Map<ID, 엔티티>` 구조. 영속 상태인 엔티티를 보관한다. 같은 트랜잭션 안에서 같은 엔티티를 다시 조회하면 DB에 안 가고 여기서 꺼낸다.
- **스냅샷 저장소**: 엔티티가 영속 상태가 된 시점의 복사본. 나중에 "뭐가 바뀌었는지" 비교할 때 쓴다.
- **쓰기 지연 SQL 저장소**: INSERT/UPDATE SQL을 모아뒀다가 플러시 시점에 한꺼번에 실행한다.

`ChatService.sendMessage()`에서 `messageRepository.save(message)`를 호출하면, Message 객체가 1차 캐시에 등록되고 스냅샷이 찍힌다. 이 시점부터 영속 상태(managed)다.

#### 변경 감지 — save() 없이 UPDATE가 되는 이유

다시 `PatientService.updatePatientInfo()`로 돌아오면:

```java
@Transactional
public void updatePatientInfo(Long userId, PatientUpdateRequest request) {
    Patient patient = getPatientByGuardianUserId(userId);  // DB 조회 → 영속 상태
    patient.updateInfo(request.getName(), request.getBirthYear(), request.getGender());
    // save() 없음
}
```

1. `@Transactional`로 트랜잭션이 시작된다
2. DB에서 Patient를 조회 → 영속 상태 (1차 캐시 + 스냅샷 저장)
3. `updateInfo()`로 자바 객체의 필드만 변경 (DB는 아직 모름)
4. 메서드 종료 → 트랜잭션 커밋 → 플러시 발동
5. 영속성 컨텍스트가 모든 영속 엔티티의 현재 상태와 스냅샷을 비교
6. "name이 바뀌었네" → UPDATE SQL 자동 생성 + 실행

`save()`의 역할은 "변경을 DB에 반영하는 것"이 아니라 **"새 엔티티를 영속 상태로 만드는 것"**이다. 이미 영속 상태인 엔티티(DB에서 조회해온 것)는 save()가 필요 없다. 같은 패턴이 `AuthService.resetPassword()`에도 있다 — `user.changePassword()`만 호출하고 save() 없이 트랜잭션 커밋 시 자동 UPDATE.

#### IDENTITY 전략과 쓰기 지연

EyeSpeak의 모든 엔티티는 `@GeneratedValue(strategy = GenerationType.IDENTITY)`를 쓴다. 이건 MySQL의 AUTO_INCREMENT인데, **INSERT를 해봐야 ID를 알 수 있다.** 1차 캐시가 `Map<ID, 엔티티>` 구조이므로 ID를 모르면 캐시에 넣을 수가 없다. 그래서 IDENTITY 전략에서는 `save()` 호출 시점에 INSERT가 즉시 나간다. 쓰기 지연이 불가능하다.

반면 SEQUENCE 전략(Oracle, PostgreSQL)은 INSERT 없이 ID만 먼저 채번할 수 있어서 INSERT를 나중에 모아서 보낼 수 있다(쓰기 지연 가능). EyeSpeak은 MySQL이니까 IDENTITY가 자연스러운 선택이고, 메시지를 한 번에 하나씩 저장하는 구조라 쓰기 지연이 안 되는 것이 실질적 문제는 아니다.

#### 하나의 트랜잭션에서 여러 엔티티 변경

`AuthService.signupPatient()`가 가장 좋은 예시다:

```java
@Transactional
public PatientSignupResponse signupPatient(PatientSignupRequest request) {
    userRepository.save(user);                     // User INSERT
    matching.getPatient().linkUser(user);           // Patient 필드 변경 (dirty checking)
    matching.link();                                // Matching 상태 변경 (dirty checking)
    ttsSettingRepository.save(ttsSetting);          // TtsSetting INSERT
}
```

하나의 트랜잭션에서 `save()` 2번(INSERT)과 dirty checking 2번(UPDATE)이 발생한다. 커밋 시점에 User INSERT + Patient UPDATE + Matching UPDATE + TtsSetting INSERT가 한꺼번에 실행되고, 하나라도 실패하면 전부 롤백된다. 만약 Patient만 업데이트되고 Matching 상태가 안 바뀌면 데이터 불일치가 생기는데, 이게 트랜잭션이 존재하는 이유다.

#### delete + save vs dirty checking

`FavoriteService.updateFavorite()`는 즐겨찾기 "수정"인데 dirty checking을 안 쓰고 삭제 + 재생성을 했다. FavoritePhrase의 정체성이 `matching_id + phrase_id` 조합인데, phrase를 바꾸면 사실상 다른 레코드다. "A 문구 즐겨찾기"를 "B 문구 즐겨찾기"로 바꾸는 건 수정이 아니라 교체. 엔티티의 속성이 바뀔 때는 dirty checking, 정체성(FK 조합)이 바뀔 때는 delete + save가 의미적으로 맞다.
