### 1. RAG를 "왜 쓰는가"에 대한 비판적 사고 과정

추천 로직을 고민하면서, RAG를 도입하려던 초기 접근에 대해 스스로 의문을 던져보았다. **"LLM만으로 되는 거 아닌가?"** 이 질문이 출발점이었다. RAG를 쓰겠다고 먼저 정해놓고 시작한 건 아닌지, 정말 RAG여야만 하는 이유가 있는지를 검증해보고 싶었다.

돌이켜보면, 처음에는 "RAG를 쓰겠다"에서 출발했지 "왜 RAG여야 하는가"에서 출발하지 않았던 것 같다. 기술을 먼저 정하고 근거를 끼워 맞추는 순서였던 셈이다. 이 부분이 가장 큰 반성 포인트였다.

### 2. 벡터 유사도의 구조적 한계 — 질문과 응답은 가깝지 않다

RAG의 핵심인 벡터 검색을 따져보다가, 구조적인 문제를 하나 발견하게 되었다. 처음에는 "물 마실래?"라는 질문의 임베딩으로 "네, 마실래요"라는 응답을 검색할 수 있을 거라 전제하고 있었다. 보호자가 "물 마실래?"라고 물으면, 벡터DB에서 "네, 마실래요"라는 환자 응답을 바로 찾아올 수 있을 거라고 생각한 것이다.

그런데 곰곰이 생각해보니, 이 전제가 맞지 않을 수 있겠다는 생각이 들었다. 벡터 임베딩은 문장을 고차원 공간의 점으로 변환하고, 의미가 비슷한 문장일수록 가까운 위치에 배치하는 방식이다. 여기서 "의미가 비슷하다"는 건 문장의 내용이나 형태가 유사하다는 뜻이지, 대화에서 서로 짝이 된다는 뜻이 아니다.

예를 들어 "물 마실래?"의 임베딩 근처에 있을 법한 문장들을 생각해보면:

```
"물 마실래?"에 가까운 것 (유사도 높음):
  → "음료 마실래?", "물 줄까?", "목 마르니?" — 비슷한 질문들

"물 마실래?"에서 먼 것 (유사도 낮음):
  → "네, 마실래요", "아니, 괜찮아" — 대응하는 응답들
```

질문과 응답은 대화에서는 짝이지만, 임베딩 공간에서는 전혀 다른 종류의 문장이다. "물 마실래?"와 "네, 마실래요"는 인간이 보기에는 자연스럽게 이어지지만, 벡터 유사도로 보면 "물 마실래?"와 "음료 마실래?"가 훨씬 가깝다. 질문-응답 간에는 유사도가 아니라 대응 관계가 있는 것이고, 이 대응 관계를 벡터 유사도로 해결하려는 것 자체가 도구를 잘못 쓰는 것이 아닌가 싶었다.

그래서 내 나름대로 내린 결론은, 벡터 검색은 질문끼리 비교해서 의도를 매칭하는 데에 쓰고, 그에 대응하는 응답은 별도의 구조화된 DB에서 가져오는 방식이 더 적합하지 않을까 하는 것이었다. 벡터 검색이 만능이 아니라, 어디에 쓸 수 있고 어디에 쓸 수 없는지를 구분하는 게 중요하다는 것을 느꼈다.

### 3. 실제 파이프라인 설계 — 2번의 깨달음을 구조로 옮긴 과정

2번에서 질문-질문 비교가 맞겠다는 결론을 내린 뒤, 이걸 우리 프로젝트에 실제로 어떻게 적용할 수 있을지 파이프라인을 구체적으로 그려보았다.

```
보호자 질문 입력
  → [벡터DB] 유사 질문 검색 (질문-질문 비교)
  → 매칭된 질문을 key로 사용
  → [DB] 해당 key의 환자 응답 데이터 조회 (텍스트 + 빈도)
  → 빈도순 정렬
  → [LLM] 컨텍스트로 전달 → 응답 생성
```

내가 고민한 구조를 풀어서 설명하면 이렇다. 보호자가 질문을 입력하면, 벡터DB에서 해당 질문과 유사도가 가장 높은 질문을 찾는다. 여기까지가 검색 단계이고, 2번에서 고민했던 "질문끼리 비교한다"는 원칙이 그대로 적용된다. 찾아낸 질문을 key로 두고, 이 key에 매핑된 value를 DB에서 가져온다. 이 value는 해당 질문에 대해 환자가 실제로 선택했던 대답들의 텍스트와 선택 횟수(빈도) 데이터다. 이 대답들을 빈도순으로 정렬해서, LLM에게 "이 보호자의 질문과 가장 유사한 질문에 대해서 환자는 이런 대답들을 해왔다"는 컨텍스트로 전달한다. LLM은 이 컨텍스트를 근거로 응답을 생성한다.

정리하면, 벡터 검색은 의도 매칭(질문-질문)에만 쓰고, 실제 응답 데이터는 구조화된 DB에서 key-value로 가져오는 방식이다. 벡터 검색이 잘하는 일과 못하는 일을 구분한 뒤, 각자 적합한 도구를 배치해보려 했다.

### 4. 프로토타입으로 개념 확인 — 설계가 실제로 동작하는지 돌려본 것

파이프라인을 설계하고 나니, 머릿속에서만 돌린 로직이 실제로 동작하는지가 궁금해졌다. sentence-transformers의 다국어 임베딩 모델(paraphrase-multilingual-MiniLM-L12-v2)로 간단한 프로토타입을 만들어서 두 가지를 확인해보았다.

#### 4.1 가설 확인 — 질문-질문 유사도 > 질문-응답 유사도

2번에서 추론했던 "질문끼리의 유사도가 질문-응답 간 유사도보다 높을 것"이라는 가설을 실제 임베딩으로 확인해보았다.

```
"물 마실래?" 기준:
  질문 유사도 평균: 0.71  ("음료 마실래?" 0.82 / "물 줄까?" 0.90)
  응답 유사도 평균: 0.38  ("네, 마실래요" 0.42 / "아니, 괜찮아" 0.34)
  차이: +0.33

"밥 먹었어?" 기준:
  질문 유사도 평균: 0.87  ("식사 했어?" 0.97 / "뭐 먹었어?" 0.87)
  응답 유사도 평균: 0.50  ("네, 먹었어요" 0.71 / "아직이요" 0.42)
  차이: +0.37
```

3개 케이스 모두에서 질문-질문 유사도가 질문-응답 유사도보다 일관되게 높았다. 차이가 +0.16에서 +0.37까지로, 2번에서 추론했던 내용이 실제 수치로도 확인된 셈이다. 벡터 검색을 질문-질문 비교에 쓰고, 응답은 별도 DB에서 가져오겠다는 3번의 설계 방향이 틀리지 않았다는 것을 확인할 수 있었다.

#### 4.2 파이프라인 개념 확인 — 잘 된 것과 안 된 것

벡터DB에 보호자 질문 8개를 넣고, 각 질문에 환자 응답 데이터(텍스트 + 선택 빈도)를 매핑한 시뮬레이션 환경을 만들어서, 보호자가 다른 표현으로 질문했을 때 올바른 질문에 매칭되는지 확인해보았다.

**잘 된 경우 — 직접적 표현 변환:**

보호자가 같은 의도를 다른 단어로 표현한 경우는 정확하게 매칭되었다.

```
"밥 좀 먹을래?"       -> "밥 먹을래?"       (유사도 0.98)
"화장실 다녀올래?"    -> "화장실 가고 싶어?" (유사도 0.95)
"체위 변경해줄까?"    -> "자세 바꿔줄까?"   (유사도 0.92)
"좀 추워 보이는데 괜찮아?" -> "춥지 않아?"  (유사도 0.87)
```

의료 용어("체위 변경")와 일상 용어("자세 바꿔줄까?") 간의 매칭도 잘 동작했다. 이 결과를 보고, 같은 의도를 표현만 바꿔서 말하는 수준에서는 벡터 검색이 충분히 유효하겠다는 생각이 들었다.

**안 된 경우 — 간접 표현과 의미 추론:**

반면, 보호자가 증상을 묘사하거나 간접적으로 표현한 경우에는 매칭이 실패했다.

```
"입이 좀 마른 것 같은데"       -> 기대: "물 마실래?" / 실제: 매칭 실패
"아까부터 얼굴이 안 좋아 보여" -> 기대: "어깨 아파?" / 실제: 매칭 실패
```

"입이 마르다"에서 "물이 필요하다"를 추론하는 것은 벡터 유사도가 할 수 있는 일이 아니었다. 벡터 검색은 문장의 형태적 유사성은 잡을 수 있지만, 증상에서 의도를 추론하는 것은 별개의 능력이라는 것을 알게 되었다.

#### 4.3 이 실험의 한계와 의미

솔직하게 말하면, 이 실험은 "검증"이라고 부르기엔 부족하다. 벡터DB에 질문이 8개뿐이고, 데이터도 전부 내가 임의로 만든 시뮬레이션이며, LLM 생성 단계는 테스트하지 못했다. 프로토타입 수준의 개념 확인이라고 보는 게 맞다.

그럼에도 이 실험에서 얻은 것이 있다면, 벡터 검색의 실질적인 한계를 직접 확인한 것이다. 벡터 검색은 '의미적 유사도'를 잘 잡아내지만, '맥락적 유사도'를 잡아내는 것은 한계가 있다라는 것을 직접 눈으로 확인해볼 수 있었다. 이 한계를 해결하려면 벡터 검색 전에 LLM 기반의 의도 분류 단계를 추가하거나, 한국어에 특화된 임베딩 모델을 적용해보는 등의 접근이 필요할 것 같다는 생각이 들었다.

### 5. 검색과 생성의 역할 구분 — RAG가 할루시네이션을 줄여주는 구조를 이해한 것

4번의 실험에서 검색이 실패하면 엉뚱한 응답 데이터가 LLM에 전달되는 것을 직접 확인했는데, 이 경험을 하고 보니 이전에 RAG의 장점이라고 생각했던 부분들에 대해서도 다시 생각해보게 되었다. 환각 방지나 일관성 같은 것들을 RAG의 고유한 장점이라고만 생각하고 있었는데, 이게 왜 장점인지를 제대로 설명하지 못하겠다는 느낌이 들어서 좀 더 구조적으로 따져보았다.

할루시네이션은 LLM이 텍스트를 생성하는 단계에서 발생하는 문제다. LLM이 자신의 파라미터 지식만으로 답을 만들다 보니, 근거 없이 그럴듯한 내용을 생성하게 되는 것이다. 여기서 RAG의 역할을 다시 생각해보았다. RAG는 검색을 통해 관련 문서를 먼저 찾고, 이 문서를 LLM에게 컨텍스트로 전달한다. LLM은 자기 지식만으로 생성하는 것이 아니라, 검색된 근거를 바탕으로 생성하게 되므로 할루시네이션이 줄어드는 구조인 것이다.

그러니까 "RAG가 할루시네이션을 줄여준다"는 것 자체는 맞는 말이었다. 다만 내가 처음에 혼동했던 부분은, 이것이 RAG를 쓰기만 하면 자동으로 해결되는 것처럼 생각했다는 점이다. 실제로는 **검색 단계가 올바른 문서를 가져와야만** 의미가 있다. 검색이 잘못되면 RAG를 써도 할루시네이션은 여전히 발생할 수 있다.

이 과정을 거치고 나니, RAG 파이프라인의 각 단계가 무엇을 책임져야 하는지가 좀 더 명확해진 것 같았다.

- **검색 단계:** 보호자 질문 → 벡터DB에서 유사 질문 매칭 → 매칭된 질문의 key로 환자의 과거 응답 데이터(빈도 포함)를 조회. 이 단계의 책임은 올바른 질문을 찾아서 올바른 응답 데이터를 가져오는 것이고, 이 단계가 실패하면 이후의 생성 품질도 무너진다.
- **생성 단계:** 검색된 환자 응답 데이터 + 컨텍스트 → LLM 정제. 검색이 올바른 근거를 제공했을 때, 환각 방지, 일관성, 맥락 반영이 비로소 효과를 발휘한다.

정리하면, RAG가 할루시네이션을 줄여주는 것은 맞지만, 그 전제는 검색 단계가 제대로 동작해야 한다는 것이었다. 처음부터 이 구조를 이해하고 접근했다면, RAG 도입 근거를 좀 더 명확하게 세울 수 있었을 것 같다는 아쉬움이 남았다.

---

### 6. 이게 정말 필요한가 — 오버엔지니어링에 대한 고민

파이프라인을 설계하고 나서, 한 발 물러서서 스스로에게 질문을 던져보았다. **우리 프로젝트에서 이걸 RAG를 쓸 만큼 유저 데이터가 방대해질 일이 있을까?** 솔직히, 이 고민도 맞다고 생각한다. 현재 단계에서 환자 한 명의 데이터가 벡터 검색이 필요할 정도로 쌓이기까지는 상당한 시간이 걸릴 것이고, 단순한 규칙 기반이나 키워드 매칭으로도 충분히 동작할 수 있는 규모일 가능성이 높다.

그럼에도 이 고민을 계속했던 이유를 솔직하게 돌아보면, 기술적 욕심이 있었던 것 같다. RAG라는 기술을 직접 설계하고 적용해보고 싶다는 마음이 분명히 있었다. 다만, 그게 순전히 나쁜 것만은 아니라고도 생각했다. 유저의 사용량이 방대해졌을 때는 충분히 고려해볼 수 있는 구조이고, 지금 이 설계를 해둔다면 나중에 확장이 필요할 때 밑그림이 있는 상태에서 출발할 수 있기 때문이다.

그런데 이 고민을 KPT 회고와 연결해서 생각해보니, 결국 같은 맥락의 문제였다는 것을 깨닫게 되었다. 추천 로직에 대한 기술적 욕심 때문에 RAG를 깊이 파고든 것이, 결과적으로 ERD와 API 명세서 작성을 미루게 만들었고, 팀원들이 할 일을 못하게 만든 원인이었다. 기술적으로 의미 있는 고민이었다고는 생각하지만, 그 고민에 빠져 있는 동안 팀 전체의 진행이 멈춰 있었다는 사실을 외면해서는 안 된다.

"이게 지금 필요한가, 아니면 내가 하고 싶은 건가"를 구분하는 것. 이건 단순히 기술 선택의 문제가 아니라, 팀에서 일하는 개발자로서의 태도 문제이기도 하다는 것을 느꼈다. 내가 하고 싶은 기술을 파는 것과, 팀이 지금 필요로 하는 것을 해내는 것 사이에서 균형을 잡는 게 앞으로의 과제라고 생각한다.

### 7. CI/CD의 정확한 이해 — 품질 개선과 검증 자동화는 다르다

CI/CD에 대해서도 개념이 모호한 상태에서 적용하려 했다는 것을 인지하게 되었다. 처음에는 CI/CD를 도입하면 로직의 품질 자체가 좋아지는 것처럼 생각하고 있었는데, 공부해보니 그게 아니었다.

CI/CD의 핵심은 **"로직을 개선하는 게 아니라, 개선한 후에도 안 깨졌는지 검증하고, 배포를 자동화하는 것"**이라고 이해하게 되었다. 정량적 평가와 자동화된 검증은 다른 개념이었고, 이 차이를 구분하는 데 시간이 좀 걸렸다.

이 개념을 정리하고 나니, 우리 프로젝트에서 CI/CD를 적용한다면 어떤 테스트가 필요할지도 어렴풋이 그려지기 시작했다. 예를 들어 추천 품질 테스트(Hit Rate, 카테고리 누수), 새로고침 시 같은 추천 표현이 뜨진 않는지 중복 방지 테스트, 사용자 로그가 들어오는 것에 대한 유효성 검증(잘못된 사용자 로그가 들어오는 건 아닌지), 콜드 스타트 엣지 케이스 같은 것들이 검증 대상이 될 수 있겠다는 생각이 들었다. 아직 실제로 구현한 것은 아니지만, CI/CD가 무엇을 위한 것인지를 이해한 것만으로도 앞으로의 방향을 잡는 데 도움이 될 것 같다.
