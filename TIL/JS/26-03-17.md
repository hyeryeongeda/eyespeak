### 1. 복합 인덱스의 좌측 접두사 원칙 — 인덱스 하나가 두 가지 검색을 커버한다

지난 TIL에서 "인덱스 전략의 세부 사항은 아직 깊이 있게 다루지 못했다"고 썼는데, 이번 ERD 검토에서 바로 그 부분과 마주치게 되었다.

팀원이 expressions 테이블에 인덱스 추가를 제안해줬다. 이 제안을 검토하는 과정에서, `(matching_id)` 단독 인덱스와 이미 존재하는 `(matching_id, last_used)` 복합 인덱스의 관계가 궁금해졌다. "단독 검색과 복합 검색은 다른 거 아닌가?"라고 처음에는 생각했다.

그런데 복합 인덱스의 좌측 접두사 원칙이라는 것을 알게 되었다. 복합 인덱스 `(A, B)`는 내부적으로 A를 먼저 정렬하고, 같은 A 값 안에서 B를 정렬하는 구조다. 그래서 `WHERE A = ?` 검색을 할 때, B가 없어도 A 기준으로 이미 정렬되어 있으니 인덱스를 탈 수 있다.

```
복합 인덱스 (matching_id, last_used) 의 내부 정렬:

matching_id=1, last_used=03-01
matching_id=1, last_used=03-05
matching_id=1, last_used=03-10
matching_id=2, last_used=03-02
matching_id=2, last_used=03-08
...

→ WHERE matching_id = 1                              → 인덱스 사용 가능
→ WHERE matching_id = 1 AND last_used > '03-05'      → 인덱스 사용 가능
→ WHERE last_used > '03-05'                           → 인덱스 사용 불가 (왼쪽이 빠졌으므로)
```

결론적으로, `(matching_id, last_used)` 복합 인덱스가 이미 있으면 `(matching_id)` 단독 인덱스는 별도로 만들 필요가 없었다. 하나의 복합 인덱스가 두 가지 검색 패턴을 커버하는 것이다. 팀원의 제안이 없었으면 이 원리를 따져볼 계기 자체가 없었을 것이다.

### 2. 인덱스에도 대칭성이 있다 — 같은 역할의 FK에 같은 패턴의 인덱스가 필요한 이유

1번에서 복합 인덱스의 원리를 이해하고 나니, 바로 다음 문제가 눈에 들어왔다. usage_log 테이블의 인덱스 구조에 비대칭이 있었던 것이다.

usage_log에는 "환자가 어떤 표현을 사용했는가"를 기록하는 3가지 방식이 있다. 시드 표현을 사용하면 `phrase_id`, 맞춤 표현을 사용하면 `expr_id`, 자유 입력이면 `content`에 값이 들어가고, 나머지는 NULL이 된다. 이 세 컬럼은 서로 배타적으로, 항상 하나만 값을 가진다.

```
phrase_id | expr_id | content
----------|---------|--------
42        | NULL    | NULL        ← 시드 표현 선택
NULL      | 15      | NULL        ← 맞춤 표현 선택
NULL      | NULL    | "물 주세요"  ← 자유 입력
```

그런데 인덱스를 보니, `(matching_id, phrase_id)`는 있는데 `(matching_id, expr_id)`는 없었다. phrase_id와 expr_id는 동일한 역할을 하는 FK인데, 한쪽만 인덱스가 있는 것이다. "맞춤 표현 #15가 몇 번 사용됐는가"를 조회하려면 expr_id로 검색해야 하는데, 인덱스가 없으면 테이블 풀 스캔이 발생한다.

같은 역할을 하는 FK라면, 같은 패턴의 인덱스가 있어야 한다. 이것을 인덱스의 대칭성이라고 이해했다. 이런 비대칭은 ERD가 점진적으로 확장될 때 자연스럽게 생기기 쉽다. 처음에는 phrase_id 중심으로 설계하다가, 나중에 expr_id가 추가되면서 인덱스가 함께 따라오지 못한 것이다. 검토 단계에서 "같은 역할을 하는 컬럼이 같은 대우를 받고 있는가"를 확인하는 것이 중요하다는 것을 배웠다.

### 3. 타임스탬프는 비즈니스 로직이 아니라 운영 인프라다 — created_at/updated_at을 넣는 진짜 이유

인덱스 문제를 정리하고 나서, 다음으로 눈에 들어온 것은 타임스탬프 누락이었다. user_words 테이블에 created_at과 updated_at이 없었다. "이 테이블의 데이터를 시간순으로 조회하는 기능이 없으니 필요 없는 거 아닌가?"라고 처음에는 생각했다.

그런데 created_at/updated_at은 비즈니스 로직만을 위한 컬럼이 아니었다. 운영과 디버깅을 위한 인프라 컬럼이었다.

프로덕션에서 "이 환자의 단어 목록이 이상하다"는 제보가 들어왔다고 가정해보자. updated_at이 없으면 "언제 마지막으로 수정된 건가?"를 알 방법이 없다. 로그를 뒤져야 하고, 로그마저 없으면 원인 추적이 불가능하다. updated_at이 있으면 "3일 전에 수정됐다"는 단서를 바로 얻을 수 있다.

더 흥미로웠던 것은 캐시 무효화에서의 활용이었다. 자주 조회하는 데이터를 캐시에 올려두면, "캐시에 있는 데이터가 DB와 같은가"를 판단해야 하는 순간이 온다. 이때 updated_at을 비교하면 된다.

```
캐시: { data: ..., updated_at: "03-15 14:00" }
DB:   { data: ..., updated_at: "03-17 09:30" }

→ DB가 더 최신 → 캐시 폐기 → DB에서 다시 로드
```

캐시의 updated_at보다 DB의 updated_at이 더 최근이면, 캐시를 폐기하고 DB에서 다시 가져오는 것이다. 비용은 datetime 컬럼 2개뿐이지만, 디버깅과 캐시 전략에서 그 이상의 가치를 제공한다. 실무에서는 거의 모든 테이블에 이 두 컬럼을 넣는 것이 관례라는 것을 알게 되었다. "지금 안 쓰니까 빼자"가 아니라 "운영에서 반드시 필요해질 것이므로 넣자"라는 관점의 전환이었다.

### 4. 설계와 검토는 다른 차원의 사고다 — 만드는 것과 깨뜨리는 것의 차이

여기까지 오고 보니, 어제의 설계와 오늘의 검토가 본질적으로 다른 사고 과정이었다는 것을 느꼈다.

어제는 "무엇을 만들 것인가"를 고민했다. Matching 테이블을 도입하고, User/Patient/Guardian을 분리하고, 시드 데이터와 사용자 데이터를 나누고. 구조를 세우는 일이었다.

오늘은 "무엇이 잘못될 수 있는가"를 고민했다. 인덱스가 빠진 곳은 없는가, 타임스탬프가 누락된 곳은 없는가, 같은 역할을 하는 컬럼이 비대칭으로 다뤄지고 있지는 않은가. 구조를 시험하는 일이었다.

설계할 때는 "이 테이블이 필요하다"는 확신을 가지고 추가하지만, 검토할 때는 "이 인덱스가 정말 필요한가", "이 인덱스가 빠진 것은 아닌가"라는 의심을 가지고 하나씩 따져본다. 팀원의 인덱스 제안을 함께 논의하면서, 단순히 "있으면 좋지 않을까"가 아니라 "이 인덱스가 실제로 필요한 근거가 있는가"를 따져보는 경험을 할 수 있었다.

테이블 배치를 정리하면서도 비슷한 경험을 했다. FK 의존성 흐름대로 배치하는 방식, 비즈니스 기능 중심으로 배치하는 방식, 허브 테이블 중심 방사형 배치 — 여러 방식이 있었는데, 정해진 표준은 없었다. 처음에는 "정답이 있을 것이다"라고 생각했지만, 결국 "팀원들이 읽기 쉬운가"라는 기준으로 기능/계층 중심 배치를 선택했다. 관계선이 겹치는 트레이드오프는 dbdiagram.io의 인터랙티브 관계 표시 기능을 근거로 수용했다. 그리고, 이 과정에서 내 나름의 분석 과정을 찾은 것 같다.

1. 이건 정답이 있는가? 아니면 트레이드 오프인가?
2. 트레이드 오프라면 -> 핵심이 무엇인가? 결국 뭘 하고 싶어서 이걸 고민하는거지?
3. 위의 두 질문에 대한 대답에 항상 근거를 붙인다. (나도 납득 못하면, 팀원들도 절때 납득 못한다.)

어제 TIL 마지막에 "인덱스 전략, 쿼리 최적화 같은 것들은 아직 깊이 있게 다루지 못했다"고 썼는데, 오늘 그 부분을 일부 채울 수 있었다. 다만, 이것들이 실제 JPA 엔티티와 쿼리에서 어떻게 작동하는지는 아직 직접 구현해보지 않았다. ERD 위의 논의와 실제 코드 사이에는 분명히 또 다른 간극이 있을 것이다. 다음 단계에서 그 간극을 직접 경험해보려 한다.
