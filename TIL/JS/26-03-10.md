### 1. MediaPipe란 무엇인가

#### 1.1 정의와 역할

MediaPipe는 Google이 만든 **실시간 영상 인식 라이브러리**이다. 카메라 영상을 입력으로 넣으면, 그 안에서 사람의 얼굴/손/몸 등을 찾아서 **좌표 데이터로 반환**해준다.

```
[입력]                    [MediaPipe]                [출력]
웹캠 프레임 (이미지)  →   내부 AI 모델이 처리   →   좌표 데이터
(RGB, 640x480 등)                                  (x, y, z 값들의 집합)
```

개발자가 하는 일은 입력을 넣고 출력을 받는 것뿐이고, 중간의 AI 처리는 MediaPipe가 내부적으로 수행한다.

#### 1.2 이 프로젝트에서 사용하는 솔루션

MediaPipe는 여러 솔루션(Face Mesh, Hands, Pose 등)을 제공하는데, 이 프로젝트에서 사용하는 건 **Face Mesh + Iris** 조합이다.

- **Face Mesh**: 얼굴에 468개 좌표점(랜드마크)을 생성
- **Iris**: 홍채에 10개 좌표점을 추가 (총 478개)

#### 1.3 Face Mesh + Iris가 눈에 대해 주는 데이터

```
[1] 눈 외곽 윤곽선 (468개 중 일부): 좌안 약 16개, 우안 약 16개
    → 눈의 위치, 크기, 열림 정도(블링크 감지)를 알 수 있음

[2] 홍채 (Iris Refinement으로 추가되는 10개): 좌안 5개, 우안 5개
    왼쪽 홍채: 468(중심), 469, 470, 471, 472
    오른쪽 홍채: 473(중심), 474, 475, 476, 477
    → 홍채의 중심 위치와 크기를 알 수 있음
```

Iris 기능을 사용하려면 `refine_landmarks=True`를 설정해야 한다.

#### 1.4 좌표 데이터의 형태

각 랜드마크는 x, y, z 세 가지 값을 가진다.

```python
landmark[468].x   # 0.0 ~ 1.0 (화면 왼쪽 ~ 오른쪽)
landmark[468].y   # 0.0 ~ 1.0 (화면 위쪽 ~ 아래쪽)
landmark[468].z   # 깊이 (카메라와의 거리, 상대값)
```

x, y 값은 픽셀이 아니라 **0~1 사이의 비율**이다. 화면 해상도가 640x480이면, x=0.5는 실제 320px 위치를 의미한다.

#### 1.5 MediaPipe 내부 처리 순서와 근본적 제약

`process()`를 호출하면 내부적으로 3단계가 순차적으로 실행된다.

```
[1단계] 얼굴 검출 → 이미지 안에서 얼굴 영역을 사각형으로 찾음
[2단계] 얼굴 메시 생성 → 얼굴 영역 안에서 468개 점의 좌표를 추정
[3단계] 홍채 정밀화 → 눈 영역을 세밀하게 분석하여 홍채 10개 점 추가
```

**핵심 제약: 1단계에서 얼굴 전체가 인식되어야 2, 3단계로 넘어간다.** 이것이 루게릭 환자 환경에서 발생하는 문제의 근본 원인이다. 고개가 틀어지면 1단계(얼굴 검출)가 불안정해지고, 이후 홍채 좌표 전부가 불안정해지거나 아예 나오지 않는다.

### 2. 캘리브레이션의 역할

#### 2.1 정의

캘리브레이션이란 **"이 사람이 이 환경에서 특정 방향을 볼 때, 홍채 좌표가 어떻게 나오는지 미리 기록해두는 것"**이다.

#### 2.2 왜 필요한가

같은 곳을 봐도 사람마다, 환경마다 홍채 좌표가 다르다. 눈 크기, 카메라 위치, 카메라와의 거리, 앉은 자세, 눈 움직임 범위(루게릭 환자는 개인차가 큼) 등이 모두 다르기 때문에, **모든 사람에게 통하는 고정된 기준값이 존재할 수 없다.** 사용 전에 그 사람, 그 환경에 맞는 기준을 만들어야 하고, 그것이 캘리브레이션이다.

#### 2.3 과정

```
화면에 영역 표시 → 사용자가 해당 영역 응시 → 그때의 홍채 좌표 기록 → 다음 영역 반복
```

6분할이면 6번 반복하여 각 영역별 기준 좌표를 확보한다.

#### 2.4 실시간 판정 로직

캘리브레이션 후에는 **실시간 홍채 좌표를 기록된 기준 좌표와 비교**하여, 가장 가까운 영역으로 판정한다. 즉, "현재 홍채 좌표가 어느 기준점에 가장 가까운가"를 계산하는 것이 핵심 로직이다.

### 3. 6분할 고도화 — 두 가지 문제의 분리

팀원에게 받은 기술 고도화 방안을 분석한 결과, 사실 **두 가지 독립적인 문제**가 섞여 있었다.

```
문제 A: 4분할 → 6분할로 정밀도를 올리고 싶다
문제 B: 고개 틀어짐에도 안정적으로 동작하게 하고 싶다
```

이 두 문제는 해결 방법이 다르다.

#### 3.1 문제 A (4→6분할) — 캘리브레이션 고도화로 충분

6분할 시선 판정의 입력과 출력은 다음과 같다.

```
입력: 홍채 좌표 2개 (iris_x, iris_y)
출력: 6개 영역 중 하나
```

**2개의 숫자로 6개 중 하나를 고르는 문제**이므로, 2D 평면 위의 점을 6개 영역으로 나누는 기하학적으로 단순한 문제이다. ML 모델 학습이 의미가 있으려면 입력이 고차원(이미지 수만 픽셀)이고 패턴이 복잡해야 하는데, 좌표 2개로 6개 분류하는 문제는 이 조건에 해당하지 않는다. 다항 회귀(degree 2~3)나 threshold 비교로 충분히 해결 가능하다.

다만, 영역이 6개로 늘어나면 기준점 사이 간격이 좁아져서 오판이 잦아지므로, 캘리브레이션의 **정확도를 높이는 보조 장치**가 필요하다.

**캘리브레이션 고도화 방법들:**

| 순위 | 항목                | 효과 | 설명                                                                          |
| :--: | ------------------- | :--: | ----------------------------------------------------------------------------- |
|  1   | 회귀 함수 전환      |  큼  | 기준점 비교 대신 다항 회귀로 연속적인 화면 좌표 예측. 비선형 왜곡도 보정 가능 |
|  2   | 머리 움직임 보정    |  큼  | 고개 움직임으로 홍채 좌표가 밀리는 것을 역보정                                |
|  3   | 양쪽 눈 융합        | 중간 | 양쪽 홍채 좌표의 가중 평균으로 떨림 감소                                      |
|  4   | 칼만 필터           | 중간 | 이동 평균보다 반응 빠르고 안정적인 좌표 평활화                                |
|  5   | 동적 재캘리브레이션 | 중간 | 더블블링크 선택 시마다 기준점을 미세 업데이트하여 자세 변화에 자동 대응       |

#### 3.2 문제 B (고개 틀어짐 대응) — 이건 별개의 문제

MediaPipe의 근본 제약(얼굴 전체 인식 필수)에서 벗어나려면, 안구만 독립적으로 검출하는 방법이 필요하다. 이것이 원문 2번 방안(안구 전용 커스텀 모델)의 핵심 목적이다.

```
MediaPipe: 얼굴 전체 인식(필수) → 눈 찾기 → 홍채 좌표
           ↑ 여기서 실패하면 전부 실패

안구 전용:  이미지에서 바로 눈만 검출 → 홍채 위치 분류
           ↑ 얼굴 전체가 필요 없음
```

**판단 기준:** 실제 사용 환경에서 고개 틀어짐으로 인해 MediaPipe가 실패하는 경우가 자주 발생하는가? 자주 발생한다면 문제 B도 풀어야 하고, 가끔이거나 보호자가 자세를 잡아준다면 캘리브레이션 고도화만으로 충분하다.

### 4. YOLO로의 접근 가능성 검토

YOLO를 쓰는 이유는 정밀도 향상이 아니라, **얼굴 전체 인식 의존을 제거**하기 위함이다.

#### 4.1 YOLO와 MediaPipe의 차이

```
MediaPipe: 얼굴 전체 인식(필수) → 그 안에서 눈 → 홍채 좌표 (정밀한 점)
YOLO:      이미지에서 바로 눈 검출 → 홍채 검출 (바운딩 박스)
```

YOLO는 바운딩 박스(사각형)를 출력하므로, MediaPipe의 랜드마크(점)보다 **정밀도는 낮다.** 대신 얼굴 전체가 필요 없이 눈만 찾을 수 있다.

#### 4.2 YOLO를 활용한 조합 방법들

| 방법            | 구조                                         | 장점                  | 단점                    |
| --------------- | -------------------------------------------- | --------------------- | ----------------------- |
| YOLO 단독       | 눈/홍채 바운딩 박스 중심으로 비율 계산       | 간단                  | 바운딩 박스 정밀도 한계 |
| YOLO + OpenCV   | YOLO로 눈 크롭 → HoughCircles로 홍채 원 검출 | 정밀도 향상           | 조명/반사에 민감        |
| YOLO + CNN 분류 | YOLO로 눈 크롭 → CNN이 6-class 분류          | 이미지 기반 직접 판정 | 학습 데이터 필요        |

#### 4.3 핵심 판단

YOLO로 눈과 홍채를 검출한 이후의 계산은 MediaPipe와 동일하다(비율 계산 → 판정). 달라지는 건 좌표를 얻는 방법이지, 좌표를 얻은 후의 로직은 같다. YOLO 도입 여부는 "얼굴 전체 인식 의존을 벗어나야 하는가?"라는 질문에 대한 답으로 결정된다.

### 5. 핵심 판단 기준 정리 — "모델 학습이 필요한가?"

이 질문에 대한 답은 **입력 데이터가 무엇인가**에 달려 있다.

|                       | 좌표 기반 (1번 방안)      | 이미지 기반 (2번 방안) |
| --------------------- | ------------------------- | ---------------------- |
| 입력 데이터           | 숫자 2개 (iris_x, iris_y) | 픽셀 수천~수만 개      |
| 복잡도                | 낮음                      | 높음                   |
| 수식으로 풀 수 있는가 | 가능                      | 불가능                 |
| ML 모델의 부가가치    | 거의 없음                 | 있음                   |

"6분할에 모델 학습이 불필요하다"가 아니라, **"좌표 기반 접근에서는 모델 학습이 불필요하다"**가 정확한 표현이다. 이미지 기반으로 접근한다면 모델 학습이 필요하고, 그것이 2번 방안의 영역이다.

### 6. 추천 시스템의 전체 지도 — 세 가지 패러다임

추천 시스템이라는 큰 기술 분야를 공부하면서, 크게 세 가지 패러다임으로 분류된다는 것을 알게 되었다.

```
추천 시스템 (Recommendation Systems)
├── 1. 콘텐츠 기반 필터링 (Content-Based Filtering)
│     → "이 아이템과 비슷한 아이템을 추천"
├── 2. 협업 필터링 (Collaborative Filtering)
│     → "너와 비슷한 사용자가 좋아한 걸 추천"
└── 3. 하이브리드 (Hybrid)
      → 1 + 2를 결합
```

**콘텐츠 기반 필터링**은 아이템 자체의 속성을 분석하는 방식이라고 이해했다. 예를 들어 사용자가 "아이언맨"을 좋아하면, 아이언맨의 속성(액션, SF, 마블)과 비슷한 "어벤져스"를 추천하는 식이다. 다른 사용자의 데이터가 필요 없다는 장점이 있지만, 사용자가 이미 아는 종류만 계속 추천되는 "필터 버블" 문제가 있다는 것을 배웠다.

**협업 필터링**은 아이템의 내용은 보지 않고, 사용자들의 행동 패턴만으로 추천하는 방식이다. "너와 취향이 비슷한 사람이 좋아한 걸 너도 좋아할 것이다"라는 가정이 핵심이라고 이해했다. 이 방식은 다시 두 갈래로 나뉜다는 것을 알게 되었다.

- **메모리 기반(Memory-Based)**: 사용자-아이템 행렬 전체를 메모리에 올려놓고 실시간으로 유사도를 계산한다. User-based("나와 비슷한 사용자가 뭘 좋아했나?")와 Item-based("내가 좋아한 아이템과 비슷한 반응을 받은 아이템은?")로 나뉘는데, Item-based가 더 많이 쓰인다고 한다. 아이템 간의 관계가 사용자 추가보다 안정적이기 때문이라고 이해했다.
- **모델 기반(Model-Based)**: 행렬을 직접 들고 있지 않고 패턴을 모델로 학습시키는 방식이다. Matrix Factorization(거대한 행렬을 두 개의 작은 행렬로 분해), Neural CF(신경망으로 비선형 관계 포착) 등이 대표적이라고 배웠다. 다만 새 사용자나 새 아이템에 행동 데이터가 없으면 추천이 불가능한 Cold Start 문제가 존재한다는 것도 함께 알게 되었다.

여기서 중요한 깨달음이 있었다. 우리 프로젝트에서는 시간대·빈도·최근성·전이·보호자 설문 등 여러 시그널을 가중 합산하여 다음 표현을 예측하는 **가중 스코어링 방식**을 사용하고 있는데, 이것은 위 세 가지 분류 중 **어디에도 깔끔하게 분류되지 않는다**는 것이다. 표현의 카테고리를 쓰긴 하므로 콘텐츠 기반의 요소가 있지만, 다른 환자의 데이터를 쓰지 않으므로 협업 필터링은 아니다. 사용자 1명, 아이템 234개, 암묵적 피드백(선택 여부)이라는 조건이 전통적 추천의 가정(수천~수백만 사용자, 명시적 피드백)과 상당히 다르기 때문이라고 생각한다.

### 7. 세션 기반 추천과 우리 프로젝트의 위치

#### 7.1 세션 기반 추천이란

전통적 추천이 "이 사용자가 전반적으로 뭘 좋아하는가"를 묻는다면, 세션 기반 추천은 **"이 사용자가 지금 이 순간 뭘 원하는가"**를 묻는다는 것을 알게 되었다. 세션이란 한 번의 연속된 사용 구간을 의미하는데, 우리 프로젝트에서는 "앱 시작 → 표현 선택 → ... → 앱 종료"가 하나의 세션에 해당한다.

이 구분이 왜 중요한지 생각해보았다. 평소 액션 영화만 보는 사람이 오늘은 로맨스를 보고 싶을 수 있고, ALS 환자가 아침에 식사 관련 표현을 연속으로 선택하는 흐름이 있을 수 있다. 전체 이력만 보면 이런 "지금의 흐름"을 놓치게 된다고 이해했다.

#### 7.2 세션 기반 추천의 발전 단계

세션 기반 추천이 어떻게 발전해왔는지를 정리해보았다.

```
[1세대] 단순 통계 — 마르코프 체인
  → "직전 행동 → 다음 행동"의 전이 확률
  → 우리 프로젝트의 전이 시그널이 이것에 해당

[2세대] 딥러닝 RNN 계열 — GRU4Rec (2016)
  → 세션 내 행동 시퀀스를 GRU로 학습
  → 직전 1개가 아니라 세션 전체 흐름을 반영

[3세대] Attention 계열 — SASRec (2018), BERT4Rec (2019)
  → 세션 내 어떤 행동이 중요한지 가중치를 부여
  → Transformer의 세션 버전이라고 이해했다

[4세대] GNN 계열 — SR-GNN (2019)
  → 세션을 그래프로 모델링하여 아이템 간 복잡한 전이 관계를 표현
```

우리 프로젝트의 전이 시그널은 1세대 마르코프 체인에 해당한다. 마르코프 체인은 "다음 상태는 현재 상태에만 의존한다"는 가정인데, 이 가정의 한계가 분명하다는 것을 느꼈다. 1차 마르코프는 직전 1개만 보므로 흐름을 놓치고, 2차 이상으로 가면 234개 표현의 조합이 기하급수적으로 늘어나 데이터가 부족해진다. 다만 우리의 가중 스코어링은 이 한계를 다른 시그널(시간대, 빈도, 보호자 설문 등)로 보완하는 구조이므로, 전이 하나의 한계가 곧 전체 시스템의 한계는 아니라고 생각한다.

GRU4Rec 같은 딥러닝 모델은 세션 전체 흐름을 볼 수 있지만, 수십만~수백만 세션 데이터가 필요하다는 것을 배웠다. 우리 프로젝트는 환자 1명의 수십~수백 세션만 있으므로, 이런 모델을 학습시키면 과적합이 일어날 가능성이 높다고 판단했다.

#### 7.3 우리 프로젝트의 위치

이 발전 단계를 놓고 보면, 우리의 5-Signal 스코어링은 데이터 요구량이 적은 쪽에 위치한다는 것을 확인할 수 있었다.

```
데이터 요구량: 적음 ◄──────────────────────────────► 많음

규칙 기반    마르코프    MF/SVD    GRU4Rec    SASRec    BERT4Rec
               │
     ┌─────────┴─────────┐
     │  가중 스코어링        │
     │  규칙 + 마르코프     │
     │  + 도메인 특화 시그널 │
     └───────────────────┘
```

이것이 나쁜 위치가 아니라, 데이터가 극소량인 환경에서는 오히려 최적의 위치라고 생각한다. 실제로 프로토타입 평가에서 이 단순한 구조가 무작위 추천 대비 약 50배의 성능을 냈다. 데이터 규모에 맞는 복잡도를 선택하는 것이 중요하다는 것을 다시 느꼈다.

또한 우리 프로젝트에서 설계한 임베딩 기반 검색은 사실 추천보다는 "검색(Retrieval)"에 가깝다는 것을 깨달았다. 현재 상황을 텍스트로 변환하여 유사한 표현을 찾는 것이므로, 행동 예측이라기보다 유사도 계산에 해당한다. 이 임베딩 검색(Stage 1)과 빈도·최근성 보정 및 LLM 리랭킹(Stage 2)을 결합한 구조가 곧 2단계 아키텍처(빠른 모델로 후보 축소 → 정밀 모델로 재정렬)와 같은 패턴이라는 연결을 확인할 수 있었다.

### 8. RAG 심층 학습 — 사전 준비부터 질의까지

RAG(Retrieval-Augmented Generation)란 LLM이 응답을 생성할 때 외부 문서에서 관련 정보를 검색하여 프롬프트에 함께 넣어주는 기법이다. LLM은 학습 시점까지의 지식만 갖고 있으므로, 학습되지 않은 도메인 특화 지식에 대해서는 환각(Hallucination)을 일으킬 수 있는데, RAG는 이 한계를 외부 지식 주입으로 보완한다.

이전에 이 기본 개념(임베딩 → 검색 → 증강 → 생성)을 학습했고, 우리 프로젝트에서는 표현 추천보다는 간병인 가이드 기능에 RAG가 적합하다는 설계 판단을 했다. 이번에는 RAG 자체를 기술적으로 더 깊이 공부해보았다.

#### 8.1 사전 준비 단계 — 문서를 벡터 DB에 넣기

RAG를 구축할 때 질문이 들어오기 전에 먼저 문서를 준비해둬야 한다는 것을 배웠다. 이 사전 준비 과정이 실제로는 RAG 구축 작업의 상당 부분을 차지한다고 한다.

```
[원본 문서]              [청크 분할]            [임베딩]            [벡터 DB 저장]
체위변경_가이드.pdf  →  의미 단위로 분할  →  각 청크를 벡터로 변환  →  pgvector에 저장
```

**(1) 청킹(Chunking) — 왜 문서를 잘라야 하는가**

LLM의 프롬프트에는 토큰 제한이 있기 때문에 문서를 통째로 넣을 수 없다. 또한 통째로 넣더라도 관련 없는 내용이 대부분이어서 LLM의 주의가 분산된다는 것을 이해했다. 그래서 문서를 작은 조각(청크)으로 잘라서 저장하고, 질문이 들어오면 관련된 청크만 골라서 프롬프트에 넣는 구조라는 것을 알게 되었다.

청킹 전략에는 여러 가지가 있다는 것을 배웠다.

| 전략               | 방식                                   | 장점            | 단점                                     |
| ------------------ | -------------------------------------- | --------------- | ---------------------------------------- |
| 고정 크기          | 500자마다 분할                         | 단순함          | 문장 중간에서 잘려 의미가 파괴될 수 있음 |
| 고정 크기 + 오버랩 | 500자마다 분할하되 앞뒤 100자씩 겹침   | 문맥 유지       | 중복 저장, 검색 시 중복 결과             |
| 구분자 기반        | 제목, 소제목, 빈 줄 등으로 분할        | 의미 단위 보존  | 청크 크기 불균일                         |
| 의미 기반          | 임베딩 유사도가 급변하는 지점에서 분할 | 가장 자연스러움 | 구현 복잡, 비용 높음                     |

우리 프로젝트의 간병 가이드 문서는 구조화된 매뉴얼(제목-소제목-절차 형태)이므로, 구분자 기반이 가장 적합하지 않을까 생각한다. **청킹 전략의 차이가 RAG 성능을 크게 좌우한다**는 점이 인상적이었다. 같은 문서, 같은 임베딩 모델, 같은 LLM을 써도 청킹을 어떻게 하느냐에 따라 검색 결과가 완전히 달라질 수 있다는 것이다.

**(2) 임베딩(Embedding) — 텍스트를 벡터로 변환**

각 청크를 고정 길이의 숫자 배열(벡터)로 변환하는 과정이다. 이 벡터가 텍스트의 의미를 수학적으로 표현한 것이라고 이해했다. 임베딩 모델의 선택이 검색 품질을 결정한다는 것을 배웠는데, 우리 프로젝트의 경우 간병 가이드가 한국어이므로 한국어 성능이 중요하다. OpenAI의 text-embedding-3 시리즈, 오픈소스인 multilingual-e5-large, 한국어 특화인 KoSimCSE 등이 후보가 될 수 있다고 파악했다.

**(3) 벡터 DB 저장**

여기서 중요한 것은 벡터 DB에는 벡터만 저장하는 것이 아니라 **원본 텍스트도 함께 저장해야 한다**는 것이다. 벡터는 검색용이고, 실제로 LLM에 넘기는 것은 원본 텍스트이기 때문이다. 이 점을 놓치기 쉽겠다는 생각이 들었다.

#### 8.2 질의 단계 — 검색에서 생성까지

사전 준비가 끝난 후 실제 질의가 들어오는 흐름을 정리해보았다.

```
환자가 "목이 아파요" 선택
    │
    ▼
[1] 질의 구성: "목이 아파요"를 검색 가능한 질의로 변환
[2] 질의 임베딩: 질의를 벡터로 변환 (사전 준비 때와 같은 모델 사용)
[3] 유사도 검색: 벡터 DB에서 코사인 유사도가 높은 청크 Top-K개 반환
[4] 프롬프트 증강: 검색된 청크를 LLM 프롬프트에 삽입
[5] LLM 생성: 검색된 청크를 참고하여 간병 지침 생성
```

특히 [4] 프롬프트 증강 단계가 과소평가되기 쉽다는 것을 느꼈다. 검색된 청크를 LLM에 그냥 던지는 것과, 역할 정의·출처 명시·출력 형식·안전 장치를 갖춘 프롬프트로 구성하는 것은 생성 품질에서 큰 차이가 날 것이라고 이해했다.

간병/의료 도메인에서는 프롬프트의 안전 장치가 특히 중요하다고 생각한다. "가이드에 없는 내용은 '의료진에게 문의하세요'로 안내", "의학적 진단이나 약물 관련 조언 금지" 같은 지시를 명시적으로 포함해야, LLM이 가이드에 없는 내용을 그럴듯하게 생성하는 할루시네이션을 방지할 수 있을 것이라고 판단했다.

### 9. RAG 성능을 좌우하는 핵심 요소들

RAG를 구축하면 "왜 엉뚱한 결과가 나오는가"라는 문제에 반드시 부딪힌다는 것을 배웠다. 원인을 세 가지로 분류할 수 있다고 이해했다.

```
[1] 검색 실패 — 관련 청크를 못 찾음
    ├── 청킹이 잘못됨 (의미가 잘린 청크)
    ├── 임베딩 모델이 도메인에 약함
    └── 질의와 문서의 표현 차이 (어휘 격차)

[2] 검색은 성공했지만 순위가 잘못됨
    ├── 관련 청크가 Top-K 밖에 있음
    └── 유사하지만 관련 없는 청크가 상위에 올라옴

[3] LLM 생성 실패
    ├── 프롬프트 설계 문제
    ├── 청크가 너무 많아 핵심을 놓침
    └── LLM이 청크를 무시하고 자체 지식으로 답변
```

이 중 우리 프로젝트에서 가장 주의해야 할 것은 [1]의 **어휘 격차(vocabulary gap)** 문제라고 생각한다. 환자가 "목이 아파요"를 선택하면, 간병 가이드에는 "경부 통증", "인후 불편감", "흡인 관련 증상" 같은 의료/간병 용어로 쓰여 있을 가능성이 높다. 환자의 일상 표현과 가이드 문서의 전문 용어 사이에 격차가 존재하면, 임베딩 유사도가 낮아져서 관련 청크를 놓칠 수 있다는 것이다.

이를 해결하는 방법으로 **쿼리 변환(Query Transformation)**이 있다는 것을 배웠다. 질의를 검색에 유리한 형태로 변환하는 것인데, 예를 들어 "목이 아파요" → "목 통증 경부 통증 인후 불편감 흡인 관련 간병 조치"로 변환한 후 검색하면 더 정확한 청크가 상위에 올라올 수 있다고 이해했다.
