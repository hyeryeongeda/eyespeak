### Keep — 계속 유지할 것

- **ML을 쓰지 않는 이유를 먼저 정리한 뒤에 대안 설계에 착수한 것.** 규칙 기반을 선택하기 전에 ML 추천이 왜 부적합한지를 데이터 규모, 콜드 스타트, 오추천 비용 측면에서 정리한 것은 좋은 습관이었다고 생각한다. 기술 선택의 근거를 먼저 확보하는 태도는 유지하고 싶다.

---

### Problem — 문제가 된 것

- **"무시 = 해결" 전제의 적절성을 검증하는 데 시간이 걸린 것.** 환자가 활성 대화를 무시하고 다른 주제로 넘어갔을 때 이전 대화를 해결로 간주하는 규칙이 정말 합리적인지, 아니면 단순히 구현 편의를 위한 타협인지 구분하는 데 고민이 필요했다. 결론적으로는 합리적이라고 판단했지만, 전제를 세울 때 "이건 설계적 결정인가, 구현 편의인가"를 더 빨리 구분하는 훈련이 필요하다고 느꼈다.
- **직접 입력(자유 텍스트)을 상태 추적에서 제외하는 결정을 내리면서, 이 결정의 한계를 문서화하지 않고 넘어갈 뻔한 것.** 제외 자체는 합리적인 판단이었지만, "어떤 상황에서 이 제외가 문제가 될 수 있는가"를 명시하지 않으면 나중에 요구사항이 바뀌었을 때 왜 이 결정을 했는지 추적이 어려워진다. 설계 결정에는 항상 한계 명시가 따라와야 한다는 점을 다시 느꼈다.
- **주제 선정 전에 이게 얼마나 힘든 주제인지 미리 공부를 좀 할 것** 주제 선정 단계에서, 주제 별로 어느 부분이 핵심인지, 그리고 이 핵심 기능을 구현하려면 어느 정도 수준의 노력이 필요한지는 파악해야한다.

## 금일 학습한 것

### 추천 로직 재설계 — 환자-보호자 간 대화를 유기적으로 이어가는 방법

기존 로직에 대한 피드백을 받았다. 핵심 질문은 **"환자가 표현을 선택한 뒤, 보호자와의 대화가 유기적으로 이어지는가?"**였다. 기존의 방식은 환자가 어떻게 해야 원하는 표현에 빠르게 접근할 수 있을까에 대해서만 고민 했지만, 환자가 "어깨 아파"를 선택한 뒤에 보호자가 대응하고, 환자가 다시 피드백하는 **유기적 흐름** 자체를 설계하지는 못했다.

---

### 1. 왜 ML 추천이 아닌 규칙 기반인가

맥락 추천 시스템이라고 하면 ML 기반 모델을 떠올렸다. 하지만 이 프로젝트의 조건을 하나씩 따져보니, ML 추천이 적합하지 않다는 나름의 결론에 도달하게 되었다. 그 근거를 정리해본다.

**첫째, 사용자 기반이 극히 작다.** 협업 필터링은 "비슷한 사용자가 좋아한 것을 추천"하는 방식인데, 사용자가 1명(혹은 극소수)인 환경에서는 이 가정 자체가 성립하지 않는다. 개인별 데이터를 충분히 수집할 수도 없다.

**둘째, 콜드 스타트를 허용할 수 없다.** ML 모델은 데이터를 축적하면서 학습하는 시간이 필요하다. 그런데 잘못된 추천을 몇 주간 보여주며 학습할 여유가 없다. 앱을 설치한 첫날부터 합리적인 추천이 나와야 한다.

**셋째, 오추천의 비용이 일반적 상황에 비해 매우 높다.** 일반적인 추천 시스템에서 오추천은 "사용자가 무시하면 그만"이지만, 안구 추적 환경에서 오추천은 환자가 원하는 표현을 찾기 위해 눈을 더 사용 해야 한다는 뜻이고, 이것이 물리적 피로로 직결된다.

**넷째, 도메인 지식이 충분히 구조화되어 있다.** ALS 환자의 일반적인 생활 패턴은 의학적으로 잘 문서화되어 있다. 개인 데이터를 기반으로 패턴을 예측하는 것이 아니라, ALS 환자의 일반 습관(general habits)을 기반으로 규칙을 설계하는 것이 더 합리적이라고 판단했다.

정리하면, ML이 힘을 발휘하려면 "데이터가 충분하고, 패턴이 복잡하며, 시행착오를 허용할 수 있는" 환경이 필요한데, 이 프로젝트는 세 조건을 모두 충족하지 않는다. 따라서 서버에서 처리하는 규칙 기반으로 접근하는 것이 더 적합하지 않을까 생각했다.

---

### 2. 상태 머신 설계 — 활성 대화와 표현 타입

이 구조를 떠올린 계기가 있다. 공통 프로젝트에서 프론트엔드를 담당하면서 다뤘던 상태 관리 개념이 갑자기 머릿속에 떠올랐다. 컴포넌트의 상태가 바뀌면 화면이 반응하듯, 환자의 선택에 따라 시스템의 상태가 바뀌고 다음 슬롯이 결정되는 구조를 만들면 되지 않을까 싶었다. 핵심 개념은 **활성 대화**라는 상태 단위를 도입한 것이다.

#### 2.1 활성 대화

환자가 표현을 선택하면, 시스템은 활성 대화를 생성한다. 활성 대화는 세 가지 정보를 가진다.

| 속성 | 설명                                 | 예시                       |
| ---- | ------------------------------------ | -------------------------- |
| 주제 | 어떤 카테고리의 표현인지             | 통증, 수분, 온도           |
| 상태 | 해결 여부                            | 미해결 / 해결됨            |
| 표현 | 환자가 마지막으로 선택한 구체적 표현 | "물 가져와줘", "어깨 아파" |

다음 화면의 6개 슬롯은 활성 대화의 '표현'을 키로, 미리 정의된 응답 세트를 불러와 구성한다. 즉, 환자가 선택한 표현이 다음 화면의 내용을 결정하는 구조다.

#### 2.2 표현 타입에 따른 슬롯 전환

모든 표현이 같은 후속 흐름을 가지는 것은 아니다. 각 표현은 타입을 가지며, 타입에 따라 다음 슬롯의 성격이 달라진다.

```
[요청] "물 가져와줘", "마사지해줘"
  → 다음 슬롯: 응답 모드 (고마워, 됐어, 더 줘...)

[상태 보고] "어깨 아파", "추워"
  → 다음 슬롯: 관련 케어 요청 (마사지해줘, 이불 덮어줘...)

[응답] "왼쪽으로 더", "아직 아파"
  → 다음 슬롯: 후속 표현

[해결] "이제 괜찮아", "됐어"
  → 활성 대화 소멸, 홈 복귀
```

이 설계의 의도는 대화의 맥락을 유지하는 것이다. 환자가 "어깨 아파"를 선택했을 때, 다음 화면에 "물 가져와줘"가 뜨면 안 된다. "마사지해줘", "파스 붙여줘" 같은 관련 케어 요청이 나와야 자연스러운 대화 흐름이 이어진다.

#### 2.3 패턴 그룹화

하지만, 바로 문제에 마주하게 되었다. 개별 표현마다 후속 슬롯을 매핑하면 매핑 테이블이 너무 커지고, 유지보수가 불가능해진다.
그런데 실제로 따져보니, "어깨 아파", "허리 아파", "다리 아파"는 전부 **'상태보고 + 통증'**이라는 동일한 패턴이고, 후속 슬롯도 동일하다.
모든 필수 소통의 표현을 일일히 설정할 필요 없이, 충분히 중복되는 부분이 있을 것이라 생각이 들었다.
(솔직히, 중복되지 않더라도 다 하드코딩 해버릴까 고민했다...ㅎㅎ)

#### 2.4 슬롯 배분 우선순위

6개 슬롯을 채우는 우선순위는 다음과 같이 정리했다.

```
[1순위] 활성 대화가 있으면 → 해당 표현의 응답 세트 (최우선)
[2순위] 활성 대화가 없으면 → 시간 기반 일반 습관 추천 + 보호자 등록 루틴
```

1순위가 최우선인 이유는, 환자가 이미 대화를 시작한 상태에서 맥락 없는 추천이 끼어들면 혼란을 줄 수 있기 때문이다.
활성 대화가 없을 때만 시간대 기반 습관 추천이 작동하고, 안전망 슬롯은 어떤 상황에서든 접근 가능하도록 항상 포함된다.

### 3. 전제 조건과 트레이드오프

이 로직은 두 가지 전제 위에서 동작한다.

#### 전제 1: 상태 추적은 카테고리 표현에서만 작동한다

우리 프로그램에는 크게 두 가지 입력 경로가 있다. 카테고리 기반 **'필요소통'**과 자유 텍스트 **'직접 입력'**이다. 직접 입력은 상태에 반영하지 않고, 보호자에게 전달만 한다.

이 결정의 근거는 이렇다. 자유 텍스트를 상태에 매핑하려면 파싱을 하거나 AI(LLM)가 필요하다. "목 아파"와 "목이 좀 불편해"가 같은 의미인지 판별하고, 이를 '통증' 카테고리에 매핑해야 한다. 이것을 직접 파인튜닝 등의 방식으로 구현하는 것은 배보다 배꼽이 커지는 기술 과제라고 생각했고, 기존의 LLM을 호출 하더라도, 100% 확실하게 매핑할 수 없다는 점이 몹시 신경쓰였다. 파싱 실패 시 오히려 잘못된 상태 추적으로 이어질 수 있고, 이는 내가 설계한 로직이 다 박살나는 결과를 초래한다.

또한 안구 추적 특성상 키보드 직접 입력은 피로도가 매우 높기 때문에, 대부분의 사용은 필요소통에서 이루어질 것으로 예상된다. **필요소통 = 시스템이 맥락을 추적하는 영역, 직접 입력 = 예상하지 못한 상황의 안전망**으로 역할을 분리하여 생각하고자 하였다.

**트레이드오프:** 직접 입력으로 전달된 내용은 추천 로직에 반영되지 않는다. 환자가 직접 입력을 자주 사용하는 패턴이 있다면, 그 패턴은 시스템이 학습하지 못한다. 이 한계는 인지하되, 현재 단계에서는 수용 가능하다고 판단했다.

#### 전제 2: 무시 = 해결

환자가 활성 대화가 있는 상태에서 다른 주제의 표현을 선택하면, 이전 대화는 해결된 것으로 간주한다.

이 부분 때문에 그냥 이 로직 폐기해버릴까 생각했다. 환자가 후속 대답을 안했을 때, 해결된건지 안 된건지 어떻게 아는가? 하지만 곰곰히 생각해보니, 시스템이 현실에서 무슨 일이 일어났는지 모든 부분을 완벽히 파악할 수도 없고, 그럴 필요도 딱히 없다라는 생각이 들었다. 환자가 활성 대화가 있는 상태에서는 분명 어떻게 해서든 지금의 상태를 해결하려고 할 것이라고 생각했다. 이런 환자가 갑자기 다른 표현을 한다? 앞의 문제는 해결했다! 라고 판단할 수 있을 것이라 생각했다.

또한, 환자가 홈으로 복귀하는 것만으로는 해결로 간주하지 않는다. 즉, 환자가 "어깨 아파"를 선택한 뒤 홈으로 돌아가면, 홈 화면에 "아직 아파?", "괜찮아졌어?" 같은 팔로업이 남아 있다. 명시적으로 다른 주제를 선택하거나, "괜찮아" 같은 해결 표현을 선택해야만 활성 대화가 소멸하도록 설계하였다.

**트레이드오프:** 실제로는 해결되지 않았지만 다른 긴급한 상황이 생겨 새로운 표현을 한 경우, 이전 대화가 자동으로 해결 처리된다. 이건... 진짜 어떻게 해야할까..??

### 4. 시나리오 검증

위 로직이 실제 사용 흐름에서 동작하는지, 예린이가 가져온 시나리오로 검증해보았다.

---

**Step 1 — 기상 루틴: 기분 체크 + 일정 확인**

```
[아침 기상] → 홈 화면
  슬롯: 기분 체크, 일정 확인, 수분 섭취 (시간 기반 추천) + 보호자 등록 루틴
```

환자가 "기분이 좋음"에 체크하고, 일정 알림을 확인한다.
→ 기분 필드가 '좋음'으로 변경된다. 기분 체크는 해결형 표현이므로 활성 대화를 생성하지 않는다.
→ 홈 슬롯에서 "기분 체크하기"가 사라지고, 다른 시간별 루틴 기반 추천으로 대체된다.

---

**Step 2 — 즐겨찾기에서 "물 가져와줘" 요청**

```
[환자] 즐겨찾기 → "물 가져와줘" 선택
  활성 대화 ⇒ [주제: 수분, 상태: 미해결, 표현: 물 가져와줘]
  보호자에게 "물 가져와줘" 전달
  슬롯 전환 (요청 타입 → 응답 모드): 고마워 | 부족해 | 더 줘 | 됐어
```

"물 가져와줘"는 요청 타입이므로, 다음 슬롯은 즉시 응답 모드로 전환된다.

---

**Step 3 — 보호자가 "물 더줄까?" → 환자가 "됐어"**

```
[환자] "됐어" 선택
  활성 대화 ⇒ [주제: 수분, 상태: 해결됨] → 상태 소멸
  홈으로 복귀
```

활성 대화의 상태가 미해결이므로, 표현 "물 가져와줘"에 매핑된 응답 세트가 슬롯에 노출되어 있다. 환자가 "됐어"를 선택하면 활성 대화가 소멸하고 홈으로 복귀한다.

---

**Step 4 — 필요소통: "어깨 아파" → "마사지해줘"**

```
[환자] 필요소통 → "어깨 아파" 선택
  활성 대화 ⇒ [주제: 통증, 상태: 미해결, 표현: 어깨 아파]
  슬롯 전환 (상태 보고 타입 → 케어 요청): 마사지해줘 | 자세 바꿔줘 | 약 줘

[환자] "마사지해줘" 선택
  활성 대화 갱신 ⇒ [주제: 통증, 상태: 미해결, 표현: 마사지해줘]
  보호자에게 "어깨가 아파요. 마사지해주세요" 전달
  슬롯 전환 (요청 타입 → 응답 모드): 편해 | 아직 아파 | 왼쪽으로 더 | 오른쪽으로 더
```

"어깨 아파"는 상태 보고 타입이므로 케어 요청 세트가 나오고, "마사지해줘"는 요청 타입이므로 다시 응답 모드로 전환된다. 두 표현이 합쳐져 보호자에게 하나의 문장으로 전달된다.

---

**Step 5 — 보호자가 "지금은 편해?" → 환자가 "왼쪽으로 더"**

```
[환자] "왼쪽으로 더" 선택
  활성 대화 갱신 ⇒ [주제: 통증, 상태: 미해결, 표현: 왼쪽으로 더]
  보호자에게 "왼쪽으로 조금 더 마사지해주세요" 전달
  슬롯 전환 (응답 타입 → 후속 표현): 편해 | 아직 아파 | 반대쪽도 해줘 | 됐어

[환자] 후속 선택 없이 홈으로 복귀
  → 활성 대화 유지 (해결 표현을 선택하지 않았으므로)
```

보호자가 육성으로 물었든 앱으로 물었든, 환자 화면에는 이미 응답 가능한 슬롯이 있다. 환자가 홈으로 복귀해도 활성 대화는 소멸하지 않는다.

---

**Step 6 — 3시간 뒤, 보호자가 "아까 어깨 아픈 건 괜찮아?"**

```
[3시간 뒤] 홈 화면
  활성 대화 유지 중: [주제: 통증, 상태: 미해결, 표현: 왼쪽으로 더]
  슬롯: 편해 | 아직 아파 | 반대쪽도 해줘 | 됐어 (이전과 동일)
```

활성 대화가 아직 살아있으므로, 홈 화면에 이전과 동일한 응답 슬롯이 유지되어 있다. 다른 선택을 하지 않았기 때문에 슬롯 구성은 그대로다. 보호자가 육성으로 물어봤어도, 환자 화면에는 이미 응답 가능한 슬롯이 있다.

---

**Step 7 — 환자가 "편해"**

```
[환자] "편해" 선택
  활성 대화 ⇒ [주제: 통증, 상태: 해결됨] → 상태 소멸
  보호자에게 "이제 괜찮아요" 전달
  통증 관련 슬롯 전부 소멸, 홈이 시간 기반 추천으로 복귀
```

해결 표현을 선택하면 비로소 활성 대화가 소멸한다. 3시간이 지났어도 팔로업이 유지되어 있었기 때문에, 보호자의 질문에 환자가 바로 응답할 수 있었다.

---

### 5. 설계를 돌아보며

이 전체 로직을 구성하는 요소는 세 가지뿐이다. **상태 관리**(활성 대화의 생성·갱신·소멸), **매핑 테이블**(패턴 그룹 → 응답 세트), **시간대 별 환자 루틴**(시간 기반 습관 추천). AI 모델도, 학습 데이터도, 추론 서버도 없다.

이것이 이 설계의 강점이자 한계라고 생각한다. 강점은 명확하다. 첫날부터 동작하고, 동작 원리를 설명할 수 있으며, 오작동 시 원인을 추적할 수 있다. 한계도 명확하다. 매핑 테이블에 정의되지 않은 흐름은 처리할 수 없고, 개인의 고유한 패턴을 학습하지 못한다.

이 설계를 고민하는 내내, 결국 하나의 질문으로 돌아왔다. **환자는 무엇을 원할까.** 이 질문을 수백 번은 한 것 같다.

내가 내린 결론은, 내 몸이 불편한 걸 보호자가 알아봐 줬으면.. 이것이었다. 인간이 가장 쉽게 불편함을 느끼는 순간은 자기 몸이 불편할 때라고 생각한다. 조금만 거슬려도 엄청나게 신경 쓰이는데, 이걸 스스로 대처하지 못하는 ALS 환자는 얼마나 스트레스를 받을지 상상 조차 되지 않는다. 이런 분들에게 가장 필요한 건, 육체적 불편함을 빠르게 전달하고 빠르게 해결하는 것이다. 이렇게 생각하니, 다른 모든 것들은 부차적이었다. 필수 소통. 이것만 제대로 추천 로직에 녹여낸다면 충분히 가치가 있다고 생각했다.

그리고 이 고민을 하면서 가장 크게 느낀 건, 화려한 AI 기술이나 RAG를 도입하는 것보다 중요한 게 있다는 것이었다. 환자를 위한 고민을 진심으로 했다는 것. 이 분들을 어떻게 도울 수 있을지 그것만을 생각했다는 것. 그리고 그 고민 끝에 내가 무엇이라도 해결책을 제안해볼 수 있었다는 것에서 많은 뿌듯함을 느꼈다. 이 프로젝트의 결과가 어떻게 되든, 이 경험만으로도 최고의 프로젝트였다고 생각할 수 있을 것 같다.
