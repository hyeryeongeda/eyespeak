# 회원가입/로그인 코드 설명

## 전체 흐름 요약

```
프론트엔드 → AuthController → AuthService → DB(User, Guardian, Matching)
                                    ↕
                               JwtProvider (토큰 생성/검증)
                               JwtFilter  (매 요청마다 토큰 확인)
```

---

## 1. 요청이 들어오는 순서 (계층 구조)

Spring Boot는 **Controller → Service → Repository** 3계층으로 나뉜다.

| 계층 | 역할 | 우리 코드 |
|---|---|---|
| Controller | HTTP 요청 받기, 응답 보내기 | `AuthController.java` |
| Service | 비즈니스 로직 (검증, 생성, 변환) | `AuthService.java` |
| Repository | DB 접근 (CRUD) | `UserRepository.java` 등 |

---

## 2. DTO (Data Transfer Object)

프론트에서 보낸 JSON을 Java 객체로 변환하는 그릇.

### GuardianSignupRequest.java — 보호자 회원가입 요청

```java
public class GuardianSignupRequest {

    @NotBlank(message = "이메일은 필수입니다")
    @Email(message = "이메일 형식이 올바르지 않습니다")
    private String email;

    @NotBlank(message = "이름은 필수입니다")
    private String name;

    @NotBlank(message = "비밀번호는 필수입니다")
    @Size(min = 8, message = "비밀번호는 8자 이상이어야 합니다")
    private String password;
}
```

**어노테이션 정리:**
- `@NotBlank` → 빈 문자열이면 400 에러 (입력값 검증)
- `@Email` → 이메일 형식인지 확인 (abc@def.com)
- `@Size(min = 8)` → 최소 8글자
- `@Getter` → Lombok이 `getEmail()`, `getName()` 등 자동 생성
- `@NoArgsConstructor` → 빈 생성자 자동 생성 (Spring이 JSON → 객체 변환할 때 필요)

### LoginRequest.java — 로그인 요청

```java
public class LoginRequest {
    private String identifier;  // 이메일
    private String password;
    private String role;        // "GUARDIAN" 또는 "PATIENT"
}
```

> **참고:** `email`이 아니라 `identifier`인 이유 — 프론트에서 필드 이름을 이렇게 보내기로 한 것.

### AuthResponse.java — 로그인/회원가입 성공 응답

```java
public class AuthResponse {
    private String accessToken;
    private String refreshToken;
    private AuthUserDto user;

    public static class AuthUserDto {
        private Long id;
        private String role;
        private String name;
        private String email;
    }
}
```

프론트가 받는 JSON:
```json
{
  "accessToken": "eyJhbG...",
  "refreshToken": "eyJhbG...",
  "user": { "id": 3, "role": "GUARDIAN", "name": "김싸피", "email": "ssafy@ssafy.com" }
}
```

## 3. Controller — 요청 받기

```java
@RestController          // 이 클래스가 API 엔드포인트임을 선언
@RequestMapping("/auth") // /api/v1/auth/** 로 들어오는 요청 처리
@RequiredArgsConstructor // final 필드를 받는 생성자 자동 생성 (DI용)
public class AuthController {

    private final AuthService authService;  // Service 주입
```

### 보호자 회원가입 엔드포인트

```java
@PostMapping("/sign-up/guardian")
public ResponseEntity<ApiResponse<AuthResponse>> signupGuardian(
        @Valid @RequestBody GuardianSignupRequest request) {
    AuthResponse response = authService.signupGuardian(request);
    return ResponseEntity.status(HttpStatus.CREATED).body(ApiResponse.created(response));
}
```

**한 줄씩 해석:**
1. `@PostMapping("/sign-up/guardian")` → POST /api/v1/auth/sign-up/guardian 매핑
2. `@Valid` → DTO의 `@NotBlank`, `@Email` 등 검증 실행. 실패 시 자동 400 에러
3. `@RequestBody` → JSON body를 `GuardianSignupRequest` 객체로 변환
4. `authService.signupGuardian(request)` → Service에 위임
5. `ResponseEntity.status(HttpStatus.CREATED)` → HTTP 201 응답
6. `ApiResponse.created(response)` → `{"code":"CREATED", "message":"...", "data": {...}}` 포맷

### 로그인 엔드포인트

```java
@PostMapping("/login")
public ResponseEntity<ApiResponse<AuthResponse>> login(
        @Valid @RequestBody LoginRequest request) {
    AuthResponse response = authService.login(request);
    return ResponseEntity.ok(ApiResponse.ok(response));  // HTTP 200
}
```

### 로그아웃

```java
@PostMapping("/log-out")
public ResponseEntity<ApiResponse<Void>> logout() {
    return ResponseEntity.ok(ApiResponse.ok());
}
```

> JWT는 서버에 세션을 저장하지 않으므로 (stateless), 서버에서 할 일이 없다.
> 프론트에서 저장된 토큰을 삭제하면 로그아웃 완료.

## 4. Service — 비즈니스 로직

```java
@Service                              // Spring Bean 등록
@RequiredArgsConstructor              // final 필드 생성자 주입
@Transactional(readOnly = true)       // 기본적으로 읽기 전용 (SELECT만)
public class AuthService {

    private final UserRepository userRepository;
    private final GuardianRepository guardianRepository;
    private final PasswordEncoder passwordEncoder;    // BCrypt 암호화
    private final JwtProvider jwtProvider;             // JWT 토큰 생성/검증
```

### 보호자 회원가입 흐름

```java
@Transactional  // 이 메서드는 쓰기(INSERT)도 하므로 readOnly 해제
public AuthResponse signupGuardian(GuardianSignupRequest request) {

    // 1단계: 이메일 중복 체크
    if (userRepository.existsByLoginId(request.getEmail())) {
        throw new BusinessException(ErrorCode.DUPLICATE_EMAIL);
        // → {"code":"AUTH-204","message":"이미 등록된 이메일입니다"} 응답
    }

    // 2단계: User 엔티티 생성 + DB 저장
    User user = User.builder()
            .loginId(request.getEmail())
            .password(passwordEncoder.encode(request.getPassword()))  // BCrypt 암호화!
            .name(request.getName())
            .role(Role.GUARDIAN)
            .build();
    userRepository.save(user);  // INSERT INTO user ...

    // 3단계: Guardian 프로필 생성 + DB 저장
    Guardian guardian = Guardian.builder()
            .user(user)         // User와 1:1 연결
            .build();
    guardianRepository.save(guardian);  // INSERT INTO guardian ...

    // 4단계: JWT 토큰 발급 후 응답
    return buildAuthResponse(user);
}
```

**핵심 포인트:**
- `passwordEncoder.encode()` → 비밀번호를 절대 평문으로 저장하지 않는다. BCrypt 해시.
- `User`와 `Guardian`은 별도 테이블. User = 로그인 계정, Guardian = 보호자 프로필.
- `@Transactional` → 중간에 에러 나면 전부 롤백 (User만 저장되고 Guardian은 안 된 상태 방지)

### 로그인 흐름

```java
public AuthResponse login(LoginRequest request) {

    // 1단계: role 변환 ("caregiver" → GUARDIAN, "PATIENT" → PATIENT)
    String rawRole = request.getRole().toUpperCase();
    Role role;
    if ("CAREGIVER".equals(rawRole) || "GUARDIAN".equals(rawRole)) {
        role = Role.GUARDIAN;
    } else if ("PATIENT".equals(rawRole)) {
        role = Role.PATIENT;
    } else {
        throw new BusinessException(ErrorCode.LOGIN_FAILED);
    }

    // 2단계: 이메일로 User 조회
    User user = userRepository.findByLoginId(request.getIdentifier())
            .orElseThrow(() -> new BusinessException(ErrorCode.LOGIN_FAILED));
    // → 없으면 "이메일 또는 비밀번호가 일치하지 않습니다"

    // 3단계: 비밀번호 검증
    if (!passwordEncoder.matches(request.getPassword(), user.getPassword())) {
        throw new BusinessException(ErrorCode.LOGIN_FAILED);
    }
    // matches(평문, 해시) → 내부적으로 BCrypt 비교

    // 4단계: role 검증 (보호자 계정으로 환자 로그인 시도 방지)
    if (user.getRole() != role) {
        throw new BusinessException(ErrorCode.LOGIN_FAILED);
    }

    return buildAuthResponse(user);
}
```

**보안 포인트:** 이메일 틀림 / 비밀번호 틀림 / role 틀림 모두 같은 에러 메시지(`LOGIN_FAILED`)를 쓴다. 이유: 해커가 "이메일은 맞고 비밀번호만 틀렸구나" 같은 정보를 얻지 못하도록.

### 환자 회원가입 흐름

```java
@Transactional
public PatientSignupResponse signupPatient(PatientSignupRequest request) {

    // 1단계: 팀코드로 Matching 조회
    Matching matching = matchingRepository.findByInviteCode(request.getTeamCode())
            .orElseThrow(...);

    // 2단계: 이미 환자가 연결되어 있는지 확인
    if (matching.getPatient().getUser() != null) {
        throw new BusinessException(ErrorCode.PATIENT_ALREADY_EXISTS);
    }

    // 3단계: User 생성 (role = PATIENT)
    User user = User.builder()
            .loginId(request.getLoginId())
            .password(passwordEncoder.encode(request.getPassword()))
            .name(request.getName())
            .role(Role.PATIENT)
            .build();
    userRepository.save(user);

    // 4단계: Patient에 User 연결 + Matching 상태 변경
    matching.getPatient().linkUser(user);  // patient.user_id = user.id
    matching.link();                       // status = LINKED
}
```

> 보호자가 먼저 환자 정보를 등록하면 Patient(user_id=NULL) + Matching(PENDING)이 생긴다.
> 환자가 팀코드로 가입하면 Patient에 User가 연결되고 Matching이 LINKED로 바뀐다.

### JWT 토큰 발급 (공통)

```java
private AuthResponse buildAuthResponse(User user) {
    String accessToken = jwtProvider.createAccessToken(user.getId(), user.getRole());
    String refreshToken = jwtProvider.createRefreshToken(user.getId(), user.getRole());

    return AuthResponse.builder()
            .accessToken(accessToken)
            .refreshToken(refreshToken)
            .user(AuthResponse.AuthUserDto.builder()
                    .id(user.getId())
                    .role(user.getRole().name())
                    .name(user.getName())
                    .email(user.getLoginId())
                    .build())
            .build();
}
```

## 5. User 엔티티 — DB 테이블 매핑

```java
@Entity                                    // JPA 엔티티 (DB 테이블과 매핑)
@Table(name = "`user`")                    // 테이블명 user (백틱: MySQL 예약어 회피)
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)  // JPA 필수. 외부에서 new User() 방지
public class User extends BaseEntity {     // BaseEntity → createdAt, updatedAt 자동 관리

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)  // AUTO_INCREMENT
    private Long id;

    @Column(nullable = false, unique = true)  // NOT NULL, UNIQUE
    private String loginId;

    @Column(nullable = false)
    private String password;                  // BCrypt 해시값 저장

    @Column(nullable = false)
    private String name;

    @Enumerated(EnumType.STRING)              // DB에 "GUARDIAN", "PATIENT" 문자열로 저장
    @Column(nullable = false)
    private Role role;

    @Column(nullable = false)
    private boolean isAgree = false;          // 약관 동의 여부

    @Builder
    public User(String loginId, String password, String name, Role role) {
        this.loginId = loginId;
        this.password = password;
        this.name = name;
        this.role = role;
    }
}
```

**어노테이션 정리:**
- `@Entity` → 이 클래스 = DB 테이블 1개
- `@Id + @GeneratedValue` → PK, 자동 증가
- `@Column(unique = true)` → 같은 이메일 두 번 가입 불가
- `@Enumerated(EnumType.STRING)` → enum을 숫자(0,1)가 아닌 문자열("GUARDIAN")로 저장
- `@Builder` → `User.builder().loginId("...").build()` 패턴 사용 가능

## 6. JWT 인증 흐름

### JwtProvider.java — 토큰 생성/검증

```java
// 토큰 생성
private String createToken(Long userId, Role role, long expiry) {
    Date now = new Date();
    return Jwts.builder()
            .subject(String.valueOf(userId))        // 토큰에 userId 저장
            .claim("role", role.name())              // 토큰에 role 저장
            .issuedAt(now)                           // 발급 시간
            .expiration(new Date(now.getTime() + expiry))  // 만료 시간
            .signWith(key)                           // 비밀키로 서명
            .compact();                              // 문자열로 변환
}
```

**Access Token vs Refresh Token:**
| | Access Token | Refresh Token |
|---|---|---|
| 용도 | API 호출할 때 인증용 | Access Token 만료 시 재발급용 |
| 만료 | 30분 | 7일 |
| 사용법 | 매 요청 Header에 포함 | /auth/refresh 호출 시에만 사용 |

### JwtFilter.java — 매 요청마다 토큰 확인

```java
// 모든 HTTP 요청이 이 필터를 거친다
protected void doFilterInternal(HttpServletRequest request, ...) {

    // 1. Header에서 "Bearer eyJhbG..." 추출
    String token = resolveToken(request);

    if (token != null) {
        if (jwtProvider.validateToken(token)) {
            // 2. 토큰에서 userId, role 꺼내기
            Long userId = jwtProvider.getUserId(token);
            String role = jwtProvider.getRole(token).name();

            // 3. Spring Security에 "이 유저는 인증됨" 등록
            UsernamePasswordAuthenticationToken auth =
                    new UsernamePasswordAuthenticationToken(
                            userId, null,
                            List.of(new SimpleGrantedAuthority("ROLE_" + role))
                    );
            SecurityContextHolder.getContext().setAuthentication(auth);
        }
        // 유효하지 않으면 인증 없이 넘어감 → 인증 필요한 URL이면 403
    }

    filterChain.doFilter(request, response);  // 다음 필터로 넘기기
}
```

**흐름 정리:**
```
프론트 요청 (Header: "Bearer eyJ...")
  → JwtFilter: 토큰 꺼내서 검증
    → 유효하면: SecurityContext에 userId/role 저장
    → 유효하지 않으면: 인증 없이 통과
      → Controller에서 인증 필요한 API면 403 에러
      → /auth/login 같은 공개 API면 정상 처리
```

## 7. 에러 처리

```java
throw new BusinessException(ErrorCode.DUPLICATE_EMAIL);
```

이렇게 던지면 `GlobalExceptionHandler`가 잡아서 아래 형태로 응답:

```json
{
  "code": "AUTH-204",
  "message": "이미 등록된 이메일입니다",
  "timestamp": "2026-03-20T..."
}
```

자주 쓰이는 에러 코드:
| 코드 | 상황 |
|---|---|
| AUTH-204 | 이메일 중복 |
| AUTH-205 | 이메일/비밀번호 불일치 |
| AUTH-201 | 토큰 만료 |
| AUTH-202 | 유효하지 않은 토큰 |
