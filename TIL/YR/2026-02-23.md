# 2. Spring-boot 
## 1. 렌더링 (Rendering)
렌더링 = HTML 페이지를 만들어내는 작업. "어디서 만드느냐"에 따라 CSR과 SSR로 나뉜다.

### CSR (Client-Side Rendering)

서버는 텅 빈 HTML + JavaScript만 보내줌
브라우저가 직접 화면을 그림
첫 로딩은 느리지만, 이후 페이지 이동은 빠름
SEO(검색엔진 최적화)에 불리
대표 프레임워크: React, Vue

### SSR (Server-Side Rendering)

- 서버가 완성된 HTML을 만들어서 브라우저에 전달
- 첫 화면이 빠르고 SEO에 유리
- 페이지 이동마다 서버에 요청해야 해서 느릴 수 있음
- 대표 프레임워크: Next.js, Nuxt.js



## 2. API vs HTTP API
### API (Application Programming Interface)

- 프로그램끼리 소통하는 창구/약속
- HTTP와 전혀 상관없는 API도 존재함
- 예) 파이썬의 list.append(), 운영체제 파일 API 등

### HTTP API

- 인터넷(HTTP 통신)으로 열어놓은 소통 창구
- 우리가 웹에서 흔히 말하는 "API 연동", "API 호출"은 거의 다 HTTP API
- HTTP API는 API의 한 종류


결론: API는 넓은 개념, HTTP API는 그 안에 속하는 좁은 개념


## 3. HTML
HTML = 브라우저가 화면에 그려주는 뼈대 문서

정적 HTML: 누가 열어도 항상 같은 내용
동적 HTML: 요청한 사람/상황에 따라 내용이 달라짐 → SSR이 이에 해당


## 4. 정적 리소스 vs HTML 페이지
### 정적 리소스

서버가 가공 없이 그냥 꺼내서 주는 파일들
- 누가 요청하든 항상 똑같은 파일
- 종류: 이미지(.png, .jpg), CSS, JavaScript, 폰트 등

### 동적 HTML 페이지

서버가 DB 조회 후 HTML을 새로 만들어서 전달
사람마다 다른 내용을 보여줄 수 있음

실제 웹페이지 하나 로드 시 흐름
1. 브라우저가 HTML 페이지 요청
2. 서버가 동적 HTML 생성해서 전달
3. 브라우저가 HTML 읽으면서 필요한 정적 리소스(CSS, JS, 이미지) 추가 요청
4. 화면 완성

## 5. JSON
JSON (JavaScript Object Notation) = 데이터를 주고받을 때 쓰는 약속된 텍스트 형식

HTTP API에서 데이터를 주고받을 때 사용하는 공통 언어
데이터에 이름표를 붙여서 구조적으로 전달

```json
{
  "name": "홍길동",
  "age": 25,
  "hobbies": ["독서", "운동"]
}
```

예전엔 XML도 많이 썼지만, JSON이 훨씬 간결해서 현재 사실상 표준
백엔드는 Java/Python 등 자기 언어로 코드를 짜고, JSON은 데이터를 밖으로 내보낼 때 쓰는 포장지일 뿐


## 6. MVC 패턴
### MVC
Model + View + Controller — 코드를 역할별로 3가지로 나누는 구조

### MVC를 쓰는 이유

역할이 명확히 분리되어 유지보수가 쉬움
화면을 바꾸고 싶으면 View만, 로직을 바꾸고 싶으면 Model만 수정하면 됨


## 7. 백엔드 개발자의 역할

- HTTP API 설계 및 구현 — 어떤 요청을 받고, 뭘 돌려줄지 정의
- 비즈니스 로직 — 실제 기능 구현 (결제, 재고 차감, 알림 등)
- DB 설계 및 쿼리 — 데이터 저장/조회
- 인증/보안 — 로그인, 권한 체크, 토큰 발급


## 8. Vue.js와 MVVM

- Vue.js는 MVC가 아닌 MVVM 패턴 (Model + View + ViewModel)
- Controller 대신 ViewModel이 존재
- ViewModel의 핵심: 데이터가 바뀌면 화면이 자동으로 바뀜 → 이를 데이터 바인딩이라고 함
- 실무에서는 패턴보다는 그냥 "프론트엔드 프레임워크"로 이해해도 충분
