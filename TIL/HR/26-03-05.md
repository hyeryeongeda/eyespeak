
# [TIL] 웹캠 Eye-Tracking 고도화: MediaPipe 넘기 위한 수식 기반 추론 + Only-Eye 학습 관점

## Context
- 웹캠만으로 **시선 기반 9-grid(또는 4-grid) 선택 UI**를 만들고 싶었다.
- MediaPipe(FaceMesh/Iris)로 PoC는 되는데, 체감 정확도가 낮고 “이거 그냥 라이브러리 갖다쓴 거 아니냐(= MediaPipe 딸깍)?” 같은 피드백이 나올 수 있어 **기술 고도화 논리**가 필요했다.
- 추가로, ALS(루게릭) 사용자 특성상 **고개 자세/각도 유지가 어렵고**, 얼굴 전체 인식 의존 방식이 불안정해질 수 있다는 리스크를 고려해야 했다.

## What I Learned

### 1) MediaPipe는 ‘정답’이 아니라 ‘관측치 스트림’이다
- FaceMesh/Iris는 eye-tracking을 “완성”해주는 게 아니라,
  - **랜드마크 좌표를 실시간으로 제공하는 센서(관측치)** 역할에 가깝다.
- 제품 입력으로 만들려면 관측치 위에 내가 설계한 레이어가 필요:
  - 좌표계/정규화 → 방향 추론(수식/모델) → 스무딩/히스테리시스 → 클릭 트리거(dwell/blink) → UI 이벤트

### 2) (Track 1) ‘홍채 상대 위치’ 수식으로 방향 예측을 만들 수 있다
- 코치 피드백 핵심: MediaPipe를 쓰더라도 **홍채 위치를 수식으로 계산**해 방향을 예측하면 “딸깍”을 벗어날 수 있다.
- 개념적으로는,
  - `홍채 중심(iris center)`과 `눈 기준점(흰자/눈꼬리 등)`의 **상대 위치 벡터**를 feature로 만들고
  - 이 값을 threshold로 구간화해서 **좌/우/상/하/중앙**을 판단한다.
- 예시(개념 스니펫):

```ts
// 개념 예시: (정확한 인덱스는 FaceMesh/Iris 문서 기준으로 확정 필요)
type Pt = { x:number; y:number };

const mean = (pts: Pt[]) => ({
  x: pts.reduce((s,p)=>s+p.x,0)/pts.length,
  y: pts.reduce((s,p)=>s+p.y,0)/pts.length,
});

function gazeDirection(irisPts: Pt[], eyeCornerL: Pt, eyeCornerR: Pt) {
  const iris = mean(irisPts);

  // 눈 가로축 정규화(0~1)
  const eyeWidth = Math.max(1e-6, (eyeCornerR.x - eyeCornerL.x));
  const nx = (iris.x - eyeCornerL.x) / eyeWidth; // 0(left) ~ 1(right)

  // 간단한 구간화(예: 5-way)
  if (nx < 0.35) return "LEFT";
  if (nx > 0.65) return "RIGHT";
  return "CENTER";
}
```

* 포인트:

  * 절대 좌표(x,y)보다 **상대 좌표(정규화)**가 자세/거리 변화에 덜 민감하다.
  * 9-grid 같은 경우는 경계 오작동이 많아서 **스무딩/히스테리시스**가 사실상 필수.

### 3) “딸깍” 방지 논리는 ‘추론 레이어 + 신호처리 + 인터랙션 설계’로 만든다

* 발표/설명에서 핵심은:

  1. MediaPipe는 landmark를 제공할 뿐
  2. 나는 landmark로 **방향 추론 수식(또는 간단 모델)**을 설계했고
  3. 실사용을 위해 **필터링/디바운스/히스테리시스 + 클릭 트리거**를 결합해 입력 시스템을 완성했다
* 즉 “라이브러리 사용”이 아니라 **입력 파이프라인 설계**로 기술적 기여를 설명할 수 있다.

### 4) (Track 2) Only-Eye 학습을 고려해야 하는 ‘도메인 리스크’를 정리했다

* 코치님 경험 기반 근거:

  * MediaPipe는 **얼굴 전체가 안정적으로 인식**되어야 품질이 유지되는 경향
  * ALS 사용자는 **고개 각도/자세 유지가 어려워** 작은 변화에도 좌표가 흔들릴 수 있음
* 그래서 “얼굴 전체 의존”을 줄이려면:

  * YOLO/영상 기반 라이브러리로 **eye ROI만 검출**하고,
  * eye ROI로 **방향(4/9-grid) 분류 또는 좌표 회귀 모델**을 학습하는 “Only-Eye” 접근이 타당하다.
* 이 방향은 난이도가 높지만, 영상 도메인 AI 관점에서 더 정통이고 확장성(데이터/학습/평가/경량화)이 있다.

### 5) 학습 로그를 보며 ‘지표 해석의 함정’을 체감했다

* MAE 같은 수치가 좋아 보여도,

  * 좌표가 **정규화(0~1)**인지 **픽셀**인지,
  * 캘리브레이션/스무딩/화면 매핑이 맞는지에 따라 **체감 품질은 완전히 달라질 수 있다**.
* 즉 모델 성능 외에 “엔드투엔드 입력 시스템 품질”을 같이 봐야 한다.

## Next Step

* **Track 1(빠른 고도화)**: MediaPipe 좌표 → 정규화 → 방향 수식(또는 간단 회귀)로 “추론 레이어”를 명확히 만들고, 스무딩/히스테리시스로 9-grid 경계 오작동을 줄이는 방향을 더 공부한다.
* **Track 2(도전 과제)**: Only-Eye 파이프라인(eye ROI 검출 → grid 분류/좌표 회귀) 관련 오픈소스/모델 구조/데이터셋(안구 데이터) 특성을 조사해서 “얼굴 전체 의존 리스크”를 실제로 줄일 수 있는지 검증한다.
* **HCI/CS 관점 보강**: dwell vs double-blink 트리거의 오탐/피로 trade-off를 정리하고, 디바운스/상태기계(Idle–Calib–Track–Click) 설계를 학습해 입력 안정성을 높인다.
