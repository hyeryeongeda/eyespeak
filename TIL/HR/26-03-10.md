
# [TIL] Access Token, Refresh Token, HttpOnly Cookie 기반 로그인 구조 이해

## Context

오늘은 프론트엔드에서 로그인 인증을 구현할 때 **세션, 토큰, 쿠키를 어떤 방식으로 쓰는지**가 헷갈려서 공부를 했다. 특히 실무에서 자주 쓰는 방식이 단순히 `토큰을 localStorage에 저장`하는 구조가 아니라, **access token은 메모리에 저장하고 refresh token은 HttpOnly 쿠키에 저장하는 방식**이라는 점이 핵심이었다.

처음에는 access token과 refresh token이 둘 다 “로그인 토큰”처럼 느껴져서 역할 차이가 명확하게 잡히지 않았는데, 오늘 정리하면서 **각 토큰의 목적, 저장 위치, 만료 시 처리 흐름, 프론트에서의 구현 방식**이 왜 나뉘는지 이해할 수 있었다.

---

## What I Learned

### 1. Access Token과 Refresh Token은 역할이 완전히 다르다

#### Access Token
- 보호된 API를 호출할 때 사용하는 토큰
- 프론트가 직접 읽어서 요청 헤더에 붙여 보냄
- 보통 수명이 짧음
- 탈취되면 그 시간 동안 API 호출이 가능하므로 짧게 운영하는 것이 일반적

즉, access token은  
**“지금 이 사용자가 인증된 사용자라는 걸 증명하는 짧은 출입증”**에 가깝다.

예시:
```http
Authorization: Bearer <accessToken>
````

---

#### Refresh Token

* access token이 만료되었을 때 새 access token을 발급받기 위한 토큰
* 일반 API 호출에는 사용하지 않음
* 보통 access token보다 더 오래 유지됨
* 더 민감한 정보이기 때문에 브라우저 JS에서 직접 접근하지 못하게 관리하는 것이 중요함

즉, refresh token은 **“출입증이 만료됐을 때 새 출입증을 재발급받는 재발급권”** 에 가깝다.

---

### 2. 왜 access token은 메모리에 저장하고 refresh token은 HttpOnly 쿠키에 저장하는가

이 부분이 오늘 가장 중요하게 이해된 포인트였다.

#### access token을 메모리에 저장하는 이유

* 프론트가 API 요청마다 직접 읽어야 함
* `Authorization` 헤더에 넣어야 하므로 JS에서 접근 가능해야 함
* 대신 오래 남아 있으면 위험하므로 `localStorage`보다 메모리에만 두는 것이 상대적으로 안전함
* 새로고침하면 사라지기 때문에 영속 저장보다 노출 범위가 줄어듦

예를 들어 React에서는 Zustand, Context, Redux 같은 상태 저장소에만 유지할 수 있다.

```ts
authStore.setAccessToken(accessToken)
```

---

#### refresh token을 HttpOnly 쿠키에 저장하는 이유

* 프론트가 직접 값을 읽을 필요가 없음
* 오히려 JS에서 읽을 수 없게 막는 것이 보안상 더 유리함
* `HttpOnly` 쿠키는 브라우저 스크립트로 접근할 수 없고, 서버 요청 시 자동으로 포함됨
* refresh token은 access token보다 더 오래 살아서 더 민감하기 때문에 보호 수준을 높여야 함

즉 정리하면:

* **access token**: 프론트가 읽어야 하므로 메모리
* **refresh token**: 프론트가 읽을 필요 없고 더 민감하므로 HttpOnly 쿠키

---

### 3. localStorage에 토큰 저장이 덜 권장되는 이유

예전에는 JWT를 `localStorage`에 저장하는 구조가 많이 보였지만,
보안 관점에서는 현재 더 신중하게 봐야 하는 방식이라는 점도 이해했다.

이유는 다음과 같다.

* `localStorage`는 JS에서 바로 접근 가능함
* XSS 취약점이 생기면 악성 스크립트가 토큰을 읽어갈 수 있음
* 특히 refresh token처럼 오래 사는 토큰을 localStorage에 두는 것은 더 위험할 수 있음

그래서 요즘은
**“장기 토큰은 JS가 못 읽는 쿠키에 숨기고, 짧게 쓰는 access token만 프론트 메모리에서 관리”**
하는 패턴이 더 많이 권장된다.

---

### 4. 프론트가 refresh token을 읽지 못해도 재발급이 가능한 이유

이 부분도 처음엔 헷갈렸는데, 핵심은 다음과 같다.

프론트는 refresh token 값을 직접 꺼내는 게 아니라,
그냥 **refresh API를 호출만 한다.**

그러면 브라우저가 자동으로 쿠키를 요청에 포함해서 보내고,
서버는 그 쿠키 안의 refresh token을 검사해서 새 access token을 발급한다.

즉 프론트 관점에서 중요한 건:

1. `/auth/refresh` 요청
2. 브라우저가 refresh token 쿠키 자동 포함
3. 서버가 유효성 검사
4. 새 access token 반환
5. 프론트가 이 access token을 다시 메모리에 저장

예시:

```ts
await axios.post("/auth/refresh", {}, { withCredentials: true })
```

이 구조 덕분에 프론트는 refresh token 값을 몰라도 된다.
오히려 이게 보안상 장점이다.

---

### 5. 로그인부터 만료까지 전체 인증 흐름

오늘 공부한 내용을 정리해보자.

#### 1) 로그인

사용자가 로그인 요청을 보냄

```ts
POST /auth/login
{
  email,
  password
}
```

#### 2) 서버 응답

서버는 보통:

* 응답 body에 `access token`
* `Set-Cookie`로 `refresh token`

을 내려줌

예시:

```http
Set-Cookie: refreshToken=...; HttpOnly; Secure; SameSite=Lax; Path=/auth/refresh
```

#### 3) 프론트 저장

* access token → 메모리 저장
* refresh token → 쿠키에 자동 저장

#### 4) 일반 API 요청

프론트는 access token을 Authorization 헤더에 넣어서 API 호출

```ts
GET /users/me
Authorization: Bearer <accessToken>
```

#### 5) access token 만료

API 서버가 `401 Unauthorized` 응답 반환

#### 6) refresh 요청

프론트가 `/auth/refresh` 호출
브라우저가 쿠키 자동 첨부

#### 7) 재발급 성공

서버가 새 access token 발급
프론트가 메모리에 다시 저장

#### 8) 원래 요청 재시도

실패했던 API 요청을 새 access token으로 다시 실행

이 흐름 전체를 자동화하는 데 많이 쓰는 것이 **axios interceptor**다.

---

### 6. axios interceptor가 하는 역할

interceptor는 인증 구조의 핵심 역할을 맡는다.

#### 요청 인터셉터

모든 API 요청 전에 access token을 자동으로 헤더에 붙임

```ts
api.interceptors.request.use((config) => {
  const token = authStore.getState().accessToken
  if (token) {
    config.headers.Authorization = `Bearer ${token}`
  }
  return config
})
```

#### 응답 인터셉터

응답이 401이면:

* refresh 요청
* 새 access token 저장
* 기존 요청 재시도

```ts
api.interceptors.response.use(
  (res) => res,
  async (error) => {
    const originalRequest = error.config

    if (error.response?.status === 401 && !originalRequest._retry) {
      originalRequest._retry = true

      const refreshRes = await axios.post(
        "/auth/refresh",
        {},
        { withCredentials: true }
      )

      const newAccessToken = refreshRes.data.accessToken
      authStore.getState().setAccessToken(newAccessToken)

      originalRequest.headers.Authorization = `Bearer ${newAccessToken}`
      return api(originalRequest)
    }

    return Promise.reject(error)
  }
)
```

즉 interceptor는 **“토큰을 붙이고, 만료되면 자동으로 재발급하고, 실패한 요청을 다시 보내는 자동화 장치”** 라고 볼 수 있다.

---

### 7. access token이 항상 JWT인 것은 아니다

이 부분도 중요했다.

보통 프론트에서 토큰 이야기하면 JWT를 많이 떠올리는데,
실제로는 **access token = JWT**가 항상 성립하는 것은 아니다.

* access token은 JWT일 수도 있음
* 단순한 opaque string일 수도 있음

즉,

* **access token / refresh token** = 역할 기준
* **JWT** = 토큰의 형식 중 하나

이 둘을 같은 개념으로 보면 안 된다.

---

### 8. refresh token이 더 민감한 이유

access token은 짧게 살기 때문에, 탈취되더라도 피해 기간이 상대적으로 짧다.
반면 refresh token은 access token을 계속 새로 발급받을 수 있는 토큰이라서 훨씬 더 위험하다.

즉,

* access token 탈취 → 짧은 시간 동안 API 호출 가능
* refresh token 탈취 → 새로운 access token을 계속 발급받을 가능성 있음

그래서 refresh token은 보통:

* HttpOnly 쿠키 저장
* Secure 설정
* SameSite 설정
* rotation(재발급 시 refresh token도 교체)

같은 식으로 더 강하게 다룬다.

---

### 9. 쿠키 기반 인증에서는 CORS와 CSRF도 같이 봐야 한다

refresh token을 쿠키에 저장하는 구조는 보안상 장점이 있지만, 그만큼 추가로 고려할 것도 있다.

#### CORS

프론트와 백엔드 도메인이 다르면:

프론트:

```ts
axios.post("/auth/refresh", {}, { withCredentials: true })
```

서버:

* `Access-Control-Allow-Credentials: true`
* `Access-Control-Allow-Origin`은 `*`가 아니라 정확한 origin 지정

이런 설정이 필요하다.

---

#### CSRF

쿠키는 브라우저가 자동으로 보내기 때문에,
cross-site 요청 위조 방어도 고려해야 한다.

그래서 보통:

* `SameSite=Lax` 또는 `SameSite=Strict`
* 필요 시 CSRF 토큰 추가

같은 방식으로 설계한다.
