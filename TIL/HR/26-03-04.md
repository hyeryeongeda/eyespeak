# 👁️ 웹캠 시선추적(Eye-tracking) 학습/실험 정리 (9-Grid 입력 목표)

**작성일:** 2026-03-04  
**작성자:** 혜령
**키워드:** eye-tracking, webcam, MediaPipe, dlib, PyTorch, 9-grid, dwell, double-blink, smoothing, calibration

---

## 0) 한 줄 요약
웹캠 기반 시선추적은 “정밀 좌표”보다 **9-grid(3×3) 선택 성공률/오작동률**이 핵심이며, 안정적인 입력을 위해 **트리거(드웰/블링크) 분리 + 스무딩 + 경계 튐 방지**가 필요하다.

---

## 1) 목표와 제약

### 🎯 목표
- **웹캠 only**로 사용자가 화면의 **9칸(3×3) 중 하나를 눈으로 선택**
- ALS 등 중증 사용자 특성을 고려해:
  - 눈동자 움직임이 느리거나 미세함
  - 조명 환경이 불안정할 수 있음
  - 오작동이 치명적(잘못 누르면 위험) → 안정성이 최우선

### ⛔ 제약
- 적외선 카메라/전용 장비 없이 웹캠으로 최대한 해결
- 로컬에서 우선 PoC/학습 파이프라인 구성 (배포는 추후)

---

## 2) 접근법 비교 (MediaPipe vs dlib vs 학습 기반)

### A. MediaPipe (Face Mesh + Iris)
- **장점**
  - 학습 없이 빠르게 PoC 가능
  - 브라우저/로컬에서 즉시 테스트 용이
- **한계**
  - 저조도/작은 눈/거리 변화/각도에서 품질이 흔들릴 수 있음
  - “내 환경에서 체감 성능이 낮음”이 바로 발생 가능

### B. dlib (랜드마크 기반)
- **장점**
  - 전통적 파이프라인으로 구조가 단순
  - 로컬에서 빠르게 붙여서 테스트 가능
- **한계**
  - 고정된 랜드마크(예: 68)로 눈 디테일이 부족할 수 있음
  - “눈만 더 촘촘히(16+)” 같은 요구에는 커스텀이 어려움(별도 학습 필요)

### C. 학습 기반(커스텀 모델: Eye crop/landmark + gaze head)
- **장점**
  - 데이터/증강으로 조명·사용자 특성에 대응 가능
  - 9-grid 목적에 맞게 **분류(9클래스)** 또는 **좌표 회귀→grid**로 설계 가능
- **리스크**
  - 데이터 라벨 형태 확인/전처리/검증까지 비용이 큼

**결론(현재 판단):**  
MediaPipe/dlib은 “빠른 PoC”에 적합하지만, 목표(ALS 포함, 저조도/느린 시선 대응)까지 커버하려면 **학습 기반 접근을 검토**해야 함.

## 3) 현재 테스트/학습 로그(실제로 확인한 출력)

### 데이터/피처 형태 (실험 로그)
- `features: (48474, 4096) float32`
- `labels  : (48474, 2) float32`
- label range
  - x: `0.29305217 ~ 0.6383789`
  - y: `0.2275754 ~ 0.7901877`

### 학습 결과(지표 로그)
- `MAE x,y: [0.01145549 0.01345299]`
- `MAE mean: 0.012454240582883358`

> **중요 메모:** 수치(MAE)가 “괜찮아 보이더라도” 실제 체감/시각 결과가 구릴 수 있음.  
> 이유는 9-grid에서는 경계 근처 오차가 곧 “다른 칸 선택”으로 이어져 **UX 품질을 크게 깎기 때문**.

## 4) 9-Grid 입력 관점에서의 ‘성능’ 정의(지표 재설계)

좌표 모델을 만들더라도 최종 목표는 “정확한 x,y”가 아니라 **칸 선택 성공**이다.

### 추천 평가 지표(실사용 중심)
1. **Grid Accuracy(%)**
   - 정답 칸을 맞춘 비율
2. **False Selection Rate(오작동률)**
   - 의도치 않게 다른 칸이 선택되는 비율
3. **Time-to-Select**
   - 선택까지 걸리는 평균 시간(피로도 직결)
4. **Stability(칸 유지 안정성)**
   - 동일 칸을 보고 있을 때 칸이 튀는 빈도(초당 변화 횟수 등)

## 5) 캘리브레이션/선택(클릭) UX 설계에서 배운 점

### 1) “커서 이동”과 “선택 트리거”는 분리해야 안정적
- 커서(시선 포인터)는 계속 흔들릴 수밖에 없음
- 선택은 별도의 의도 신호로 분리:
  - **드웰(dwell)**: 일정 시간 응시 유지 시 선택
  - **더블 블링크(double blink)**: 눈 깜빡임을 의도 신호로 사용

### 2) 드웰만 쓰면 생기는 문제
- 피로도 증가
- 오작동(잠깐 쳐다본 것만으로 선택) 위험
- ALS 사용자는 “고정 응시” 자체가 부담일 수 있음

### 3) 더블 블링크의 실전 포인트
- 오작동을 줄이는 데 유리하지만,
- 블링크 인식이 불안정하면 반대로 입력이 막힐 수 있음  
→ 결국 **드웰/블링크를 상황별로 조합**하거나, 임계값/쿨다운 설계를 잘 해야 함.

## 6) 안정화(Smoothing)와 경계 튐 방지(Hysteresis)

웹캠 기반 시선추적은 **미세 떨림/노이즈가 기본값**이다.

### 적용 가치가 큰 안정화 기법
- **EMA(지수이동평균)**: 가장 간단, 즉시 체감 개선
- **One-Euro Filter**: 빠른 움직임/느린 움직임을 상황에 따라 자연스럽게 처리
- **Kalman Filter**: 모델링 기반, 튜닝 난이도는 높음

### 9-grid에서 특히 중요한 “경계 튐 방지”
- 칸 경계 근처에서 좌표가 흔들리면 칸이 계속 바뀜
- 해결:
  - “새 칸으로 확정되려면” 일정 시간 유지 or 더 큰 이동 요구
  - 즉, **hysteresis(히스테리시스)** 룰을 넣어 칸 변경을 어렵게 만들기

## 7) 데이터셋/학습 파이프라인 관점에서 정리한 체크포인트

### 1) 라벨 형태를 먼저 확인해야 함
- (A) screen normalized **(x,y)** 회귀 라벨
- (B) **yaw/pitch** 각도 라벨
- (C) **9-grid class**로 재가공 라벨(목표 직결)

### 2) 9-grid 목표라면 설계 선택지
- **좌표 회귀 → grid 변환**
  - 장점: 더 유연(추후 5-grid/12-grid로 확장 용이)
  - 단점: 경계 민감(안정화 필수)
- **9클래스 분류**
  - 장점: 목표에 직결, 평가지표가 명확
  - 단점: 칸 수 바뀌면 재학습 부담

### 3) 증강(Augmentation)은 “조명/거리/각도”가 핵심
- 목표 사용자가 다양한 환경(실내 조명, 화면 반사 등)에 놓임
- 실사용 품질은 데이터 증강에 크게 좌우됨

---

## 8) 실행/환경(실습 과정에서 같이 배운 점)
- 데이터 다운로드/압축/경로 문제로 파이프라인이 자주 멈춤
- WSL/conda/jupyter 등 실행 환경이 불안정하면 실험 속도가 급격히 떨어짐
- “돌아간다”와 “쓸만하다”는 다름  
→ 반드시 **검증 시나리오 + 로그 + 리포트**가 같이 가야 함

---

## 9) 현재 문제 요약 & 원인 가설

### 문제
- 시각적으로 “커서가 구리다/불안정하다” 체감
- 가까운 거리/작은 눈/조명 변화에서 흔들림

### 원인 가설
- 좌표 자체 노이즈 + 경계 민감 + 트리거 설계 미흡이 합쳐져 UX가 무너짐
- MAE 같은 회귀 지표만으로는 “9-grid 성공률”을 대변하지 못함

## 101) 결론
웹캠 시선추적은 기술적으로 좌표를 뽑는 것보다, **입력 장치로서 쓸 수 있게 만드는 것(평가 지표, 스무딩, 트리거, 캘리브레이션, 오작동 방지 UX)**이 더 중요하다.  
따라서 다음 단계는 “모델 성능”만 보지 않고, **9-grid 선택 성공률 중심으로 파이프라인 전체를 재구성**하는 것이다.
