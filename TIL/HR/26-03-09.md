# TIL

**주제: 안구 추적 기반 ALS 의사소통 서비스의 화면 구조, 입력 방식, 문서 설계 기준 정리**

## 알게 된 점

- 오늘 가장 크게 정리된 건, **이 서비스의 UI는 일반적인 웹서비스처럼 “보기 좋은 화면”을 만드는 문제가 아니라, 제한된 입력 환경에서 실제로 선택 가능한 구조를 만드는 문제**라는 점이었다.
    
    평소에는 화면을 설계할 때 정보 구조나 배치, 디자인 일관성, 컴포넌트 재사용성 같은 걸 먼저 생각하게 되는데, 이번 서비스는 그보다도 먼저 **사용자가 눈으로 얼마나 안정적으로 선택할 수 있는지**를 기준으로 봐야 한다는 걸 더 분명히 이해하게 됐다.
    
    특히 4분할, 6분할, 9분할 같은 구조는 단순히 메뉴 개수를 늘리고 줄이는 문제가 아니었다. 분할 수가 늘어나면 한 화면에서 제공할 수 있는 정보량은 많아지지만, 그만큼 시선 이동 부담이 커지고 오선택 가능성도 같이 커진다. 반대로 분할 수를 줄이면 선택은 쉬워지지만 원하는 표현에 도달하기까지 단계가 늘어날 수 있다.
    
    결국 이 UI는 “한 번에 많이 보여줄 것인가”보다 **“최소한의 피로와 최소한의 오작동으로 목적에 도달하게 할 수 있는가”**를 중심으로 판단해야 한다는 걸 다시 배웠다.
    
- **6분할도 그냥 균등 분할이 아니라 실제 사용 흐름 기준으로 해석해야 한다**는 점이 정리됐다.
    
    처음엔 6분할이라고 해서 단순히 화면을 6개의 동일한 영역으로 쪼개는 정도로 생각했는데, 실제로 논의한 구조는 그런 개념과 조금 달랐다.
    
    오늘 다시 보면서 정리된 건, 이 6분할은 웹페이지 기준으로 **상단 3칸 + 하단 3칸** 구조를 전제로 하고, 그 안에서도 기능 중요도에 따라 고정 영역과 전환 영역을 나눠서 생각해야 한다는 점이었다.
    
    예를 들어 뒤로가기처럼 사용 흐름 전체에 영향을 주는 기능은 일반 메뉴와 동일한 레벨에서 계속 섞여 있으면 사용자가 헷갈릴 수 있기 때문에, 가능한 한 **항상 같은 자리에 고정**되어야 한다. 반대로 선택 결과에 따라 열리고 닫히는 영역은 맥락형으로 보여주는 것이 더 자연스럽다.
    
    결국 같은 “6칸”이라도 단순 레이아웃이 아니라, **어떤 칸은 구조적으로 고정되고 어떤 칸은 상황에 따라 전환되는 인터랙션 모델**로 봐야 한다는 점을 더 명확하게 이해했다.
    
- **더블 블링크와 dwell을 단순 입력 수단으로만 보면 설계가 얕아지고, 상태 전이 규칙으로 봐야 문서가 제대로 정리된다**는 점도 배웠다.
    
    처음에는 “응시하면 선택되고, 더블 블링크하면 뒤로간다” 정도의 규칙만 있으면 되는 줄 알았는데, 실제 문서를 쓰려다 보니 그 정도로는 부족했다.
    
    예를 들어 사용자가 특정 영역을 응시하는 순간 바로 선택되는 게 아니라, 먼저 응시 유지 시간이 쌓이는 과정이 필요하다. 이건 단순한 클릭이 아니라 `DwellProgress` 같은 상태로 봐야 한다. 그리고 dwell이 완료되면 `Selected`가 되고, 그 다음엔 선택 완료를 사용자에게 보여주는 `Feedback`이 있어야 한다. 선택 결과가 실제 전송과 연결된다면 `Sending` 상태도 필요하다. 반대로 얼굴이 감지되지 않으면 `NoFace`, 감지는 되지만 신뢰도가 낮으면 `LowConfidence` 같은 예외 상태도 필요하다.
    
    즉, 입력 장치를 설명하는 것만으로는 부족하고, **사용자 행동이 시스템 상태를 어떻게 바꾸는지**까지 정리해야 기능 명세서, 상태 정의서, 예외 처리 기준이 서로 일관되게 이어진다는 걸 실감했다.
    
- **‘선택’ 자체보다 ‘선택 직전과 직후’를 어떻게 다루는지가 훨씬 중요하다**는 것도 느꼈다.
    
    일반 클릭 UI에서는 사용자가 버튼을 눌렀다면 그걸로 거의 끝인데, 시선 기반 UI에서는 선택 전후 과정이 훨씬 더 중요하다.
    
    선택 직전에는 사용자가 “내가 지금 무엇을 선택 중인지”를 인지할 수 있어야 하고, 선택 직후에는 “방금 선택이 정상 반영됐는지”에 대한 피드백이 확실해야 한다. 그렇지 않으면 사용자는 다시 응시하거나, 의도치 않게 같은 기능을 반복 선택할 가능성이 커진다.
    
    오늘 얘기 나온 “최종 문장을 읽는 시간 3초~5초를 준 다음 선택 가능하게 하기”, “dwell 시간을 조절 가능하게 하기” 같은 조건도 결국 이 문제와 연결된다. 시스템은 빠르게 반응하는 게 무조건 좋은 게 아니라, **사용자가 따라갈 수 있는 속도로 반응해야 안정적**이라는 걸 다시 생각하게 됐다.
    
    그래서 이 서비스의 반응성은 ‘빠름’보다 **‘예측 가능함’과 ‘회복 가능함’**이 더 중요하다는 점이 인상 깊었다.
    
- **기능 명세서와 API 명세서는 전혀 다른 문서인데, 실제 협업에서는 자주 섞여서 혼선이 생긴다**는 점을 다시 체감했다.
    
    오늘 문서를 보다 보니 내가 어색하다고 느꼈던 이유가 정확히 이 부분이었다. 어떤 문서는 겉으로는 기능 명세서처럼 보이는데, 실제 내용은 API 요청/응답 구조나 백엔드 처리 단위에 가까웠다. 그러면 프론트 입장에서는 “이게 사용자 기능을 설명하는 문서인지, 시스템 구현 단위를 설명하는 문서인지”가 불명확해진다.
    
    기능 명세서는 기본적으로 사용자 관점 문서다. 화면 목적, 사용자, 진입 조건, 화면 구성, 입력 방식, 동작 흐름, 예외 상황, 종료 조건처럼 **사용자가 무엇을 보고 무엇을 하고 어떤 결과를 받는지**가 중심이어야 한다.
    
    반면 API 명세서는 엔드포인트, 요청 파라미터, 응답 스키마, 상태 코드, 에러 메시지처럼 **시스템 간 데이터 계약**을 다루는 문서다.
    
    오늘 정리하면서, 앞으로는 문서를 볼 때도 “이 문서는 사용자 행위를 설명하는가, 아니면 데이터 교환 규칙을 설명하는가”를 먼저 구분해서 봐야겠다고 느꼈다. 이 기준이 없으면 화면 흐름과 서버 로직이 뒤섞여서, 나중에 구현 단계에서 해석 차이가 더 커질 수밖에 없다.
    
- **프론트가 개발을 시작하기 전에 필요한 문서는 생각보다 많고, 그중에서도 상태 정의서와 화면별 제약 문서가 실제 구현 안정성에 큰 영향을 준다**는 점도 배웠다.
    
    흔히 개발 전에 필요한 문서라고 하면 요구사항 정의서, 화면 목록, 기능 명세서 정도만 떠올리기 쉬운데, 오늘 정리하면서 그보다 더 세밀한 문서들이 왜 필요한지 더 이해하게 됐다.
    
    예를 들어 안구 추적 기반 서비스에서는 “선택 중일 때 뒤로가기가 가능한가”, “NoFace 상태에서는 현재 화면을 유지하는가 아니면 안내 화면으로 전환하는가”, “피드백은 몇 초 동안 노출되는가”, “문장 완성 후 사용자가 읽을 시간을 얼마큼 줄 것인가”, “응시 dwell 시간을 사용자가 조절할 수 있는가” 같은 규칙이 실제 사용자 경험에 매우 직접적으로 영향을 준다.
    
    이런 내용은 단순 화면 목록이나 와이어프레임만으로는 잘 안 드러난다. 그래서 **상태 정의서**, **버튼/타이포/피드백/뒤로가기 규칙 문서**, **예외 화면 목록**, **화면별 UI 제약 문서** 같은 세부 산출물이 필요하다는 걸 더 분명히 느꼈다.
    
    특히 이 서비스는 정상 흐름보다 예외 흐름에서 훨씬 더 많은 문제가 생길 가능성이 높기 때문에, 문서도 “무엇을 보여줄지” 못지않게 **“언제 막히고, 어떻게 복구시킬지”**를 먼저 정리해야 한다고 느꼈다.
    
- **프론트가 주도적으로 정리해야 할 부분과 팀 공용으로 합의해야 할 부분을 구분하는 것도 중요하다**는 걸 느꼈다.
    
    오늘 대화하면서 특히 느낀 건, 모든 걸 프론트 문서에 넣는다고 좋은 게 아니라는 점이었다. 어떤 건 프론트가 명확히 정의해야 하고, 어떤 건 팀 전체 정책으로 분리해서 정리해야 한다.
    
    예를 들어 화면 구성, 뒤로가기 위치, 선택 피드백 방식, 라우팅 구조, 컴포넌트 분리 기준, 화면별 제약은 프론트에서 먼저 정리해볼 수 있다. 하지만 더블 블링크를 어디까지 허용할지, 응시 dwell 기준을 기본값으로 어떻게 둘지, 선택 확정 후 취소를 허용할지, 추천 로직이 언제 개입할지 같은 건 프론트 단독으로 확정하기보다 **정책 확정 필요**로 열어두는 게 맞다.
    
    오늘 문서를 정리하면서, 모든 불확실성을 억지로 해소하려 하기보다 **확정된 것 / 미확정인 것 / 팀 합의가 필요한 것**을 분리해서 적는 방식이 오히려 더 실무적이라는 걸 느꼈다.
    
- **이 서비스의 핵심은 단순히 기능이 많아지는 것이 아니라, 사용자가 적은 선택만으로 원하는 표현에 도달하게 만드는 정보 구조 최적화**라는 점도 더 분명해졌다.
    
    메인 화면에 호출, 여가, 통증/생리, STT 소통, 키보드 같은 기능이 있다고 해도 중요한 건 기능 수가 아니라 진입 깊이와 회수였다.
    
    예를 들어 자주 쓰는 기능은 가능한 한 상위 레벨에 둬야 하고, 자주 안 쓰는 기능은 너무 깊숙이 넣기보다 별도 진입점이나 보조 흐름으로 분리하는 편이 더 좋을 수 있다. 또한 뒤로가기/복귀가 어렵다면 아무리 기능 구성이 좋아도 사용성이 급격히 떨어질 수 있다.
    
    결국 사용자 입장에서는 기능이 많고 적고보다 **“내가 원하는 말을 몇 번 만에, 얼마나 덜 힘들게, 얼마나 확실하게 말할 수 있느냐”**가 더 중요하다는 걸 다시 생각하게 됐다.
    
    그래서 앞으로는 기능을 추가할 때마다 “이게 정보 구조를 복잡하게 만드는가, 아니면 실제 선택 경로를 줄여주는가”를 기준으로 보게 될 것 같다.
    

## 인사이트 및 느낀 점

오늘 정리하면서 가장 크게 든 생각은, 이 프로젝트는 단순히 **웹에서 동작하는 특수 입력 UI를 만드는 것**이 아니라 **입력 제약이 있는 사용자를 위해 서비스 전체 구조를 다시 설계하는 일**이라는 점이었다.

평소 프론트 작업에서는 화면이 자연스럽게 연결되는지, 상태 관리가 잘 되는지, API 연동이 깔끔한지를 많이 보게 되는데, 이번 프로젝트는 그보다 앞에서부터 “이 사용자는 정말 이 화면을 사용할 수 있는가?”를 먼저 물어야 했다.

그래서 기능 하나를 추가하는 것도 일반 서비스처럼 “편의 기능 추가”로 끝나지 않고, 시선 이동량, 오작동 가능성, 피로 누적, 복귀 방식, 인지 부담까지 같이 보게 된다. 이 부분이 생각보다 훨씬 어렵고, 동시에 이 프로젝트를 특별하게 만드는 지점이라는 생각이 들었다.

또 하나 느낀 건, 내가 오늘 계속 정리했던 기능 명세서나 상태 정의서 같은 문서들이 단순 행정 작업이 아니라는 점이다.

예전에는 문서를 쓰는 일이 개발 전에 해야 하는 준비 작업처럼 느껴질 때도 있었는데, 오늘처럼 입력 제약이 강한 서비스를 다루다 보니 문서 자체가 거의 **서비스 설계의 핵심 결과물**처럼 느껴졌다.

화면은 나중에 바뀔 수 있고, 스타일은 더 다듬을 수 있지만, 상태 전이 규칙이나 예외 처리 기준이 흔들리면 구현 단계에서 계속 충돌이 날 수밖에 없다.

결국 문서를 잘 쓴다는 건 단순히 정리를 잘하는 게 아니라, **팀이 같은 제품을 같은 방식으로 이해하게 만드는 일**이라는 걸 다시 느꼈다.

그리고 오늘 가장 실무적으로 얻은 깨달음은, 앞으로는 화면을 바로 만들기보다

**상태 정의 → 기능 명세 → 예외 규칙 → 화면 제약 → 라우팅/컴포넌트 구조 → 구현**

이 순서로 가는 게 훨씬 덜 흔들리겠다는 점이다.

특히 안구 추적 UI처럼 선택 방식이 특수한 서비스에서는 화면을 먼저 만들면 나중에 규칙이 바뀔 때마다 화면과 로직을 같이 뒤엎게 될 가능성이 높다. 반대로 상태와 규칙이 먼저 잡혀 있으면, 화면은 오히려 그 위에 안정적으로 올라갈 수 있다.

그래서 오늘은 단순히 몇 개 문서를 더 만든 날이 아니라, **이 프로젝트를 어떤 순서로 설계하고 구현해야 덜 흔들리는지에 대한 기준을 세운 날**로 기억될 것 같다.

마지막으로, 오늘 느낀 건 내가 지금 하고 있는 고민들이 생각보다 되게 본질적인 고민이라는 점이다.

겉으로 보면 화면 분할 수나 뒤로가기 위치, dwell 타임, 더블 블링크 규칙 같은 아주 세부적인 문제처럼 보일 수 있다. 그런데 실제로는 이런 작은 규칙 하나하나가 사용자의 피로도, 실수 가능성, 신뢰감, 서비스 지속 사용 가능성에 다 연결된다.

즉, 지금 고민하는 것들이 단순한 UI 디테일이 아니라 **사용 가능성과 접근성의 핵심 설계 요소**라는 점에서, 앞으로도 이런 기준을 더 꼼꼼히 잡아야겠다고 느꼈다.

오늘은 “무엇을 만들까”를 넘어서, **“어떻게 해야 실제로 쓸 수 있는 서비스를 만들 수 있을까”**를 많이 배운 하루였다.
