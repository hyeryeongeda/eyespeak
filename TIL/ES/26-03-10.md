# TIL - EC2 인프라 세팅 (Docker, Jenkins, GitLab 연동)

## 오늘 한 일

EC2에 Docker를 설치하고, Jenkins 컨테이너를 띄우고, SSAFY GitLab과 연동하여 git clone까지 성공했다.

---

## 배운 것

### 1. EC2에 Docker 설치하는 법을 배웠다

EC2(Ubuntu)에 Docker를 설치하려면 Docker 공식 GPG 키와 저장소를 먼저 추가해야 한다. `apt install docker`로 대충 설치하면 오래된 버전이 깔릴 수 있어서, Docker 공식 저장소에서 최신 버전을 받는 게 중요하다.

설치 후 `sudo usermod -aG docker $USER`를 해야 `sudo` 없이 docker 명령을 쓸 수 있는데, 이 설정을 적용하려면 SSH를 한 번 끊고 다시 접속해야 한다. 처음에 이걸 몰라서 계속 `permission denied`가 떠서 헤맸다.

### 2. Jenkins를 Docker 컨테이너로 띄우는 게 편하다

Jenkins를 직접 설치할 수도 있지만, Docker로 띄우면 `docker compose up -d` 한 줄이면 끝이다. docker-compose.yml에 Jenkins 이미지와 볼륨 설정을 적어두면 컨테이너를 삭제해도 데이터(jenkins_data 볼륨)가 유지된다.

중요한 건 `/var/run/docker.sock`을 마운트하는 것이다. Jenkins 컨테이너 안에서 호스트의 Docker를 사용할 수 있게 해주는 건데, 나중에 Jenkins가 Docker 이미지를 빌드하고 배포하려면 이게 필요하다.

초기 접속 시 비밀번호는 `docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword`로 확인할 수 있다. "admin 계정으로 계속하기"를 누르면 비밀번호가 admin으로 설정되는 줄 알았는데 아니었다. 초기 비밀번호를 직접 확인해야 한다.

### 3. EC2에서 SSAFY GitLab SSH 연결이 안 된다

EC2에서 `ssh -T git@lab.ssafy.com`을 했는데 응답이 없었다. `nc -zv lab.ssafy.com 22`도 마찬가지. SSAFY GitLab이 VPN 내부에서만 SSH 접근을 허용하는 것으로 보인다. EC2는 AWS 외부 네트워크이기 때문에 VPN 밖이라 SSH 포트(22)가 막혀있었다.

이 경험에서 배운 건, 네트워크 환경에 따라 SSH가 안 될 수 있으니 **항상 HTTPS 방식도 대안으로 준비해야 한다**는 것이다.

### 4. SSH가 안 되면 HTTPS + Access Token으로 대체할 수 있다

SSH 대신 HTTPS 방식으로 GitLab에 접근하려면 Access Token이 필요하다. 개인 Access Token과 Project Access Token 두 가지가 있는데, 팀 프로젝트에서는 Project Access Token이 더 적합하다. 개인 토큰은 개인 계정에 묶여서 그 사람이 나가면 토큰도 무효화되지만, Project Access Token은 프로젝트에 묶여서 팀원 변동과 무관하게 유지된다.

Project Access Token을 만들면 GitLab이 자동으로 봇 계정을 생성해준다. git clone 할 때 Username에 이 봇 이름, Password에 토큰 값을 넣으면 인증이 된다.

단, Project Access Token 생성은 Maintainer 권한 이상이 필요하다. Developer 권한으로는 Settings > Access Tokens 메뉴 자체가 안 보일 수 있다.

### 5. SSH 키 종류 — RSA vs Ed25519

SSH 키를 만들 때 RSA와 Ed25519 두 가지를 고민했다.

Ed25519가 속도도 빠르고 보안도 좋지만 호환성이 걱정이었다. 조사해보니 OpenSSH 6.5(2014년) 이상이면 다 지원하고, EC2 Ubuntu, GitLab, Jenkins 전부 최신 버전이라 Ed25519를 써도 문제없었다. 결국 SSH 방식 자체를 안 쓰게 됐지만, 나중에 다른 프로젝트에서 SSH 키를 만들 때 Ed25519를 쓰면 될 것 같다.

이미 RSA로 키를 만들었더라도 Ed25519로 새로 만들면 파일명이 다르기 때문에(`id_rsa` vs `id_ed25519`) 서로 충돌하지 않는다. 안 쓰는 키는 `rm`으로 삭제하면 된다.

### 6. Jenkins Credentials에 GitLab 인증 정보를 등록하는 법을 배웠다

Jenkins가 GitLab에서 코드를 가져오려면 인증 정보가 필요하다. Jenkins 관리 > Credentials > Global > Add Credentials에서 "Username with password" 타입으로 등록한다. Username에 봇 이름, Password에 Access Token을 넣으면 된다.

ID 필드(예: `gitlab-token`)는 GitLab에서 가져오는 값이 아니라 내가 직접 짓는 별명이다. 나중에 Jenkinsfile에서 `credentials('gitlab-token')`으로 참조할 때 이 ID를 사용한다.

### 7. EC2에서 HTTPS로 git clone이 되면 Jenkins에서도 된다

EC2 터미널에서 직접 `git clone https://...` 해서 성공하면, 같은 인증 정보를 Jenkins에 등록했을 때도 동일하게 동작한다. EC2에서 먼저 테스트하고 Jenkins에 등록하는 순서가 안전하다.

---

## 삽질 기록

- `docker` 명령어 permission denied → `usermod -aG docker` 후 SSH 재접속 필요
- Jenkins 초기 비밀번호를 admin으로 착각 → `docker exec`로 직접 확인해야 함
- SSH로 GitLab 연결 시도 → VPN 문제로 실패 → HTTPS + Access Token으로 전환
- RSA 키 먼저 만들고 Ed25519로 바꿈 → 결국 SSH 자체를 안 쓰게 됨 → 키 삭제

---

## 느낀 점

인프라 작업은 "이론적으로 되어야 하는 것"과 "실제로 되는 것"이 다를 수 있다는 걸 느꼈다. SSH가 당연히 될 줄 알았는데 네트워크 환경 때문에 안 돼서 HTTPS로 전환해야 했다. 항상 대안을 준비하고, 안 되면 빠르게 방향을 바꾸는 게 중요한 것 같다. 삽질한 시간이 아깝지만, 덕분에 SSH/HTTPS 인증 방식의 차이, Access Token 종류, Docker 소켓 마운트 등 기반 지식이 쌓였다.
