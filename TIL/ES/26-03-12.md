# TIL - Frontend Docker Compose + Healthcheck

## 오늘 한 일

Frontend용 Docker Compose를 백엔드처럼 base / local / dev / prod 로 나누어 작성했다. Dockerfile은 Node로 빌드하고 nginx로 정적 파일만 서빙하는 멀티스테이지로 구성했고, Dev·Prod·Blue/Green·모니터링을 대비해 프론트 컨테이너에도 healthcheck를 넣었다. 환경별 API 주소는 표(로컬 8080, Dev/Prod 도메인)를 기준으로 맞추었고, 실제 도메인은 `j14e205.p.ssafy.io` 로 반영했다. 로컬·Dev·Prod 각각 띄워 보면서 테스트하는 방법도 정리했다.

## 배운 것

### 1. 프론트엔드는 빌드 시점에 API 주소가 박힌다

백엔드는 실행 시 환경변수로 DB URL을 바꿀 수 있는데, Vite(React)는 빌드할 때 `import.meta.env.VITE_*` 값이 코드에 들어간다. 그래서 환경마다 **다른 API 주소**를 쓰려면 이미지를 환경별로 따로 빌드해야 한다. docker-compose에서 `build.args` 로 `VITE_API_BASE_URL` 을 넘기고, Dockerfile에서 `ARG` → `ENV` 로 받아서 `npm run build` 전에 세팅해 두면, 로컬(localhost:8080), Dev(dev.j14e205.p.ssafy.io), Prod(j14e205.p.ssafy.io) 각각 다른 주소가 박힌 이미지를 만들 수 있다. 프론트는 .env 파일이 필수는 아닌 이유도 여기 있다. 백엔드는 DB 비밀번호 등 런타임에 꼭 필요해서 .env가 거의 필수인 반면, 프론트는 빌드 시 한 번만 넣으면 되고 기본값을 compose에 적어둬도 되기 때문이다.

### 2. 프론트 컨테이너에도 healthcheck를 두는 이유

처음에는 “그냥 nginx 띄우는 건데 healthcheck가 있나?” 싶었는데, Dev/Prod에서 Nginx 리버스 프록시가 upstream( front-blue, front-green ) 상태를 보고, Blue/Green 전환 시 “Green이 진짜 살아 있는지” 확인하고, 모니터링에서 “프론트가 응답하는지” 판단하려면 **컨테이너 단위 healthcheck**가 있으면 편하다. 그래서 “로컬만 쓸 때는 없어도 되지만, Dev/Prod·Blue/Green·모니터링을 쓸 거면 넣어 두는 게 좋다”는 걸 배웠다. nginx:alpine에는 wget이 없을 수 있어서 Dockerfile에서 `apk add --no-cache wget` 한 뒤, healthcheck에서 `wget -q -O /dev/null http://127.0.0.1/` 로 200만 확인하도록 했다.

### 3. Docker Compose 프로필로 “어떤 서비스를 띄울지”를 나눈다

base에는 `front-blue`, `front-green` 만 정의하고 둘 다 `profiles: blue` / `green` 을 준다. 로컬용은 `front-local` 하나만 쓰고 프로필 없이 두었기 때문에, `-f docker-compose.yml -f docker-compose.local.yml up -d` 하면 front-local만 뜨고 blue/green은 안 뜬다. Dev는 `--profile blue` 로 front-blue만, Prod는 `--profile blue --profile green` 로 둘 다 띄우면 된다. “같은 compose 파일로 환경만 바꿔서 어떤 서비스를 올릴지 제어한다”는 패턴을 백엔드에서 쓰던 걸 프론트에도 그대로 적용한 거라, 구조가 통일돼서 기억하기 쉬웠다.

### 4. 환경별 URL을 한 번에 정리해 두면 실수 줄어든다

로컬 / Dev / Prod 의 “프론트 주소”와 “백엔드 API 주소”를 표로 정리해 두고, 그걸 기준으로 각 compose 파일 주석이랑 `VITE_API_BASE_URL` 기본값을 맞춰 두었다. 나중에 도메인만 바꾸면 될 때 표 하나만 보고 수정하면 돼서, “Dev는 어디고 Prod는 어디지” 하는 혼란이 덜했다. 실제 도메인이 `j14e205.p.ssafy.io` 라서 `.com` 없이 그대로 넣었고, Dev는 `dev.j14e205.p.ssafy.io` 로 통일했다.

### 5. “잘 되는지” 확인하는 방법 정리

- `docker ps` 로 컨테이너 Up + (healthy) 확인  
- 브라우저에서 해당 포트(로컬/Dev 8000, Prod는 8000·8001) 접속해서 화면 뜨는지 확인  
- Windows에서는 `curl -s -o NUL -w "%{http_code}" http://localhost:8000` 이나 `Invoke-WebRequest` 로 200만 빠르게 확인할 수 있다. 리눅스처럼 `/dev/null` 쓰면 안 되고 `NUL` 로 써야 한다는 걸 새로 알았다.

## 삽질 기록

- **Docker 이미지 전부 지우려다 `invalid reference format`**  
  `docker image rm -f $(docker image ls)` 를 PowerShell에서 썼는데, `docker image ls` 가 표 형태(REPOSITORY, TAG, IMAGE ID …)로 출력돼서 그게 통째로 인자로 넘어갔다. `docker image rm` 은 이미지 ID나 repository:tag 만 받기 때문에 “IMAGE”, “ID” 같은 단어가 들어가면서 에러가 났다. 이미지 **ID만** 넘기려면 `docker images -q` 로 받아서 `ForEach-Object { docker image rm -f $_ }` 하거나, 그냥 `docker image prune -a -f` 로 안 쓰는 이미지만 정리하는 게 낫다.

- **Windows에서 curl로 응답만 보고 싶을 때**  
  리눅스처럼 `-o /dev/null` 하면 안 되고, Windows에서는 `-o NUL` 이라고 써야 한다. PowerShell이면 `(Invoke-WebRequest -Uri ... -UseBasicParsing).StatusCode` 로 상태 코드만 받는 게 더 나을 수도 있다.
