# TIL - 백엔드 초기 세팅

## 오늘 한 일

Spring Boot 프로젝트의 global 패키지 구조를 잡고, 팀원 모두가 동일한 패턴으로 개발할 수 있도록 공통 코드를 작성했다.

---

## 배운 것

### 1. 공통 응답 포맷을 왜 만들어야 하는지 알게 됐다

프론트엔드가 API 응답을 파싱할 때, API마다 구조가 다르면 매번 다른 파싱 로직을 짜야 한다.
성공은 `ApiResponse`, 에러는 `ErrorResponse`로 포맷을 통일하면 프론트에서 공통 로직 하나로 처리할 수 있다.

```java
// 성공 → 항상 이 구조
{ "code": "SUCCESS", "message": "요청이 성공하였습니다", "data": { ... } }

// 에러 → 항상 이 구조
{ "code": "PATIENT-301", "message": "환자를 찾을 수 없습니다", "timestamp": "..." }
```

`ApiResponse`에서 `@JsonInclude(JsonInclude.Include.NON_NULL)`을 쓰면 data가 null일 때 JSON에서 아예 빠진다. 삭제 성공처럼 돌려줄 데이터가 없을 때 깔끔해진다.

### 2. 에러를 Enum으로 관리하면 프론트와 소통이 편해진다

처음에는 `throw new RuntimeException("환자를 찾을 수 없습니다")` 이렇게 하면 되지 않나 싶었는데, 이러면 프론트에서 에러 메시지 문자열로 분기를 해야 해서 메시지가 바뀌면 프론트도 깨진다.

`ErrorCode` enum에 HTTP 상태, 에러 코드, 메시지를 한 곳에서 관리하면 프론트는 `"PATIENT-301"` 같은 코드 문자열로 분기할 수 있다. 메시지가 바뀌어도 코드가 같으면 프론트 코드를 안 고쳐도 된다.

```java
// 에러 코드 3요소: HTTP 상태 + 코드 문자열 + 메시지
PATIENT_NOT_FOUND(HttpStatus.NOT_FOUND, "PATIENT-301", "환자를 찾을 수 없습니다")
```

### 3. GlobalExceptionHandler 덕분에 Controller가 깔끔해진다

`@RestControllerAdvice`를 붙인 클래스가 앱 전체의 예외를 한 곳에서 잡아준다. 이게 없으면 모든 Controller에 try-catch를 반복해야 한다.

Service에서 `throw new BusinessException(ErrorCode.XXX)` 한 줄이면 GlobalExceptionHandler가 잡아서 ErrorResponse로 변환해준다. Controller는 성공 로직에만 집중하면 된다.

`BusinessException`이 `RuntimeException`을 상속하는 이유도 알게 됐다. Checked Exception이면 throws 선언을 매번 해야 하고, Spring의 `@Transactional`도 기본적으로 RuntimeException만 롤백하기 때문이다.

### 4. 유효성 검사 에러와 일반 에러는 응답 구조가 다르다

일반 에러는 원인이 하나라서 메시지 하나면 충분하지만, 유효성 검사 에러는 여러 필드가 동시에 틀릴 수 있어서 `errors` 배열로 필드별 에러를 알려줘야 한다. 이래야 프론트에서 각 입력창 밑에 에러 메시지를 붙일 수 있다.

DTO에 `@NotBlank` 같은 어노테이션을 달고, Controller에서 `@Valid`를 붙이면 자동 검사된다. 단, `spring-boot-starter-validation` 의존성이 있어야 동작한다.

### 5. BaseEntity로 중복 코드를 줄일 수 있다

거의 모든 테이블에 `created_at`, `updated_at`이 필요한데, 매번 쓰는 건 비효율적이다. `@MappedSuperclass`로 만든 BaseEntity를 상속받으면 자동 추가된다.

`@EnableJpaAuditing`을 메인 클래스에 안 붙이면 `@CreatedDate`, `@LastModifiedDate`가 동작 안 해서 null이 들어간다. 이거 빼먹어서 한참 헤맬 뻔했다.

### 6. application.yml을 환경별로 분리하는 이유

로컬에서는 `ddl-auto: create`로 테이블을 매번 새로 만들어야 개발이 편하고, 운영에서는 `validate`로 테이블을 절대 건드리면 안 된다. DB 비밀번호도 로컬은 하드코딩해도 되지만 운영은 환경변수로 숨겨야 한다.

`application.yml`(공통) + `application-{환경}.yml`(환경별 오버라이드) 구조로 분리하면 `spring.profiles.active` 값만 바꿔서 환경을 전환할 수 있다.

### 7. CORS는 브라우저의 보안 정책이다

CORS 에러는 서버가 아니라 **브라우저**가 차단하는 거다. 프론트(localhost:8000)에서 백엔드(localhost:8080)로 요청할 때 포트가 달라서 "다른 출처"로 판단하고 차단한다.

`CorsConfig`에서 허용할 출처를 등록하면 해결된다. 나중에 같은 도메인으로 배포하면 CORS 문제가 없지만, 로컬 개발에서는 반드시 설정해야 한다.

### 8. 로컬 DB는 Docker로 띄우는 게 낫다

PC에 MySQL을 직접 설치하면 팀원마다 버전이 다를 수 있고, 설치/삭제가 번거롭다. `docker-compose.local.yml`로 MySQL 컨테이너를 띄우면 팀원 전원 같은 환경, `docker-compose up -d` 한 줄로 세팅 끝.

MySQL 8.0에서 `Public Key Retrieval is not allowed` 에러가 나는데, JDBC URL에 `allowPublicKeyRetrieval=true`를 추가하면 해결된다. MySQL 8.0의 인증 방식(caching_sha2_password) 때문에 발생하는 거다.

---

## 느낀 점

초기 세팅이 단순히 "프로젝트 만들기"가 아니라, 팀 전체의 개발 패턴을 정하는 과정이라는 걸 느꼈다. 공통 응답 포맷, 에러 코드 체계, 예외 처리 흐름을 처음에 제대로 잡아두면 이후 도메인 개발할 때 "어떻게 에러 처리하지?", "응답 형식을 어떻게 하지?" 고민 없이 정해진 패턴대로 하면 된다. 초기 세팅에 시간을 들인 만큼 나중에 돌아올 거라고 생각한다.
